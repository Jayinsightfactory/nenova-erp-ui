# 서버 지연 확인과 복구

운영 서버 프로젝트 디렉터리에서 `node scripts/server-work-summary.cjs 30`을 실행하면 최근 30분의 응답 시간·HTTP 오류·지연 구간과 CPU, RSS, 이벤트 루프 지연을 집계한다. GitHub Actions의 기존 읽기 전용 성능 진단도 같은 집계를 출력한다. 새 HTTP 진단 권한이나 공개 API는 없다.

* `focusRoutes`에는 로그인·내 업무·업로드·드라이브·주문 등의 우선 점검 경로를 항상 표시한다. 0건은 완료 요청 표본이 없다는 뜻이다. `slowSamples`는 느리거나 실패한 요청 표본을 경로·GET/POST 등으로 나누고, 가장 오래 걸린 **동일 요청**의 HTTP 상태와 계측된 단계 시간을 보여 준다. 전역 `slowStageMaxMs`를 특정 주문의 원인으로 해석하지 않는다. DB 구간은 중첩되거나 동시에 실행될 수 있고, 계측되지 않은 시간이 SQL 잠금이라는 뜻은 아니다.
* 운영 중 빠른 확인: 기존 Cafe24 배포 워크플로의 수동 입력 `work_summary_only=true`는 웹을 다시 시작하거나 배포하지 않고 최근 60분의 업무 로그만 집계한다. 장시간 nginx 이력을 다시 읽지 않는다. 측정 구간이 겹치면 요청 수를 서로 더하지 않는다.
* 발주 엑셀 미리보기는 작업자 하나가 기존 원본 복사와 시트 해석을 처리한다. 큐에는 임시 경로만 유지하며 추가 대기는 최대 20건, 20초이다. 처리 제한 45초. 과부하 시 해당 미리보기에 재시도 가능한 503이 반환되며, 주문 등록을 자동 재실행하지 않는다.

* data/runtime/server-logs/work-YYYY-MM-DD.jsonl: UTC 일자별 파일, 최근 7일, 파일당 최대 16MiB. 분 단위 전체 호출수/응답시간 분포와 느린 요청(1초 이상), 5xx, 전송 중단의 표본을 기록한다. 정해진 정적 API 경로 또는 other-api만 저장한다. URL 쿼리, 사용자명, 파일명, 내용, 인증정보는 기록하지 않는다. 로그 쓰기 지연·실패는 요청을 막지 않는다. 분석의 p95BucketMs는 해당 표본 p95의 구간 상한이다. minute이 없는 구간은 관측 누락이며 정상으로 간주하지 않는다.
* 전체 API가 함께 느리고 loopMaxMs/CPU가 높으면 해당 시각 CPU 작업·이벤트 루프 정지를 조사한다. CPU%는 코어 합산이다. dbPool/dbQuery가 길면 연결 준비 또는 SQL 요청(풀 대기 포함)을 조사한다. 개인 파일/지침/품질/업로드 접수 대기·파싱·저장·송금 구간은 별도로 기록된다. 구간은 중첩될 수 있어 합산하지 않는다.
* 업로드는 한 웹 프로세스당 2개 본문을 받고 추가 24개 연결만 최대 15초 대기한다. 초과는 503+Retry-After. 원본·색인 저장 전에는 성공을 반환하지 않는다. 직원 데몬의 기존 5분 재시도와 로컬 발신함은 별도 PC 변경 범위이다.
* 저장과 CPU 분석은 웹과 다른 낮은 우선순위 자식 프로세스에서 수행한다. 상한은 각각 V8 old-space 256MiB이며 전체 RSS 제한이 아니다. 접수 작업 제한은 45초, 짝 분석은 10분이다. 메모리·디스크·CPU가 같은 호스트에 있으므로 자원 여유를 계속 관측한다.
* data/drive/pair-jobs의 미처리 표식은 서버 재시작 후 복구된다. data/drive/mirror-jobs에는 경합 시 임시로 원본과 메타정보가 들어가므로 운영 드라이브와 같은 권한/백업으로 관리한다. 반복되는 PAIR_JOB_RETRY, 미처리 증가 또는 빈 디스크 부족 시 웹 조회를 우선 유지하고 분석 오류/디스크를 조사한다. 해당 폴더를 지우거나 송금 처리 요청을 무조건 재생하지 않는다. 송금 DB 쓰기와 업무별 최종 성공 의미는 기존 계약을 따른다.
* 롤백은 이전 검증 빌드로 진행하되 드라이브 원본·색인·대기 파일은 보존한다. 구버전은 새 대기 파일을 처리하지 않으므로 호환 작업자를 복구한 후 소진을 확인한다. 새 저장소 구매·전체 직원 PC 변경·ERP 스키마 변경은 없다.
