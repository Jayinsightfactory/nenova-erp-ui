# 정본 — 모든 에이전트가 작업 전에 읽는 판단 기준

> 이 저장소에서 일하는 Claude Code · Codex · PM 조사관이 **같은 기준**으로 판단하도록 한 곳에 모은 문서다.
> 길어지면 아무도 안 읽는다. 이 파일은 **판단 기준과 "어느 규칙이 어디에 있는가"** 만 담고, 도메인 규칙 본문은 옮겨 적지 않는다.
> 고칠 때는 이 파일 하나만 고친다. 다른 지침 파일에 같은 내용을 복사하지 않는다.
> 검사: `npm run test:canon` (정본이 있고, 각 지침 파일이 이 경로를 가리키는지만 본다. 판단 품질은 검사하지 않는다.)

기준일 2026-11-12 · 근거 조사: [`RULE_FILE_INVENTORY_2026-11-12.md`](RULE_FILE_INVENTORY_2026-11-12.md)

## 1. 판단 우선순위

둘이 부딪히면 위쪽이 이긴다.

| 순위 | 기준 | 뜻 | 근거 |
|---|---|---|---|
| 1 | **돈·숫자 정합** | 금액·수량·재고·청구가 정답(엑셀 물량표·매출원가 양식·`nenova.exe` 화면)과 숫자 하나까지 맞는가. 고친 뒤 견적·매출에 누락이 생기지 않는가. 이미 맞던 값을 바꾸지 않았는가. | 학습 기록 확인됨 |
| 2 | **현장 수용성** | 직원이 설명 없이 화면만 보고 일을 끝낼 수 있는가. 카톡·엑셀로 하던 방식 위에 덧씌우는가(새 도구 사용을 강요하지 않는가). | 학습 기록 확인됨 |

아래 둘은 2026-11 기획 대화에서 나온 기준이다. 사장님 지시 이력에서 학습된 기록과 **맞지 않거나 근거가 없어** 순위에 넣지 않았다. 사장님 확인 뒤 넣거나 버린다.

| 확인 필요 | 기획 대화의 주장 | 걸리는 점 |
|---|---|---|
| 하드코딩 탈피 | 규칙을 코드에서 빼서 데이터·자연어로 바꾼다 | 학습 기록은 반대 방향이 더 강하다: "기존 로직 + A 방식으로 덧붙여서 이미 맞는 값이 바뀌지 않아야", "exe 산식·수식 변경 금지". 순위 1과 부딪히면 **순위 1이 이긴다**(이 부분은 확정). |
| 확장성(다른 업종 이식) | 네노바 전용이 아니라 다른 업종에도 쓸 수 있게 | 제품화 의도는 기억 기록에 있으나 판단 기준으로 학습된 적은 없다. 이 저장소에서 지금 적용되는 것은 `/pm` 판매 예정 코드의 경계 검사(`npm run test:pm-boundary`) 하나다. |
| 네 기준의 순서 | 이익 방어 > 현장 수용성 > 하드코딩 탈피 > 확장성 | 순서를 뒷받침하는 기록이 없다. "역마진"이라는 낱말도 학습 기록에 없다. |

## 2. 사고 순서

지시 종류에 따라 다르게 쓴다. **수정·버그 지시에 긴 사전 분석을 붙이지 않는다.**

- **수정·버그·실행 지시** — 원인 실측 → 수정 → 같은 유형 전수 점검 → 테스트 → 운영 화면에서 재확인 → 증거와 함께 보고. 승인 질문은 되돌리기 어려운 작업에만 한다.
- **새 기능·기획 지시** — 아래 순서로 쓴다.
  1. 현장 문제: 직원이 실제로 어느 화면에서 어느 칸을 보고 무엇을 하는가(추측으로 흐름을 지어내지 않는다)
  2. 기존 구조 어디에 붙는가: 이미 있는 화면·기능·자산을 먼저 찾고 거기에 덧붙인다. 9단계(발주→입고→분배→출고→견적→거래처 전달→입금→해외송금→이익) 중 어디인지 적는다
  3. 측정 방법: 끝났다는 기준을 숫자로 확인할 수 있게 적는다. 못 정하면 만들지 않고 결론만 낸다
- **확인 필요** — 기획 대화는 1과 2 사이에 "다른 회사는 어떻게 하나 → 기존 도구의 한계 → 우리 방식"을 매번 넣자고 했다. 사례는 있으나(기술 레이더, 업계 비교 자료) 매 작업의 고정 단계라는 근거는 없고, "모든 작업에 외부 검색을 강제하지 않는다"는 기존 기준과 부딪힌다. 지금은 **사장님이 비교를 요청한 기획에만** 쓴다.

## 3. 반드시 지킬 것

1. **제안에는 가장 큰 약점을 1개 이상 적는다.** 실행 지시에서 발견한 부족점은 묻지 말고 보완한 뒤 보고한다.
2. **근거 없는 수치는 "가설"이라고 표시한다.** 측정한 값만 수치로 쓴다. 확인하지 못한 것은 "미검증"이라고 쓴다.
3. **지금 만들 것과 장기 비전을 구분해서 적는다.** 한 문단에 섞지 않는다.
4. **측정 방법이 없는 기능은 측정 방법과 같이 제시한다.** 측정 방법을 못 붙이면 다음 단계로 넘기지 않는다.

## 5. 어느 규칙이 어디에 있는가

같은 규칙을 두 곳에 적지 않는다. 새 규칙은 담당 파일 한 곳에만 넣는다.

| 주제 | 담당 파일(한 곳) | 읽는 도구 |
|---|---|---|
| 판단 기준·충돌 우선순위 | 이 파일 | 전부 |
| ERP 원장 변경 절차·계약·검증 명령 | `AGENTS.md` | Codex 자동, Claude는 `erp-contract-guardian`·스킬 경유 |
| DB 쓰기 규칙·출고일 계산·진단 API·빌드 주의 | 루트 `CLAUDE.md` | Claude Code 자동 |
| 세션 시작 체크리스트·보존 태그 | `.claude/CLAUDE.md` | Claude Code 자동 |
| 합의 보존·되묻기 기준(바뀐 항목만 교체, 이미 받은 답 재사용) | `.claude/rules/insight-agreement.md` — 넷째 줄이 가리키는 `insight-requirement-review` 스킬은 아직 본편에 없다(메인 작업 폴더에만 있음). 없으면 그 줄은 건너뛴다 | Claude Code 자동 |
| 사용 라이브러리 | 루트 `CLAUDE.md` "사용 라이브러리"(목록의 정답은 `package.json`) | Claude Code 자동 |
| 하위 에이전트 역할 | `.claude/agents/*.md` | Claude Code |
| 새 메뉴·화면틀·가이드 영상 | `docs/MENU_DEVELOPMENT_DEFAULTS.md` · `docs/UI_LAYOUT_AND_MENU_CONTRACT.md` · `docs/WORKFLOW_VIDEO_GUIDES.md` | 전부(`AGENTS.md`·`CLAUDE.md`가 가리킴) |

## 6. 수정 + "왜" 기록 형식 (`why-log.jsonl`)

한 줄에 수정 하나(JSON). **사람이나 에이전트가 결과물을 고쳤고 그 이유가 다음에도 쓸모 있을 때**만 적는다. 모든 저장 기록을 옮겨 적지 않는다.

| 필드 | 뜻 |
|---|---|
| `id` | `연월일-짧은이름` (중복 금지) |
| `date` | 수정한 날 `YYYY-MM-DD` |
| `area` | 업무 영역(견적·분배·물량표·빌드 등) |
| `before` / `after` | 고치기 전 / 고친 뒤(한 줄씩) |
| `why` | 왜 고쳤는가. 모르면 "모름"이라고 적는다(지어내지 않는다) |
| `why_source` | `stated` 고친 쪽이 그때 직접 말하거나 적은 이유 · `inferred` 나중에 추정한 이유 · `unknown` 이유 없음 |
| `decided_by` | `owner` 사장님 · `staff` 직원 · `agent` 에이전트 · `unknown` 기록으로 확인 안 됨 — 누가 고치자고 정했는가 |
| `evidence` | 근거 위치(수정안 번호, 파일·줄, 기록 문서) |
| `status` | `case` 사례 1건 · `candidate` 원리 후보 · `rule` 담당 파일에 규칙으로 들어감 · `retired` 폐기 |
| `valid_until` (선택) | 성수기·특정 차수에만 맞는 수정이면 끝나는 때 |
| `rule_ref` (선택) | `status=rule`일 때 규칙이 들어간 파일·줄 |

지켜야 할 것: 이유를 직접 말한 기록(`why_source: stated`)이거나 사장님이 직접 정한 것(`decided_by: owner`)만 `rule`이 될 수 있다(검사가 막는다). 사장님이 정했지만 이유를 말하지 않았으면 `why`에 추정이라고 적고 지어내지 않는다. 과거 저장 기록을 소급해 모은 것은 "왜"가 없으므로 `candidate`까지만 간다(2026-11-12 첫 수집: [`FIX_HISTORY_BACKFILL_2026-11-12.md`](FIX_HISTORY_BACKFILL_2026-11-12.md), 대표 8건). `candidate` → `rule`은 사장님 승인으로만 한다.
