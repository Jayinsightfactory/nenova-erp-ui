# 견적서 선택 유지 / 품종 한정 확정 사이클

## 작업 범위

사용자 요청: 코드 수정과 버튼별 검증만 수행한다. 운영 저장/삭제/확정/확정취소, 데이터 보정, 원격 업로드, 병합, 배포는 하지 않는다.

## 확인한 결함

- 목록 재조회가 현재 선택을 버리고 첫 거래처를 선택한다. 목록, 상세, 불일치 조회에 최신 요청 판별이 없어 늦은 응답이 다른 거래처 내용을 덮는다.
- 통합 저장은 계산된 품종을 로그에만 쓰고 실제 확정 사이클에 빈 품종 배열(전체)을 전달한다.
- 확정취소 일부 성공 후 실패한 차수는 복구 목록에 추가되지 않아 이미 취소한 품종이 남는다.
- 웹의 '같은 차수의 모든 미확정 품종을 함께 확정' 정책은 실제 EXE의 선택 CountryFlower 확정 동작과 다르다. 기존 테스트를 근거로 전체 취소를 유지하면 안 된다.

## 필수 조건

- 모든 범위는 OrderYear+OrderWeek를 명시한다. 같은 차수의 다른 연도는 제외한다.
- 확정 범위는 CountryFlower이며 stockProdKeys는 재고 합산 범위일 뿐 확정 범위가 아니다.
- 목록을 B 거래처로 유지할 때 첫 거래처 A의 상세를 사용하지 않는다.
- 실패/늦은 응답/이전 연도 응답은 선택, 상세, 불일치, 로딩 상태를 덮지 않는다.
- 가격 전용 저장, 기존 네 등록 버튼, 선택 삭제, 담당자/요일/출력 기능은 보존한다.
- 추가 품목 모달의 단가·출고일 후보도 업체/품목/모달 열림 회차별 최신 요청만 적용한다. 이전 업체 응답을 새 업체의 후보로 사용하지 않는다.
- 버튼 감사에서 발견한 사전검증 실패를 정상으로 간주하는 경로를 수정한다. 조회 실패 차수를 안내하고 확정 요청은 보내지 않는다.
- 다중 출력에서 일부 업체의 조회 실패는 전체 성공으로 처리하지 않는다. 누락 업체명을 알려주고 해당 문서는 생성하지 않는다. 정상 조회된 0행은 실패가 아니다.
- 허용된 부작용과 실제 SP 동작은 CLI EXE 근거 및 현재 DB SELECT로 대조한 뒤 수정한다.

## 검증

거래처 재조회 유지, A→B 늦은 응답, 필터/연도 변경, 상세 실패, 저장 후 재조회, 품종 1개/복수/빈 값, 일부 취소 성공 후 실패 복구, 2025/2026 동일 차수, 가격 전용 무확정 사이클, 버튼별 실제 호출 경로를 검사한다. 운영 자료 쓰기 없이 자동 검사와 로컬 화면 검사로 확인하며 실제 운영 저장 시험을 했다고 보고하지 않는다.

## 완료 상태

위 범위의 코드와 재발 검사 연결을 완료했다. 전체 ERP 계약·견적·선택 차감 삭제·게시판·dnSpy 근거·변경 범위·쓰기 보호·운영용 빌드 통과. 로컬 가짜 자료 화면에서 업체 유지와 네 등록 모달·확정현황 진입을 확인했다. 운영 EXE와 DB 프로시저/연도/관련 행은 읽기 전용으로 대조했다.

운영 저장 및 배포는 하지 않았다. 별도의 수동 여러 차수 취소와 여러 종류 동시 저장 등 잔여 위험은 `2026-08-26_estimate-button-audit.md` 상단에 명시했다. 기존 운영 자료를 복구·변경하거나 모든 버튼의 실제 저장까지 시험했다고 해석하면 안 된다.

## 후속 요청: 모든 재조회 경로 통일

사용자가 원인 진단을 다시 제시하고 통일 작업을 명시 요청했다. 기존 미배포 수정본을 보존하고 화면 상태만 추가 보강한다. API/SQL/계산식/저장 payload/확정 사이클은 이번 후속 변경 대상이 아니다.

### 기준 장부

| 사용자 동작 | 적용 기준 | 주문/분배/견적/재고 원장 영향 |
| --- | --- | --- |
| 업체 검색어 입력·붙여넣기·한영 전환 | 검색 초안만 변경. 선택된 업체·상세·저장 대상은 보존. 검색 후보 선택 전 전체 조회 금지 | 모두 보존 |
| 검색 결과 업체 명시 선택 | 선택한 CustKey를 적용. 이전 후보 응답 무효화. 기존 전체 요일 기본값 유지 | 모두 보존 |

| 수량·단가·통합·추가품목·품목정보·차감 저장/삭제 후 재조회 | 저장 시작 범위를 캡처하고 공통 재조회 함수 사용. 현재 범위와 다르면 시작/반영 모두 무시. 목록→선택 업체 상세 순으로 한 번 조회 | 재조회 자체는 모두 보존. 기존 저장 부작용 계약 변경 없음 |

직접 EXE CLI의 `FormEstimateView.GetDetailLoad`는 focused row의 CustKey를 `GetDetail(custKey)`에 넘긴다. 현재 웹의 소스상 부족한 부분은 검색 onChange/한글 키 처리의 `setSelectedCust(null)`, 단가 오류 후 상세+목록 중복 재조회, 선택 삭제 뒤 별도 직접 setItems, 품목정보의 상세만 재조회다. 이들을 공통 규칙으로 통일한다.

수용 검사: 2026년34차 신라 선택→조회 유지, 검색어만 변경/빈문자/한영 전환 보존, 명시 다른 업체 선택, 2025 동일차수 응답 무시, A 저장 중 B 선택 후 늦은 A 완료 무시, 같은 업체 새 조회 중 옛 상세/오류 무시, 삭제 후 0행, 각 저장 경로의 공통 재조회 사용. 운영 저장 없이 가짜 응답과 로컬 화면으로 검사한다.

### 후속 구현 결과와 검증 경계

- 일반/자동 조회와 수량·단가·통합·등록·삭제·품목정보 저장 뒤의 재조회를 `refreshCapturedEstimate`로 통일했다. 저장 시작의 업체·연도·차수·필터를 보존하고, 현재 화면이 다른 범위이면 이전 저장 완료 콜백을 적용하지 않는다.
- 검색 입력/붙여넣기/한글 키 처리/한영 전환은 초안만 바꾼다. 후보 선택과 명시 필터 해제만 실제 조회 대상을 바꾸며, 조회 결과가 없는 업체를 첫 업체로 대체하지 않는다.
- 새 목록 요청은 같은 업체의 과거 상세·불일치 요청도 무효화한다. 늦은 오류·대체 조회·로딩 종료도 현재 화면을 덮지 않는다. 저장 후 편집 기준값 갱신 역시 성공한 저장의 업체 범위가 현재와 같을 때만 수행한다.
- 단가 저장 뒤 지연 구간에서도 범위를 다시 확인하여 새 업체의 미저장 단가를 지우지 않는다. 실제 저장은 성공하고 재조회만 실패하면 `저장 완료 · 다시 조회 필요`를 표시한다.
- 새 `estimateRefreshFlow.test.js`는 실제 페이지의 검색 JSX 콜백, 단가 저장 함수, 상세/목록 조회 함수를 구문 분석 후 격리 실행한다. 가짜 응답과 타이머로 업체 전환·같은 업체의 새 조회·늦은 실패를 재현한다. 실제 DB 요청이나 저장은 실행하지 않는다.
- 이번 후속 수정본의 브라우저 클릭 시험은 연결 오류(`Tabs can only be moved to and from normal windows`)로 완료하지 못했다. 위의 이전 단계 로컬 화면 성공은 후속 수정 전 근거이며, 이번 화면 검사 성공으로 재사용하지 않는다. 자동 실행 검사와 운영용 빌드 성공도 실제 운영 저장 성공을 뜻하지 않는다.
- 새 커밋·원격 전송·병합·배포, 운영 저장·삭제·확정 변경은 하지 않았다. 자동 검사 최종 결과는 같은 날짜 세션 기록에 남긴다.
