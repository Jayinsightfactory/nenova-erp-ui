### 6. 콜롬비아 1차/2차 N21:N24 DIV/0 템플릿 경고

- 수식: `N21=+M21/L21` (장미), `N22=+M22/L22`(카네이션), `N23`(알스트로), `N24`(루스커스) — 6차수 전부 동일 패턴.
- `L21:L24`(판매금액)는 6차수 전부 완전히 비어 있다(값도 수식도 없음). `M21:M24`는 `+L-K` 라서 결국 0이거나
  음수(K만 채워진 경우).
- 즉 이 셀들은 라이브 Excel에서 열면 **분모가 빈칸이라 `#DIV/0!`가 뜨는 게 정상**인 템플릿 잔재 행인데,
  xlsx 파일 안에 저장된 캐시값은 6차수 전부 예외 없이 `7`이다 — 실제 결과가 아니라 과거 어느 시점(L열에
  값이 있었을 때)의 스테일 캐시로 보인다. **수식이 셀 참조가 아니라 캐시값이라 원본과 대조가 안 되는 대표
  사례**라 `expectedAnomalies`에 넣고 원인 확정은 하지 않았다(unknownReason에 해당하지만 별도 필드 없이
  anomaly 설명에 서술로 남김).

### 7. 이스라엘/뉴질랜드/일본 행의 공식 변형 (신규 확인, 요청 항목은 아니었으나 발견된 사실이라 기록)

- 다른 13개 카테고리: `I = E+G+H-F`, `J = C-I`, `K = J/C`
- 이스라엘(18행)·뉴질랜드(19행)·일본(20행) 3개만: `I = E+G+H` (F 미차감), `J = C-I+F`, `K = J/(C+F)`
- 6차수 전부 동일 패턴으로 재확인. 왜 이 3개국만 F를 I가 아니라 J·K 쪽으로 옮겼는지는 원본에서 근거를
  찾을 수 없어 `formulaVariants.unknownReason`에 "알 수 없음"으로 명시했다(임의 해석 금지).
  참고: `docs/work-reports/2026-08-11_profit-report-source-guide.md` 38~40행에 이미 코드 쪽 반영 사실이 있어
  이번 실측이 그 문서와 일치함을 재확인한 셈이다.

## 원본과 대조가 안 되는 부분 (수식이 셀 참조가 아니라 캐시값인 경우 등)

- 위 6번(콜롬비아 N21:N24)이 정확히 이 유형이다 — `xlsx` 모듈은 마지막 저장 시점의 캐시값만 읽고
  라이브 재계산을 하지 않으므로, 파일을 실제 Excel/LibreOffice로 열어 재계산하면 다른 값(또는 오류)이
  나올 수 있다. fixture에는 **캐시값**을 그대로 넣었고 "라이브로 열면 다를 수 있다"는 사실을 anomaly에
  명시했다.
- 5번(J78 결측)도 동일 계열 — 배열수식이었을 것으로 추정되는 자리에 캐시 결과조차 없어(`v`, `f` 둘 다 undefined)
  셀이 완전히 빈 것과 구분이 안 된다. 어느 원인인지는 fixture에 단정하지 않았다.
- **[2026-08-11 정정]** 24차 파일에만 `Sheet1`이라는 보조 시트가 하나 더 있다(다른 5개 차수엔 없음)는
  사실은 맞지만, "빈 시트"라는 서술은 **오류**였다. 실측 결과 `Sheet1`은 값 63개·수식 14개가 들어있는

## 전체 67시트 구조 전수조사 (2026-08-11 보완)

**이번 보완 작업의 성격을 명확히 한다:** 아래는 6개 파일의 **모든 시트를 `XLSX.readFile(..., { cellFormula:true, cellNF:true, cellDates:true })`로 직접 열어 `wb.SheetNames` 전체와 시트별 셀 개수·수식 개수를 실측한 구조 전수조사 + 부속 시트가 어느 코드 경로와 연결되는지 확인한 결과다.** 위쪽 섹션들(1~7번, 원본 대조 항목)에 적힌 "메인 시트는 완전 추출, 부속 시트는 특정 셀만 확인"이라는 서술은 **셀 단위 값 대조 범위**에 대한 것이며 그 범위 설명은 그대로 유효하다 — 이번 보완이 새로 한 일은 "부속 시트 전체를 셀 단위로 대조"한 것이 아니라, "① 67시트 전부의 이름·셀개수·수식개수를 세고 ② 그중 메인 계산에 실제로 쓰이는 시트와 쓰이지 않는 시트를 코드(`lib/profitReport.js`, `lib/customsForwarding.js`, `lib/colombiaTruck.js`) 대조로 구분하고 ③ 눈에 띄는 이상 패턴(오류 캐시·캐시 없는 수식)이 더 있는지 전 시트 스캔한 것"이다.

### 3. `Sheet1`(24차) 상세 실측

`XLSX.utils.sheet_to_json(ws, {header:1})`으로 `A2:F16` 전체를 덤프한 결과:

```

A3  씨스타펀            B=100         E=-100  F3=SUM(B3:E3)=0
A4  엄브렐러펀           B=369  D=-195 E=-172  F4=SUM(B4:E4)=2

A7  반커부쉬             B=271  C=550 D=-310 E=-505  F7=6
A8  에뮤페더             (전부 공란)                 F8=0

F열 수식은 전부 `=SUM(Bn:En)`(n=3~16)이고 값 캐시가 정상적으로 붙어 있다(캐시 없는 수식 0건). "에뮤페더"·"에뮤그라스" 두 품목은 루트 `CLAUDE.md` "패턴 1: 고스트 출고 레코드" 회고의 실측 사례(Emu Feather Out=200 주문0, Fern Sea Star Out=50)와 이름이 겹쳐 눈에 띄지만, 이 `Sheet1`은 그 회고와 직접 연결된 근거 자료는 아니다(이 시트 자체엔 DB 키·주문/출고 구분이 없고 단순 기초/입고/출고/기말 숫자만 있다) — 우연히 같은 품목군(그린소재 필러)을 다루고 있다는 점만 기록해 두고 추가 해석은 하지 않는다.

**결론: 24차 `Sheet1`은 빈 시트가 아니라 값 63개·수식 14개의 그린소재 재고 대사 워크시트이며, 다른 시트에서 참조되지 않으므로 메인 계산에는 여전히 연결되지 않는다.** 위 139번째 줄 근방의 "빈 보조 시트" 서술만 오류였고, "메인 계산에 참조되지 않는다"는 결론은 실측으로 재확인되었다.

### 4. `품목리스트` 시트 — 새로 확인한 역할 (엑셀 내부에서는 사용됨)

`품목리스트`는 22~27차 전부 수식이 0건이라 "메인계산 미사용"으로 보이기 쉽지만, **엑셀 파일 내부의 다른 부속 시트가 이 시트를 INDEX/MATCH로 참조**하고 있다는 사실을 22차 파일 전체 수식 문자열 스캔(`f.includes('품목리스트')`)으로 확인했다:

| 참조하는 시트 | 참조 건수(22차) | 용도 |
|---|---|---|
| 판매현황 | 709건 (I열 전체) | `INDEX(품목리스트!$E$2:$E$9000, MATCH(...품목리스트!$C$2:$C$9000...))`로 품명(B열)을 국가로 자동분류 후 콜롬비아 세부품목/네덜란드/태국/중국 등 키워드 매칭까지 이어지는 다단 `IFERROR(IF(...))` 체인 |
| 불량차감 | 86건 (J열 전체) | 위와 동일한 국가분류 체인(품명 I열 기준) |
| 그 외 매출액 | 80건 (J열 전체) | 위 체인 앞에 "현지상차운임"/"루스커스 운송료" 등 운송료 항목 특수 매칭을 추가한 확장판 |

즉 `품목리스트`(품목번호/품목코드/품목명/꽃/국가/출고단가/출고단위/견적단위/비고, 22차 기준 3,031행)는 엑셀 자체의 카테고리 자동분류 로직이 참조하는 **원천 마스터 테이블** 역할을 한다 — 이는 웹 코드의 `Product.CounName` 기반 `CASE_CATEGORY`(`lib/profitReport.js`)·`baseCountry()`(`lib/countryClassification.js`)와 **개념적으로 동일한 역할**이지만, 웹 코드는 이 xlsx 시트를 직접 읽지 않고 DB의 `Product` 테이블 값을 그대로 쓴다. 그래서 위 표의 "메인계산 연결"란에는 "간접"으로 표기했다 — 엑셀 워크북 안에서는 다른 시트가 실제로 참조하는 활성 데이터지만, 지금 웹 코드 경로에는 이 시트 자체가 입력으로 들어가지 않는다는 뜻이다. 26~27차 등 다른 차수에서도 동일한 수식 패턴(체인 구조)이 반복되는지는 22차 1개 파일만 확인했다(전수는 아님).

### 5. 콜롬비아 1차/2차 N21:N24 재확인 — 오류 타입 상세

기존 6번 항목("캐시값이 6차수 전부 예외 없이 7")을 22차·27차 콜롬비아 1차/2차 4개 시트에서 셀 객체를 직접 찍어 재확인했다:

```
N21 {"t":"e","v":7,"f":"+M21/L21","w":"#DIV/0!","z":"0.00%"}
```

`t:"e"`는 SheetJS가 표시하는 Excel 오류 타입이고, `v:7`은 그 오류의 **내부 오류 코드**(Excel BIFF 오류코드 7 = `#DIV/0!`)이며, `w:"#DIV/0!"`가 실제로 셀에 표시되는 텍스트다. 즉 기존 문서가 "캐시값이 7이다 — 스테일 캐시로 보인다"고 적은 부분은, 정확히는 **"7"이 스테일 숫자가 아니라 `#DIV/0!` 오류 자체의 내부 코드값**이라는 뜻이다 — `xlsx` 라이브러리로 `.v`만 보면 7이라는 숫자로 보이지만 `.t`/`.w`까지 같이 보면 이 셀은 저장 시점에 실제로 `#DIV/0!` 오류였다(스테일 계산 결과가 아니라 정상적으로 캐시된 오류). 분모 `L21:L24`(판매금액)가 6차수 전부 완전히 비어 있다는 기존 서술은 그대로 재확인됐다. 원인(왜 L열이 항상 비는 템플릿 잔재 행인지)은 여전히 원본에서 근거를 찾을 수 없어 결론을 내리지 않는다.

### 6. 추가 이상 패턴 스캔 결과

67시트 전체에서 `t==='e'`(오류 캐시) 또는 `v===undefined && f`(캐시 없는 수식) 패턴을 스캔한 결과, **콜롬비아 1차/2차 N21:N24(6차수×2시트=12곳) 외에는 추가로 발견된 이상 셀이 없다.** 27차 `그 외 매출액!J78` 결측(셀 자체가 `v`/`f` 둘 다 `undefined`)은 기존 5번 항목에 이미 기록되어 있고, 이번 스캔에서도 재확인만 했다(같은 셀, 새로운 발견 아님).

const wb = XLSX.readFile(filePath, { cellFormula: true, cellNF: true, cellDates: true });
const ws = wb.Sheets['주차별 매출이익 보고서'];
// C7:U22 카테고리 행 + C23:U23 합계행을 셀 단위로 { value, formula } 추출
```

## 결론

- 22~27차 **6차수 모두 완전 추출** 완료. 막힌 부분은 "원본 자체의 결함/스테일 캐시"(위 5·6번)뿐이며,
  이는 추출 실패가 아니라 원본에 원래 존재하는 문제로 `expectedAnomalies`에 정확히 격리해 기록했다.
- fixture 안 모든 숫자는 원본 셀에서 실측한 값이며, 추정/보간한 숫자는 없다.
