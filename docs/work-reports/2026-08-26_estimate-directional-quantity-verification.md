# 견적서 수량 방향별 저장 — 최종 검증 및 운영 적용 조건

## 1. 이번 요청과 완료 범위

사용자: “구조 변경작업 시작, 수량이 늘어나는 작업에서만 수량검증하면되는거잖아.”

기존 “수정작업만 실행” 지시를 유지했다. 하위 작업에서 구현하고 메인이 통합·검증했다.
이번 결과는 **로컬 수정본**이다. 운영 안전장치 설치, 원격 전송·병합·배포, 실제 고객의
수량·단가·확정 상태 수정, 이미 부분 해제된 34-02 상태 복구는 수행하지 않았다.

## 2. 변경된 처리 방식

- 기존 출고일별 수량은 전체/품종 확정취소 없이 기존 확정 상태를 유지해 저장한다.
- 서버가 잠근 실제 출고일·상세 수량과 단위 환산으로 증가/감소를 판정한다.
- **부족재고 검사는 실제 증가에만 적용**한다. 감소나 동일 상세의 총량 불변 날짜 이동은
  기존 음수재고 때문에 차단하지 않는다. 연도·업체·단위·출고일 합계·동시 수정 검사는 유지한다.
- 확정 수량 변화는 `Product.Stock`에 native CANCEL(old)+FIX(new)의 순효과만 반영하고,
  수동 재고조정과 구분한 출고 이력을 기록한다. 변경 품목에만 native `usp_StockCalculation`을
  호출한다. 여러 차수의 같은 품목은 가장 이른 변경차수부터 한 번 계산한다.
- 수량이 0이면 기존 출고 상세/출고일/농장 연결 정리 정책을 적용하되 주문수량은 보존한다.
- 한 수량 저장 요청의 출고·금액·재고·이력·편집 기준값을 같은 트랜잭션에서 처리한다.
  계산/검증 실패 시 전체를 되돌린다. 미확정 상세는 확정 재고에 반영하지 않는다.
- 기존 단가만 수정하는 경로와 신규 품목 추가 경로는 분리한다. 신규 추가는 기존 ADD·농장
  배정과 수정 품종에 한정된 확정 사이클을 사용한다. 그 사이클은 영향을 받는 각 차수를
  계산한 후 다음 차수로 진행한다.
- 작업창에 경과 시간과 이 요청의 진행 상태를 표시한다. 공용 서버 로그는 접힌 참고 자료로
  분리하며, 작업 식별자가 없는 다른 사용자의 로그를 이번 작업의 성공 증거로 취급하지 않는다.
- 응답이 끊기면 “미저장”으로 단정하지 않고 다시 조회한 뒤 재시도하도록 안내한다.

### 계산식과 EXE의 관계

증가 전 검사: 직전 `StockMaster`에 해당하는 품목 `ProductStock` + 현재 `ViewWarehouse`
+ `CodeInfo.StockType` 조정 - 현재 확정/미확정 `ViewShipment` 전체 - 선택 상세의 양수 변화 합계.

출고 이력이 수동 조정으로 다시 합산되지 않도록 StockType 분류도 검사한다. 부족 판단은
기존 웹의 소수점 3자리 기준이며 native Fix의 정수 반올림보다 엄격하다. 예를 들어 -0.4박스도
웹에서는 부족이다. 반올림 정책까지 EXE와 동일하다고 보고하지 않는다.

## 3. 검증 근거

### 실제 구조 읽기

- dnSpy CLI로 `FormShipmentDistribution`의 품종별 확정취소와 별도 연결의 전체 품목
  재고계산 호출을 확인했다. 저장소 golden과 운영 프로시저 정의를 읽기 전용으로 대조했다.
- 운영 `StockType`, 연도 범위, 테이블/프로시저 구조를 SELECT로 확인했다.
- 운영 기록의 약 272.5초 작업과 부분 성공은 원인 분석 자료이며, 이번 수정본의 처리 속도
  측정값이 아니다. 운영에서 몇 초로 줄어든다고 보장하지 않는다.

### 격리된 실제 SQL 시험

로컬 전용 SQL Server 2022를 호환성 수준 130으로 실행했다. 운영은 SQL Server
13.0.7095.1이므로 실제 2016 엔진 시험과 동일하다고 주장하지 않는다.

`scripts/test-estimate-directional-sql.cjs`는 실제 API 코드를 격리 어댑터로 실행하고,
테스트 트랜잭션에서 저장된 native 재고계산 본문을 호출한다. 운영 연결은 사용하지 않는다.
인증·감사·작업권은 fixture 대체물이며, 운영 로그인·실제 작업권 시험을 대체하지 않는다.

통과한 주요 시나리오:

- 확정 10→9→10과 수량·금액·재고 복원
- 기존/후속 음수재고가 있어도 감소 저장
- 정상 미확정 증가 허용, 부족 시 `STOCK_SHORTAGE`, 확정 상태·확정 재고 불변
- 같은 품목의 여러 상세 증가 합산 및 부족 차단
- 날짜별 변경 이력의 정확한 출고일 기록
- native 실패/NULL 반환 시 출고·재고·이력 전체 복구
- 0으로 변경 시 출고 연결 정리 및 주문 보존
- 단가만 변경 시 재고 불변
- 다른 연도 동일차수·다른 품종의 시험 자료 불변
- SQL에서 `-3e-14`는 3자리 반올림 후 0, 실제 증가 후 잔량 `-0.001`은
  `STOCK_SHORTAGE`로 차단 및 전체 복구

소유자 보호 SQL 검사 `__tests__/stockGateOwnership.test.js --sql` 29개도 별도 전용 DB에서
통과했다. 다른 연결의 상태를 잘못 지우지 않음, 같은 연도/차수의 후속 계산 인계, 실패 후
대기 상태 유지, 오래된 소유 토큰 무효, 다른 연도 차단, 변경 스크립트 재실행을 검증했다.

- 로컬 빌드 화면에서 가짜 API 자료로 10→9 저장·재조회, 선택 업체 유지, 진행 시간 표시,

  의도적으로 지연한 가짜 응답 시간이며 운영 성능 증거가 아니다.

## 5. 운영 반영 전 필수 조건과 남은 제한

이번 구조에는 DB의 **작업 소유자 보호 기능 V2**가 필요하다. 기존 기능은 실패 후 다른
작업의 잠금을 지울 수 있으므로 앱 코드만 바꿔 안전하다고 판단할 수 없다.

운영 반영 지시 후 메인이 수행할 순서:

1. 현재 배포본·프로시저 정의·권한·모든 구버전 잠금 해제 호출을 다시 대조한다.
2. 새 웹 호환 코드를 준비하되 V2가 없으면 새 수량 경로는 실행하지 않는다.
3. EXE·웹·예약 작업의 쓰기가 모두 멈춘 구간을 확보하고 실행/후속 계산 대기가 없음을 확인한다.
4. 소유자 보호 스크립트를 적용하고 원래 EXE 호출 서명 유지·기능 검사를 확인한다.
5. 웹 적용과 제한된 실제 저장 검증을 조율한 뒤 정상 작업을 재개한다.

실행/대기 상태가 남아 있으면 시간 경과만으로 삭제하지 않는다. 별도 확인 없이 이미 부분
해제된 확정을 복구하거나 전산 수량을 보정하지 않는다. 운영 V2 설치와 배포는 아직 하지 않았다.

추가 제한:

- 2025년 이하 수정 및 후속 연도 재고 스냅샷이 존재하는 빠른 경로는 native 범위 제한 때문에
  차단한다. 현재 연도로 추정하거나 후속 연도 전체를 조용히 재계산하지 않는다.
- 원자성 보장은 **한 수량 저장 요청**에 해당한다. 단가·수량·신규품목을 여러 API로 순차
  실행하는 통합 저장 전체를 하나의 거래로 만든 것은 아니다. 부분 성공 상태를 구분해야 한다.
- 실사용자 권한, 운영 네트워크 단절, EXE와 실제 고객 원장을 동시 수정하는 시험은 미실시다.
  코드/fixture 통과를 “모든 운영 상황에서 무오류” 또는 “운영 반영 완료”로 표현하지 않는다.
