# 견적서관리 중복 수량 입력행 보강

## 증상과 원인

같은 품목이 위아래 두 행으로 표시된 화면에서 한쪽 수량을 입력하면 다른 입력칸도 함께
변경됐다. 화면의 수량 상태는 이미 `ShipmentDate.SdateKey` 기준이었지만, 조회 SQL의 JOIN이
같은 물리 `ShipmentDate` 행을 두 번 반환하면 두 화면행이 동일한 상태 키를 공유했다.

## 적용 기준

- 같은 `SdateKey`가 JOIN으로 반복된 경우만 한 번 표시한다.
- 같은 품목·같은 출고일이어도 `SdateKey`가 다르면 두 행을 유지하며 각각 수정한다.
- 차감행은 같은 `EstimateKey`의 반복만 제거한다.
- 단가 fallback의 `CustomerProdCost` 중복행과 차감 날짜용 `ShipmentDetail` 후보는 최신 실제
  한 행만 결정하여 조회 행 증가를 막는다.

## 부작용 범위

| 동작 | Order | ShipmentDetail | ShipmentDate | Estimate | 재고·확정·손익 |
|---|---|---|---|---|---|
| 견적 상세 조회·중복 정리 | 읽기/보존 | 읽기/보존 | 읽기/보존 | 읽기/보존 | 변경 없음 |
| 브라우저 수량 입력 | 변경 없음 | 변경 없음 | 저장 전 변경 없음 | 저장 전 변경 없음 | 변경 없음 |

기존 수량 저장 API와 방향별 재고검사·확정 상태 보존 계약은 변경하지 않는다.

## 회귀 검사

- 동일 `SdateKey` 중복 결과는 한 행만 남는다.
- 동일 품목·날짜의 서로 다른 `SdateKey` 두 건은 모두 남고 입력 키도 서로 다르다.
- 동일 `EstimateKey` 차감 중복은 한 행만 남는다.
- 화면 행의 React key도 실제 행 키를 사용한다.
