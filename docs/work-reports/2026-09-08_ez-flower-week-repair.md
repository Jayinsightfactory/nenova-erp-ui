# EZ Flower 입고 차수 정정

사용자 요청: 2026년 EZ Flower 잘못 입력된 07-09 입고를 37-01로 정정. 다른 차수 확정취소·재업로드 없이 처리.

## 범위 및 보존 계약

| 대상 | 허용 변경 |
|---|---|
| WarehouseMaster 7211 | OrderWeek만 07-09 → 37-01 |

원본 파일명, 원래 작업자와 시간은 보존한다. ViewWarehouse는 Master의 차수를 참조하므로 상세 재작성 없이 조회 차수가 이동한다. 조회 기반 후속 보고에서는 해당 입고의 차수 귀속이 달라진다. 저장된 확정 재고 스냅샷은 이번 작업에서 다시 계산하지 않는다.

- 입고는 CodeInfo.StockType 재고조정 종류가 아니므로 이력 이동으로 조정량 중복 계산하지 않는다.

사전 모의 실행 통과: 상세 11행, 이력 10행, ProductStock 692행 보존 대상 확인.

## 후속 중단된 재고 계산 복구 계획

실제 gate: RUN/CALC, 2026/07-09, 소유 연결953, 14:47:57.073 시작. 앞선 입고 차수 변경은 이 gate를 변경하지 않았다. SQL 실행 상태 조회 권한이 없어 소유 연결이 사라졌다는 단정은 금지한다.

사용자가 모든 직원 EXE·웹 쓰기 중단을 확인했다. 이 PC의 Nenova 프로세스 종료도 별도 확인했다. 직렬화 트랜잭션의 gate 행 잠금, StockMaster/ProductStock 배타적 잠금 NOWAIT 획득에 성공했으며 07-09 StockMaster는 없다. 실제 적용에서 이 조건을 다시 검사한다. 시간 경과만으로 해제하지 않는다.

추가 조회: 사용자는 15:49에 7211을 삭제하고 15:50에 7213(37-01, Invoice2614580)을 재업로드했다. 7211/7212를 복원하지 않으며 최신 7213과 입고·삭제 이력을 그대로 보존한다. 7211 기준 사전 검사가 실패하여 운영 쓰기 없이 중단한 뒤 현재 근거로 재검증했다.

허용 변경: 정확한 gate 상태 전체 일치(CAS) 시 회복하고, 같은 외부 트랜잭션에서 ProdKey 2565/2829/3353/3354/3355/3356/3357만 native usp_StockCalculation(2026,37-01,pk) 순차 실행. ProductStock의 해당 품목·37-01 이후 49개 행만 계산 결과 변경 가능. StockMaster 및 과거/다른 품목 스냅샷, Product.Stock, 입고 상세/이력, 주문/분배/출고일/농장/확정 상태는 보존. 감사 기록 1행 추가. FIX/CANCEL 및 게이트 프로시저/정의 변경 없음.

독립 계산은 직전 36-02 저장재고 + 각 차수 입고 - 확정출고 + StockType 재고조정을 사용하며 SQL과 동일하게 소수2자리 반올림한다. 37-01 기대값: 2565=60,2829=100,3353=50,3354=90,3355=40,3356=150,3357=80. 구형 NULL 차수 메타데이터는 계산 대상에서 제외하며 미래 계산 범위·직전값에 중복 차수가 있거나 다른 연도가 포함되면 중단한다.

모의 실행 통과, 계산 self-test 통과(이월/연도격리/NULL/중복·미래연도 차단/반올림). 다른 품목 482958행 SHA256·개수, 전후 보존 스냅샷, 49행 독립 계산 결과 및 gate idle를 commit 전 검사. 실패·deadlock·timeout 시 전체 rollback한다. 운영 적용은 아직 미실행.

### 복구 실행 완료

첫 실행은 7개 native 계산이 성공했으나 50-01(StockKey94) 재고0이 기대60과 달라 전체 rollback했다. 기존 SP는 임시 차수 목록 생성에는 ORDER BY가 있지만 실제 cursor SELECT에는 ORDER BY가 없다. 복구 호출을 기존 7개 차수 순서(37-01,37-02,38-01,38-02,39-01,39-02,50-01)로 명시하고 각 차수에서 7개 품목의 native CALC를 실행했다. SQL 프로시저 정의·공식은 변경하지 않았다.

두 번째 실행에서 같은 49행이 모두 독립 계산과 일치하여 commit 완료. 다른 품목482958행의 SHA256/개수, 전체 StockMaster, 전체 Product.Stock, 입고원장/이력 및 대상 주문·출고·날짜·농장 조회가 전후 동일했다. 백업 scripts/ez-gate-recovery-1788852579864-before.json. 리뷰에서 이후 차수 신규 추가 시 범위확대 가능성을 지적하여 보관 스크립트에 정확한 7차수 목록과49행 강제검사도 추가했다. 실제 커밋 출력과 사전 조회의 실행 범위는 승인된 7차수49행 그대로였다.

별도 신규 DB연결 검증: gate Mode/Action/OwnerSessionID=NULL, PendingCalc=0. 현재7213입고 37-01/2614580 11행 유지, 07-09 StockMaster0. 37-01 재고는 60/100/50/90/40/150/80. 업무 확정 SP를 호출하지 않고 36-01 FIX 게이트 입장/실패종료 경로만 별도 트랜잭션에서 검사했으며 enter=0/leave=0/idle 후 rollback했다. 실제 출고확정·취소는 실행하지 않았다.

별도 발견·미변경: 3356 ZOFIA는 사용자의 두 번 삭제/재업로드 이후 Product.Stock=350이다. 동일품목2개행 삭제 이력의 BeforeValue가 같은250으로 반복되어 각각150/200이 기록되는 현상이 있다. 이번에는 최신 사용자 현재고를 임의 조정하지 않았고 37-01 입고 기반 ProductStock150과 구분한다. 해당 legacy 삭제 처리의 현재고 차이는 별도 확인이 필요하다. 자동 orphan 재발 방지나 SP 자체 cursor 정렬 수정은 이번 단일 데이터 복구에 포함하지 않았다.
