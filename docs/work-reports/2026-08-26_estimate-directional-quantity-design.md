# 견적 수량 방향별 저장 — 구현 기준 및 검증 범위

상태: 로컬 구현·격리 SQL 검증 완료. 운영 설치·배포 및 고객 원장 저장은 하지 않음.
검사 결과와 적용 조건은 `2026-08-26_estimate-directional-quantity-verification.md` 참고.

## 승인 및 근거

사용자 2026-08-26: 구조 변경 시작, 수량이 늘어나는 작업에서만 수량 검증.
여기서 생략 가능한 것은 **재고 부족 검사**이며 입력 유효성, 실제 원장 대조,
출고일 합계, 동시 수정 보호, 단위 환산은 생략하지 않는다.
16:29 KST 운영 SELECT로 usp_ShipmentFix/Cancel/StockCalculation 및 gate 정의 재확인.
실제 native 확정 SP는 감소 여부와 무관하게 부족 검사를 실행한다. 따라서 클라이언트의
skip 검사만으로 요구사항을 충족한다고 주장할 수 없다.

## 저장 기준 및 부작용

| 단가·비고만 | 보존 | 해당 금액·비고만 | 보존 | 보존 | 보존 |

| 동일 상세의 총량 불변 날짜 이동 | 보존 | 날짜별 수량·금액·이력과 합계 검증 | 보존 | 보존 | 재계산 없음 |

0 수량 출고의 상세·일자·농장 정리는 기존 purge 정책만 사용하며 주문을 삭제하지 않는다.
농장 수량을 임의 재배분하거나 Estimate/WebProfitReport를 직접 쓰지 않는다.

## 고정 조건 (criteria ledger)

- year/week/customer: 요청과 잠금 조회한 ShipmentMaster 모두 일치, 현재 연도 추정 금지.
- 증가/감소: 서버가 잠금 조회한 실제 ShipmentQuantity를 마스터 단위로 환산하여
  SdetailKey별 총량 변화를 계산한다. 서로 다른 품목·차수·상세의 증가를 감소로 상계하지 않는다.
- 기존 출고 수량의 양방향 저장을 단일 transaction으로 통합한다. 증가한 상세는 쓰기 전
  부족 검사를 수행한다. 다른 품목·차수 감소로 상계하거나 클라이언트 방향을 신뢰하지 않는다.
- 확정 감소: 필수 editGuard 검증, 재고 gate 행 잠금 후 NULL 상태에서만 실행.
  타 작업 RUN/WAIT_CALC는 지우거나 만료로 간주하지 않는다. 바쁨은 짧게 구체적 안내.
- 확정 출고 수정의 Product.Stock 효과는 native CANCEL(old) + FIX(new)의 순효과 old-new와 동일.
  StockHistory는 수동 재고조정이 아닌 native 출고 분류여야 하며 CodeInfo StockType에
  포함되어 재고 계산에 이중 가산될 경우 실행 금지.
- 확정 감소 이력, 출고 변경, 품목별 native 재계산, 편집 기준값 갱신을 한 transaction에 묶는다.
  재계산·검증 실패 시 전체 롤백. 감소도 재고 갱신 자체는 생략하지 않는다.
- native 계산은 @ProdKey를 지정하여 변경 품목만, 같은 품목은 가장 이른 변경차수에서
  한 번 호출한다. 전년도 수정을 허용하지 않고 뒤 연도 스냅샷이 존재하면 이 빠른 경로는
  범위 오류로 차단한다(native SP의 뒤 차수 cascade 범위를 조용히 확장하지 않음).
- 증가 부족 검사는 잠금 상태의 전재고+입고+조정-실제분배로 수행한다.
- 실제분배에는 해당 품목·연도·세부차수의 확정/미확정 `ViewShipment`를 모두 포함한다.
  같은 품목에 여러 상세 증가가 있으면 증가분을 합산한다. 다른 상세의 감소로 상계하지 않는다.
  웹은 기존 3자리 정규화 정책을 유지하여 -0.001도 부족으로 판정한다. native Fix의
  `ROUND(remain,0)<0`보다 엄격하다. 데이터 원천과 재고 순효과를 맞춘 것이며 부족 판정의
  반올림까지 EXE와 완전히 같다고 주장하지 않는다. 재계산 뒤에도 `ROUND(Stock,3)<0`을 사용한다.
- 기존 출고 저장에서는 native Fix를 호출하지 않으므로 증가 부족 검사를 서버가 직접 수행하고,
  native StockCalculation 후 증가 품목의 이후 스냅샷 부족까지 같은 transaction에서 검증한다.
  신규 출고의 기존 확정 경로는 native 최종 검사 유지. 변경된 날짜별 ShipmentHistory도 기록한다.
- 현재 운영 GateLeave는 전체 rollback 뒤 타 연결의 잠금 상태까지 지울 수 있다. 새 경로는
  소유 연결/세대 확인이 있는 gate 기능을 필수로 검사하며, 안전한 변경 및 SQL 동시 실행
  시험 완료 전 운영 활성화하지 않는다. 실행 중 RUN을 만료 시간만으로 강제 회수하지 않는다.
- 클라이언트는 감소 추정만으로 안전을 확정하지 않는다. 실제 서버 저장 결과를 사용한다.
- 같은 금액 수정과 혼합한 저장에서 성공한 수량을 다시 저장하지 않도록 기존 순차 결과 계약 유지.
- 수량 0/false 값은 누락값으로 대체하지 않는다. 품목 삭제/변경, 다른 연도, 오래된 수량·단가·비고는 차단.

## 필수 시험

확정 10→9(기존 재고 음수여도 감소 허용), 10→10 날짜 이동(부족 검사 없음), 10→11(부족 검사),
혼합 품목 감소+증가(상계 금지), 단가만(물량/재고 불변), 10→0 주문 보존,
실제 다른 화면 변경(차단), 자기 저장 후 기준값 갱신, 다른 작업 gate 보존,
native 계산 실패 전부 롤백, 2025/2026 동일차수, 원래 미확정 상태 보존,
변경되지 않은 카테고리 불변, 상세 진행창 오류 보존.

운영 고객 원장 저장 시험과 이미 부분 해제된 34-02 상태 복구는 이번 코드 변경에 포함하지 않는다.
기존 사용자의 ‘수정작업만 실행’ 제한은 유지한다. 이 작업에서는 구현·격리된 SQL 검증까지
수행하며, 새 소유자 보호 프로시저의 운영 적용과 서비스 배포는 검증·적용 조건을 보고한 뒤
별도 운영 반영 지시에 따른다. 마이그레이션은 기존 실행 중 작업을 배제하고 잠금이 완전히
비어 있는 상태에서만 가능하며 실행 중 또는 후속 계산 대기 상태를 임의 초기화하지 않는다.
