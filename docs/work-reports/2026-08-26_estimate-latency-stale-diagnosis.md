# 견적서 수량 수정: 확정 해제 지연·상세 로그 미표시·변경 충돌 진단

## 요청과 실행 경계

- 요청: 수량 수정 시 확정 해제에서 오래 멈추고 세부 로그가 없으며, 다른 화면 변경 안내가 발생하는 원인과 대응방법 확인.
- 이번 작업은 진단만 수행했다. 제품 코드 수정·운영 DB 쓰기·확정/취소/저장·기존 자료 복구·병합·배포는 하지 않았다.
- 앞서 준비된 선택 유지/품종 범위 축소 수정본은 로컬 미배포 상태이며 이번 운영 근거와 구분한다.

전체 경과는 약 **272.5초(4분 32초)**다.

현재 SQL 정의:

- `usp_ShipmentFixCancel`은 `usp_NenovaStockWeekGateEnter(Action=CANCEL)` 후 실행하고 성공 시 Leave를 호출한다.
- `usp_NenovaStockWeekGateLeave`: 성공한 FIX/CANCEL이면 Mode를 `WAIT_CALC`, LockedAt을 현재 시각으로 둔다.
- `usp_NenovaStockWeekGateEnter`: 비어 있거나 90초 경과, 또는 CALC가 WAIT_CALC를 인수하는 경우만 진입한다. 그 외에는 1초씩 기다린다.
- 웹의 DB 요청 제한은 60초다.
- 배포본 `pages/api/shipment/fix.js:1145-1184`는 품종군별 SP를 직렬 실행한다. `skipStockCalc=true`이면 성공 후 중간 계산을 하지 않으며, 대기 해제는 **전체 반복 후** `:1205-1206`에서만 한다.

따라서 첫 취소 성공 → 다음 취소는 대기하다 60초 초과 → 그 다음 취소는 남은 약 30초를 기다린 뒤 성공하는 패턴이 생긴다. 실제 로그 간격과 일치한다. 이 작업에서는 중간 재고 합산 자체가 느린 것이 아니라, 합산을 생략한 경로와 재고 대기 규칙이 충돌한 것이다.

자동 수량 저장은 `pages/estimate.js:2358-2367`에서 `countryFlowers: []`를 보내 선택 품목의 품종군이 아닌 전체 7개를 대상으로 했다. 필요한 후속 세부차수까지 포함될 수 있어 지연·변경 범위가 커진다. EXE는 선택 CountryFlower를 전달하므로 범위를 검증해서 제한할 근거가 있다. 다만 해당 품종군의 여러 업체에 걸친 확정 동작을 개별 업체 한 행과 동일시하면 안 된다.

## 2. 세부 로그는 서버에 있지만 자동 저장창에 연결되지 않음

- `pages/estimate.js:770-825`: AppLog 조회 시작 조건은 수동 확정 진행 또는 구간 확정취소 상태다.
- 자동 수량 저장은 `costApplying/costApplyLog`만 갱신하며 이 조회 조건과 로그 시작시각/대상 차수를 설정하지 않는다.
- 자동 저장 모달 `:4480-4514`는 단계 메시지만 표시한다. 상세 서버 기록 패널 `:5150-5157`은 수동 구간 취소 쪽이다.
- 따라서 서버에 `unfix_sp_start/unfix_exception`이 기록되어도 자동 저장창에는 ‘확정해제 중’만 남는다.
- 브라우저 요청의 기다림 한도는 20분이므로 DB 단계가 실패/대기하는 동안 충분한 설명 없이 오래 기다릴 수 있다.

## 3. 본인이 만든 일부 변경도 ‘다른 화면 변경’으로 안내될 수 있음

- 편집 비교값에는 `ShipmentMaster.isFix`와 `ShipmentDetail.isFix`가 포함된다. 수량·단가가 같더라도 확정 상태가 달라지면 비교값이 변한다 (`lib/erpEditPresence.js:160-212`).
- 자동 취소는 품종군별로 독립 반영된다. 한 품종군이라도 실패하면 `success=false`이며, 기준 비교값 갱신을 하지 않는다 (`pages/api/shipment/fix.js:1233-1234`).
- 일부 취소가 반영된 뒤 기존 비교값으로 조회하면 차이가 감지된다. 화면은 이를 실제 타인의 변경과 구분하지 않고 같은 문구로 안내한다.
- 클라이언트의 복구 대상은 해제 요청이 전부 성공한 차수만 기록한다 (`pages/estimate.js:1601-1613`). 따라서 현재 차수에서 4개 성공/3개 실패한 부분 성공분은 복구 목록에 들어가지 않을 수 있다.
- 수동 확정취소에도 편집 기준값 갱신 경로가 빠져 있는 별도 경로가 있다.

**증거 한계:** 실제 다른 직원/EXE의 같은 시각 변경이 전혀 없었다고 단정하지 않는다. 작업별 이전/이후 비교 이력과 요청 식별자가 없어 이 경고 1건의 원인을 개별 특정할 수는 없다. 하지만 본인 일부 해제만으로 동일 경고가 발생하는 구조는 배포 코드를 사용한 메모리 실행으로 재현했다.

## 5. 대응 설계

1. **범위 제한:** 서버가 변경 품목의 국가·품종군을 직접 검증하고 해당 그룹과 필요한 후속 차수만 처리한다. 빈 필터를 전체로 승격하지 않는다.
2. **대기 상태 관리:** 해제 → 저장 → 재확정 → 최종 재고계산을 하나의 작업번호로 관리한다. 같은 작업 안의 연속 단계와 다른 사용자의 작업을 구분한다. 현재 전역 게이트를 무조건 해제하거나 시간 제한만 늘리지 않는다. 재고 합산 생략 시에도 실행 소유권·연도·차수·복구 상태를 검증해야 한다.
3. **부분 실패 복구:** 성공한 품종군, 실패/결과 불명 품종군을 각각 기록한다. 실제 반영 상태를 재조회한 뒤 성공분의 정확한 복구 또는 미처리분 재개를 제공한다. 이미 저장된 수량을 다시 더하지 않는다.
4. **진행 표시:** 편집 보호 확인 / 대상 확인 / 품종군별 해제 / 수량 저장 / 재확정 / 재고계산 / 결과 대조를 표시하고 경과시간·대상 n/m·마지막 응답시각을 보여준다. 로그 요청 실패 시 기존 기록을 지우지 말고 로그 조회 실패를 별도 표시한다.
5. **충돌 안내 구분:** 본인 작업 진행 중, 본인 부분 성공 후 확인 필요, 다른 사용자의 변경, 작업권 만료를 구분한다. 실제 외부 변경에는 입력값과 전산값 비교를 제공한다. 무조건 비교 기준만 새로 맞춰 충돌을 숨기지 않는다.

즉시 안전한 사용 원칙은 오류 상태에서 같은 저장을 반복하거나 전체 확정취소를 추가 실행하지 않는 것이다. 수정 전에 현재 일부 해제 상태와 실제 수량을 먼저 대조해야 한다.

## 진단 검증 결과

- 운영 로그/원장/현재 SP 정의 읽기 성공. 조회는 제한 시간 12초의 SELECT만 허용했다.
- dnSpy CLI 실제 EXE 읽기 성공.
- 배포 코드의 편집 비교 함수를 가짜 자료로 실행: 수량·단가 변경 없이 본인 확정 해제만으로 stale 발생 확인.
- 실제 게이트 규칙의 메모리 시간 재현: 7개 처리에서 4개 성공/3개 시간 초과, 약 270초. 실제 272.5초와 흐름 일치. 실제 SP를 실행한 성능 시험은 아니다.
- 활성 DB 요청/차단 세션 조회는 사용할 수 없어, 물리 잠금 대기 전체를 관측했다고 주장하지 않는다.
- 운영 저장/확정/해제·고객 데이터 변경·배포 없음. 이 문서는 원인 진단이며 수정 완료 보고가 아니다.

## 후속 질문: 이미 확정됐으니 수량 계산을 모두 생략해도 되는가

사용자는 중간 반복 계산을 없애 처리 속도를 높일 수 있는지 질문했다. 현재 운영 SP 정의와 실제 EXE CLI를 추가 확인했다.

- 실제 EXE `FormShipmentDistribution.btnFixCancel_Click`은 선택 CountryFlower로 확정 취소 후 `uspStockCalculation(year, week, 0)`까지 수행한다. 웹의 중간 합산 생략은 이 EXE 순서를 최적화한 별도 경로이므로 게이트 연결도 함께 설계해야 한다.
- 현재 `usp_ShipmentFixCancel`은 기존 출고량을 Product.Stock에 돌려주고 StockHistory를 기록한다. `usp_ShipmentFix`는 새 출고량을 다시 차감하고 이력을 기록한다. 따라서 단순 확인 표시 변경이 아니다.
- 차수별 확정 잔량 ProductStock은 `usp_StockCalculation`이 전차수 잔량+입고−확정출고+조정으로 갱신한다. 선택 차수 이후의 저장된 재고에도 영향이 전파된다. 실제 출고 총량이 바뀌면 이 갱신을 모두 생략할 수 없다.
- 단가만 변경하거나 같은 품목의 출고 총량을 유지한 날짜 재배치라면 물리 재고 재계산 생략을 별도로 검토할 수 있다. 수량·날짜·견적금액 검증까지 생략한다는 뜻은 아니다.
- 안전한 수량 수정 방향: 대상 품종군만 해제 → 중간 반복 합산 생략 → 수량/출고일/금액 저장 → 재확정 → 변경 품목과 영향받는 차수의 최종 재고 정리. 이미 확정됐다는 이유만으로 변경 전 잔량을 유지하지 않는다.
- 이번 실패는 이미 `skipStockCalc=true`였다. 계산을 더 끄는 것이 해결책이 아니며, 동일 작업 내 게이트 관리와 부분 성공 복구부터 바로잡아야 한다.

후속 확인도 읽기만 수행했으며 코드와 운영 자료는 변경하지 않았다.
