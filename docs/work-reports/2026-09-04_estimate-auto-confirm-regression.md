# 견적서 수량·단가 저장 후 자동확정 오인 및 본인 변경 충돌 보완

## 확인한 현상과 원인

- 기존 출고행의 수량과 단가는 확정 상태를 유지한 채 직접 저장하는 경로인데도, 통합 저장의 마지막 오류 문구가 모든 실패를 `자동 확정차수 편집 오류`로 표시했다.
- 한 번의 통합 저장에서 앞 단계의 수량 변경이 반영된 뒤 뒤 단계가 실패하면 전체 성공값은 `false`가 된다. 이때 저장 종료 확인을 건너뛰어, 서버가 앞 단계의 정상 반영으로 갱신한 기준값과 브라우저가 가진 이전 기준값이 어긋났다.
- 그 결과 다음 주기 확인에서 이 브라우저가 방금 저장한 값을 `nenova.exe 또는 다른 화면의 변경`으로 잘못 판단할 수 있었다.

## dnSpy 및 현재 계약 대조

- `FormEstimateView.btnSave_Click`은 수정된 `ShipmentDate.SdateKey`별로 `ClassShipmentDate.Update()`를 호출한다.
- 원본 EXE의 견적수량 저장은 `ShipmentDate.EstQuantity/Amount/Vat/Descr` 직접 저장이며 차수 전체 확정취소를 호출하지 않는다.
- 웹의 물리 출고수량 확장 저장은 현재 서버 잠금 아래 확정 상태를 유지하며 `ShipmentDate`와 `ShipmentDetail`을 같은 거래에서 갱신한다. 기존 행 수량·단가 저장은 확정취소·재확정 사이클에 넣지 않는다.
- 실제 확정취소·재확정은 `추가 품목등록`으로 새 분배를 만드는 경우에만 해당 품목 범위에서 실행한다.

## 변경 계약

1. 견적서의 모든 저장·삭제 시도는 현재 작업 업체와 차수가 그대로일 때 저장 종료 heartbeat를 수행한다.
2. heartbeat는 현재 원장을 새 기준으로 강제 수용하지 않는다. 서버 거래가 갱신한 기준값과 실제 원장만 비교한다.
3. 앞 단계만 성공한 부분 반영도 본인 변경으로 정상 정산한다. 반대로 저장 중 EXE나 다른 창이 변경했으면 heartbeat가 계속 `stale`로 차단한다.
4. 기존 수량·단가만 수정한 경우 오류·완료 문구에 `자동 확정차수`를 사용하지 않는다.
5. 추가 품목이 포함된 경우에만 `추가 품목 확정 처리`로 표시한다.

## 완료 기준

- 기존 수량·단가 통합 저장에 확정취소 API가 호출되지 않는다.
- 일부 단계가 실패해도 다음 주기 확인이 앞 단계의 본인 반영을 외부 변경으로 오인하지 않는다.
- 실제 외부 변경은 자동 수용되지 않고 기존처럼 저장을 차단한다.
- `OrderYear + OrderWeek + CustKey + 실제 행 키` 범위와 기존 네 등록 버튼을 보존한다.
- ERP 계약, dnSpy 근거, 변경 범위, 쓰기 보호, 빌드 검사를 모두 통과한다.
