# 붙여넣기 주문등록·견적서관리 동시수정 보호

## 목적

같은 연도·대차수·업체를 웹의 여러 탭이나 여러 사용자가 동시에 수정하거나, 웹 조회 뒤 `nenova.exe`에서 같은 원장을 저장했을 때 오래된 화면이 새 값을 덮어쓰지 않게 한다.

보호 업무키는 `OrderYear + 부모 OrderWeek(WW) + CustKey`다. 따라서 `32-01`과 `32-02`는 같은 업체 작업으로 묶고, 2025년과 2026년의 같은 차수는 분리한다.

## 확인한 원인

- 기존 API 일부에는 행별 이전값 확인이 있었지만 화면 전체의 주문·분배·출고일·농장·견적 변경을 한 기준으로 비교하지 않았다.
- 웹 사용자가 같은 업체를 열었는지 알 수 있는 공통 작업 상태가 없었다.
- `nenova.exe`는 웹 작업 상태를 알지 못하고 웹도 EXE의 입력 중 상태를 직접 받을 수 없다.
- 조회 후 EXE가 저장한 경우, 각 API의 제한된 이전값 검사에 걸리지 않는 다른 테이블 변경은 오래된 웹 화면이 덮어쓸 수 있었다.

## 적용 구조

### 1. 웹 작업 표시

- 별도 표 `WebErpEditLease`에 작업자, 화면, 탭 식별값, 만료시간을 저장한다.
- 작업권은 90초이며 작업 중 20초마다 연장한다.
- 다른 사용자 또는 다른 브라우저 탭이 같은 업체·대차수를 작업 중이면 이름을 표시하고 저장을 막는다.
- 최초 상태 확인이 끝나기 전과 업체를 바꾸는 순간에도 이전 업체의 작업권을 재사용하지 않고 저장을 막는다.
- 만료된 작업권은 다음 사용자가 정상적으로 가져갈 수 있다.
- 견적서 목록 재조회에서 세부차수 표시 순서가 달라져도 대차수 작업키는 바뀌지 않는다.
- 같은 로그인 계정의 다른 창이 보유한 작업권은 이름만 "다른 사용자"로 표시하지 않고,
  사용자가 `이 창에서 계속 작업`을 선택하면 기존 창의 토큰을 무효화한 뒤 안전하게 넘겨받는다.
- 작업권을 다시 얻을 때마다 토큰을 교체하므로 이전 화면의 늦은 종료 요청이 새 작업권을
  만료시키지 못한다.

### 2. 전산 변경 감지

- 주문, 분배, 출고일, 농장, 견적 행을 정렬한 뒤 SHA-256 기준값을 만든다.
- 화면은 8초마다 읽기 전용으로 다시 확인한다.
- 실제 저장 직전에는 같은 SQL 트랜잭션에서 원장 행을 잠그고 다시 비교한다.
- 조회 후 `nenova.exe` 또는 다른 정상 경로가 저장했다면 `ERP_EDIT_STALE`로 중단하고 입력값과 경고를 화면에 유지한다.
- 정상 웹 저장이 성공하면 같은 트랜잭션에서 서버 기준값만 새 결과로 이동한다. 확정취소→수정→재확정의 자기 저장은 허용하면서 중간 EXE 저장은 다음 단계에서 차단한다.
- 견적 품목 편집은 수량·단가뿐 아니라 품목·단위·적요의 조회시점 값도 다시 대조한다.

### 3. 적용 화면과 저장 경로

- 붙여넣기 주문등록: 주문 추가·취소, 분배 조정, 일괄 주문·분배, 실행 취소
- 견적서관리: 수량, 출고일+수량, 단가, 품목정보, 불량/검역, 불량차감, 판매요청, 추가 품목등록
- 공용 출고 분배와 확정/확정취소 API

견적서의 기존 네 등록 버튼인 `불량/검역등록`, `불량차감등록`, `판매요청`, `추가 품목등록`은 모두 유지한다.
추가 품목등록은 견적서에서 현재 조회한 업체로 고정하여 다른 업체의 작업권을 잘못 사용할 수 없게 한다.

## 부작용 표

| 작업 | ERP 원장 | 보호용 표 | 실패 시 |
|---|---|---|---|
| 상태 조회 | 읽기만 | 읽기만 | 저장 차단 안내 |
| 작업 시작·연장·종료 | 변경 없음 | 작업자·만료시간 갱신 | ERP 영향 없음 |
| 외부 변경 감지 | 읽기만 | 변경 없음 | 기존 입력 유지, 새로고침 요구 |
| 기존 주문·분배·견적 저장 | 기존 API 계약 그대로 | 성공 후 기준값·회차 갱신 | 트랜잭션 롤백 |
| 확정취소·재확정 | 기존 EXE 호환 절차 그대로 | 전체 성공 뒤 기준값 갱신 | 부분 실패 상태를 자동 수용하지 않음 |

보호 기능 자체는 `OrderDetail`, `ShipmentDetail`, `ShipmentDate`, `ShipmentFarm`, `Estimate`, `ProductStock`, `WebProfitReport`를 새로 수정하지 않는다.

## 알려진 기술 한계

`nenova.exe`를 수정하지 않는 한 EXE 사용자가 아직 입력만 하고 저장하지 않은 상태는 웹이 알 수 없다. 대신 EXE가 저장한 직후에는 최대 8초 안에 화면 경고가 나타나며, 8초 전에 저장 버튼을 눌러도 서버가 저장 직전 다시 비교하므로 덮어쓰지 않는다.

EXE의 ‘입력 중’까지 표시하려면 EXE 또는 PC 보조 프로그램이 같은 작업 상태 API에 접속하도록 별도 배포해야 한다. 현재 구현은 EXE 수정 없이 달성 가능한 안전 범위인 ‘저장된 변경의 덮어쓰기 방지’를 보장한다.

## 검증 항목

- 같은 사용자의 같은 탭 재진입
- 다른 사용자·다른 탭의 동시 진입 차단
- 90초 만료 후 작업권 회수
- 20초 연장과 장시간 저장 중 유지
- EXE 저장을 모사한 주문 원장 변경 후 저장 차단
- 웹의 연속 저장 뒤 자기 변경 오탐 방지
- `32-01`·`32-02` 공통 보호 및 2025·2026 분리
- 붙여넣기 일괄 작업의 업체별 작업권 선취득과 실패 시 전부 반납
- 견적서 네 등록 버튼과 모든 수정 경로의 작업 확인값 전달
- 상태 조회 경로의 DDL·장기 SQL 잠금 금지
