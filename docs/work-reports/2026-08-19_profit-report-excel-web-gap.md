# 주차별 매출이익 — 사용자 업무규칙 vs 현재 웹 vs 엑셀가 어긋나는 지점

## 결론

계산식 이름(매출·매입·통관·포워딩)은 엑셀과 웹이 같습니다.  
숫자가 달라지는 이유는 **같은 이름을 쓰면서 원천·배분·차량추천이 다른 부분**과, **엑셀은 그때 장부·엑셀은 지금 장부**가 섞이기 때문입니다.

아래는 방금 정리하신 규칙을 현재 코드와 1:1로 대조한 결과입니다.

---

## 맞는 부분 (웹이 이미 그렇게 되어 있음)

| 말씀하신 규칙 | 웹 현재 |
|---|---|
| 기초재고 E = 전차수 F 재계산. `(전차수 G + 전차수 H) ÷ 전차수 매입수량 × 전차수말 재고` | 콜롬비아 5품종·베트남만 이 공식. `G = Q×R + S×R` |
| 구매현황 = 입고관리 세부차수 구매금액 | `WarehouseDetail.TPrice`, 운송료·GW/CW 행 제외, 대차수 `27-%` 합산 |
| 판매현황 = 차감 없는 순수 매출 | 확정 출고 `ShipmentDetail.Amount` (`sm.isFix=1` 그리고 `sd.isFix=1`) |
| 불량차감 = 견적의 불량차감 전체 | `Estimate` + `CodeInfo.Descr2='불량차감'` → L |
| 그외 매출 = 불량·순수매출 외 견적 | 같은 Estimate에서 불량차감이 아닌 금액 → O |
| GW/CW 행은 매입·매출이 아니라 백상 kg | 금액 합계에서 제외, 백상창고료 `(GW1+GW2)×단가` |
| 카장알루 항공료는 APOLLO 합계를 1차·2차로 나눠 표시 | `WebColombiaWeekly` 반차수 GW/CW/AirRateUSD |
| 수국은 카장알루와 평소 따로, 같이 들어오면 같이 | 평소는 인보이스 `콜수국` vs `콜카장`으로 분리. **같이 들어온 경우를 자동으로 한 풀에 넣는 코드는 없음** |
| 호주는 사서 재고로 두고 파는 특이 케이스 | 평균원가 공식 대상 아님. `재고수량 × AUD 단가 × 과세환율` |

## 실제로 어긋나는 지점 (우선순위)

### 1. 차량 추천 — 가장 큰 공식 차이

말씀하신 예: **GW 3,342kg = 3.3t → 2.5t를 넘으니 5T 275,000원**.

지금 웹 추천(`lib/colombiaTruck.js`)은 이렇게 나눕니다.

- 5,000kg 묶음을 먼저 빼고
- 남은 3,342kg는 2.5t 1대 + 1t 1대
- 금액 **187,000 + 99,000 = 286,000원**

즉 같은 3,342kg에서 **웹 추천 286,000 vs 말씀하신 5T 275,000**, 차이 11,000원입니다.  
이 금액이 그외통관비 H에 들어가고, 콜롬비아·베트남 평균원가 E/F에도 다시 곱해집니다.

이 추천은 2026-08-12에 “비용 최저 1대(3.3t→5T)”에서 “용량 분해(3t→2.5t+1t)”로 바뀐 것입니다.  
이유는 22~27차 엑셀 실제 차량이 한 규칙으로 안 맞았기 때문입니다. 예: 26-01 GW 6,706kg 엑셀은 5T 1대만, 웹 추천은 5T+2.5T. 27차 수국 4,508kg 엑셀은 2.5T 1대.

**저장된 실제 대수·청구액이 있으면 추천은 덮지 않습니다.** 엑셀과 맞추려면 그외통관비 화면의 실제 칸에 5T 1대를 넣는 것이 현재 설계입니다.

### 2. 카장알루 분배 — H는 항상 무게, S만 CW/GW 전환

말씀: APOLLO CW=GW이면 무게로 그외통관비, CW>GW이면 CBM으로 분배.

엑셀 원본 수식과 지금 웹은 이렇게 나뉩니다.

- **그외통관비 H**: 항상 `박스수 × 박스당 무게` 비율 (CW/GW를 안 봄)
- **포워딩 S(항공료 USD)**: CW≈GW이면 무게, 아니면 `박스수 × 박스당 CBM`

그래서 총 항공료가 같아도, CW>GW인 주에 **품종별 H**는 웹이 무게로만 나눕니다.  
엑셀 콜롬비아 시트의 항공료 IF는 S 쪽입니다.

### 3. 수국을 “같이 들어오면 같이 포함”

카장알루 배분 대상은 장미·카네이션·알스트로·루스커스 네 개뿐입니다.  
수국이 같은 APOLLO에 실려 있어도 웹은 `콜수국` 국가행으로 빼고, 네 품목 비율에 수국 박스·무게를 넣지 않습니다.

### 4. 환율 R — 엑셀은 선율 직접입력, 웹은 자동 원천

말씀: 전차수 신고 환율(선율) 직접입력.

웹 자동 순서:

1. 당주 입고 `FreightCost.ExchangeRate`
2. 그 차수에 저장한 과세환율
3. 2026 22~27차 원본 엑셀 R
4. 28차 이후 관세청 과세환율

전차수 R과 통화마스터 환율은 **참고 제안만**이고 자동으로 안 들어갑니다.  
엑셀에 적어 둔 선율과 웹 자동 R이 다르면 G·P·T와 평균원가 E/F가 전부 갈립니다.

### 5. 포워딩 S 원천

말씀: 입고관리에 등록된 운송비 내역 합계.

웹 우선순위:

1. 포워딩/콜롬비아 화면의 구조화 값(APOLLO AirRateUSD 포함)
2. 입고 `운송료/항공료/FREIGHT/SERVICE FEE` 행 분류 합계
3. 없을 때만 BILL `CW × 운임률 + 서류비` 추정치

엑셀은 APOLLO 청구 합계를 1·2차에 나눠 적은 값입니다.  
입고 운송료 행이 미분류이거나 BILL 추정치로 떨어지면 S가 달라집니다. 29차부터는 미분류가 검증을 막습니다.

### 6. 호주 재고

평균원가 `(G+H)÷매입수량×재고`를 쓰지 않습니다.  
엑셀 재고잔량은 `재고수량 × AUD 품목단가 × 당주 과세환율`입니다.  
웹에 AUD 단가 근거가 없으면 호주 E/F가 비고, 엑셀은 숫자가 있습니다.

### 7. 같은 공식이라도 장부가 다름

2026-08-14 운영 대조에서 22~28차 매출·매입 차이의 큰 덩어리는 **엑셀을 만든 뒤 전산 출고·입고가 수정된 것**이었습니다.  
웹은 지금 `ViewShipment`/`ViewWarehouse`를 다시 읽습니다. 엑셀 숫자는 그때 복사본입니다.

추가로 웹은 26차 F를 27차 E로 다시 계산하고, 엑셀 27차 베트남 E 예외값(+3,658,863원)은 넣지 않습니다.

## 숫자로 보면 어디가 먼저 틀어지나

```
R(환율) 또는 H(통관·트럭) 또는 S(항공료)
  → G = Q×R + S×R
  → 콜롬비아·베트남 E/F = (G+H)÷매입수량×재고
  → I = E+G+H−F
  → J = C−I, K = J/C
```

N/L/O/Q가 엑셀과 같다면, 이익률이 크게 벌어지는 원인은 거의 항상 **R, 트럭/선율 H, APOLLO S, 호주·기타국 재고단가** 네 가지입니다.

## 권장 확인 순서 (한 차수)

1. 그외통관비 화면: 카장알루 합산 GW가 APOLLO와 같은지, 실제 트럭이 5T인지 2.5T+1T인지
2. 같은 화면: 선율·관세 직접입력 금액이 엑셀과 같은지
3. 포워딩 화면: 1차·2차 AirRateUSD 합계가 APOLLO와 같은지, CW vs GW
4. 본표 R이 엑셀 선율과 같은지
5. 그 다음에 N/Q/E/F 본표 대조
