# 영업방 전체 원문 대조

## 범위와 근거

사용자 목적은 어제까지 처리한 요청의 누락 확인이다. 최근 200건 slice로 337건 중
137건이 대조 대상에서 빠졌던 UI를 수정한다. 원문 전체를 기존 차수 그룹 함수에
전달하며 같은 차수 요청을 분할해 같은 로그를 중복 소비하지 않는다.

FormOrderAdd.cs 804–827의 OrderHistory 상세키 조인과 960–970의 주문수량
BeforeValue/AfterValue 기록을 재확인했다. 주문 이력을 분배 완료로 승격하지 않는다.
이전 운영 조회에서 2026/37-02 CustKey478 ProdKey53의 ShipmentHistory100582는
48→30단이며 두 원문의 2단+1박스(16단)와 합계 일치했다. 이번 재조회는 sales-feed
502로 실패했으므로 이전 근거를 신규 성공 조회로 주장하지 않는다.

## 부작용 표

| 동작 | Order/Shipment Master·Detail | History | 재고/ShipmentDate/Farm | Estimate/WebProfitReport |
|---|---|---|---|---|
| 전체 원문 전산 대조 | SELECT, 보존 | SELECT, 보존 | 기존 읽기만, 보존 | 보존 |
| 사유·박스 표시 | 보존 | 보존 | 보존 | 보존 |

SQL·단위환산·완료 판정·ERP 쓰기 경로는 변경하지 않는다. API 메시지 수 검증만
200→1000으로 확대한다. 문자 한도 200000과 SQL 이력 한도는 유지한다.
초과는 전체 오류로 반환하고 일부 결과를 완료로 표시하지 않는다.
브라우저 표시 건수는 실제 반환 identity 수이며 미조회 원문 및 조회 실패를 구분한다.
불러온 원문 수는 기간 전체 수와 같다고 단정하지 않고 feed hasMore/incomplete를 표시한다.

## 검증·위험

- 1000건 수락, 1001건 거부, 같은 이력 경쟁·교차연도 배제 회귀 유지.
- 전체 계약, dnSpy evidence, manifest/write guard, build 후 배포한다.
- 1920×1080 운영에서 API 요청 총수=불러온 원문 수, 200건 이후 응답 identity,
  완료 박스와 미확인 사유를 확인한다. 유료 AI 및 업무 저장은 실행하지 않는다.
- 더 넓은 요청 집합 때문에 기존 단독 일치가 경쟁 근거로 바뀔 수 있다. 이것은
  완료 수를 늘리기 위해 생략할 수 없는 보수적 검증이다.
- 1000건/문자 한도 초과 또는 30초 timeout은 명시적 조회 실패로 남는다.
