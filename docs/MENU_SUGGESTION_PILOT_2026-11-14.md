S 규칙은 화면 기록, D 규칙은 전산 기록에서 센다. **이번 시험에서 카드로 이어진 것은 모두 D 규칙이 뒷받침한 후보였다.** 화면 기록만으로는 "어디가 불편한가"까지, 전산 기록이 "몇 줄이 걸려 있나"를 준다.

자료의 한계(카드마다 다시 적는다):
- 직원 PC 화면 기록은 최근까지 올려 보낼 것의 약 35%만 도착했다. 화면 캡처 대비 해독은 23~25%다. "반복이 없다"는 결론은 자료가 빠져서일 수 있다.
- 컷은 30일치뿐이라 월 단위 일(결제·월말 증빙)은 1~3번만 보인다.
- 주말·전화·휴대폰 메신저·회의는 기록에 없다.

## 4. 읽기 화면과 바꾸는 화면 — 제외가 아니라 증명 수준의 차이

금액·재고·차수를 바꾸는 절차도 기록과 전산에 근거가 남는 관찰된 절차이므로 제안 대상이다. 다만 카드에 아래 칸을 더 채워야 올린다.

| 칸 | 읽기 화면 | 바꾸는 화면 |
|---|---|---|
| ① 관찰된 절차 | 어느 화면의 어느 칸을 보는가, 근거 건수 | 어떤 순서로 무엇을 보고 어떤 값을 넣는가, 근거 건수 |
| ② 과거 실제 건으로 맞춰 보기 | 조회 줄 수가 전산 화면과 같은지 | 과거에 사람이 넣은 값을 정답으로 놓고 몇 건 중 몇 건이 맞는지. 100%가 아니면 자동 저장하지 않는다 |
| ③ 전산 프로그램·오늘 DB 대조 | 오늘 DB 값으로 셌는지 | 같음 + 전산 프로그램 화면과 대조. 못 했으면 "미검증" |
| ④ 차수 간에 항상 맞아야 하는 것 | 해당 없음(바꾸지 않음) | 무엇으로 확인하는지(전후 줄 수·수량 합, 재고는 `STOCK_INTEGRITY_DESIGN.md` 절차) |
| ⑤ 시작 단계 | 목록 보기 | "제안만 하고 사람이 저장"으로 시작. 자동 저장은 ②가 100%이고 사장님이 따로 승인한 뒤 |

화면 틀 4종과 맞는 증명 수준:

| 틀 | 쓰임 | 이번 카드 |
|---|---|---|
| 목록 | 빈칸·대기 줄을 한곳에 | 카드 3 |
| 대조표 | 두 자료를 줄 맞춰 비교 | 카드 2 |
| 체크리스트 | 줄마다 "확인함" 표시 | 카드 3의 2단계 |
| 입력 폼(제안값 채움) | 후보를 채워 주고 사람이 저장 | 카드 1 |

## 5. 지금 사람 손이 들어간 부분

1. 컷 분해 실행(한 번 수동으로 돌린 결과를 받았다).
2. 낱말 목록 고르기와, 낱말에 걸린 발췌를 읽어 진짜 막힘인지 가르기.
3. 신호 → "전산의 어느 표를 세면 되나" 연결(이번에는 저장소를 읽어 찾았다).
4. 이미 있는 화면인지 확인(발주·입고 비교, 마이너스 진단, 수입부 수정 요청은 이미 있었다 — 새로 만들 것이 아니라 붙일 것).
5. 카드 문장 쓰기, 3장 고르기.
6. 사장님께 올리기(파일), 승인 받기(말).

자동화 순서 제안: ②의 D 규칙(전산 조회) → ①의 컷 분해 주 1회 → ④의 카드 틀 → ⑤의 승인 버튼. 3·4번은 당분간 사람이 한다.

## 6. 승인 자리 — 확인한 것

- 카드를 올리면 승인·반려 버튼이 뜨는 자리는 지금 없다.
- `/pm`의 "승인 대기 N건"은 건수 표시만 한다. `/pm` 직원 요청 게시판은 로그인 직원이 글로 올리는 자리다.
- `/my-work`의 기능 후보는 `proposals` 자료를 읽어 보여 주는 읽기 화면이다(관리자 전용). 카드 목록을 보여 주기에는 여기가 가장 가깝지만, 올리려면 자료 전체를 바꿔 올려야 해서 다른 후보를 덮을 수 있다. 이번에는 쓰지 않았다.
- `/mgmt/approvals`는 승인·반려 버튼과 기록이 있으나 경영관리 결재용이고, 등록된 요청이 0건이다.
- 그래서 이번 카드는 사장님 PC 바탕화면 `메뉴제안카드` 폴더에 파일로 두었다.
