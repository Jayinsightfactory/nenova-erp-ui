# ECOUNT 기능의 네노바웹 이관 설계

작성일: 2026-10-20 KST. 대상: 네노바 대표와 구현 담당자. 코드 기준: `abe88d34`.

목표는 ECOUNT 의존 없이 네노바웹에서 동일 업무와 결과를 처리하는 것이다. 기초정보·거래·재고·회계·결재는 자체 DB와 업무 로직으로 구현할 수 있다. 은행·카드의 새로운 거래 수집, 전자세금계산서 발행·국세청 전송 등은 외부 연결이 필요하다. 외부에서 받은 결과도 내부 DB에 관리한다.

현재는 **실화면 일부 조사와 코드 분석에 기반한 실행 설계**다. 전체 기능 동등성, 과거 데이터 완전성, 운영 API 자격은 아직 검증하지 않았다. 사이트맵에 보인 메뉴와 실제 동작을 검증한 기능을 구분한다. 화면 복제만으로 100% 이관 완료로 판정하지 않는다.

## 범위와 완료 기준

전체 후보 범위는 로그인된 계정의 사이트맵, 다른 역할에만 보이는 메뉴, 사용자 정의 양식·보고서, 외부 연동, 과거 자료·첨부·변경 이력까지 포함한다. 사용 빈도가 낮은 메뉴도 임의로 제외하지 않고 후순위로 둔다. 네노바 업무 100% 대체와 ECOUNT 제품 전체의 모든 선택 기능 재현은 별도 지표로 관리한다.

기능별로 조회·입력·수정·취소·확정·승인·인쇄·Excel·권한·오류·외부 처리 결과를 나눠 검증한다. 적용 기능 수가 확정되기 전에는 완료율을 계산하지 않는다. 완료율은 `검증 통과한 적용 시나리오 / 전체 적용 시나리오`이며, 미확인·접근 불가 기능도 분모에서 삭제하지 않는다.

최종 전환 조건은 모든 적용 시나리오 통과, 필수 데이터 누락 0건, 원인 불명 잔액 차이 0건, 최소 한 번의 월마감 병행 대사, 역할별 사용자 인수 확인, 복원 연습 통과다. 금액 허용오차는 임의로 설정하지 않고 문서별 반올림 규칙으로 설명한다.

| `pages/api/finance/bank.js` | BankTransaction 목록·수동 등록, IsSample 구분 | 거래 저장 기반. 은행 전체 연동 완료 아님 |

기존 6월 계획은 ECOUNT 연동·대조 중심이었다. 이번 설계는 자체 업무 원장으로 전환하는 계획이며, 기존 문서의 push 경로를 이관 자동 작업에 포함하지 않는다.

은행 거래와 세금계산서도 DB화할 수 있다. DB만으로 대체되지 않는 부분은 은행·국세청 등 외부 기관의 사실 확인과 처리다. CSV 업로드는 과거 자료 이관의 대안이며, 자동수집 API와 동등한 무인 운영은 아니다.

팝빌의 계좌조회·세금계산서 발행·홈택스수집 기능은 공식 문서로 확인했다. 실제 네노바의 이용 가능 여부와 요금은 확인되지 않았다. 카드·PG·신고는 후보 목록이며 공급자 선정 완료가 아니다. 은행/세금 서비스 계약이 있어도 모든 ECOUNT 외부 기능이 자동 대체되는 것은 아니다.

## 데이터 구조 제안

기존 MSSQL과 별도 웹 전용 영역을 사용한다. 아래 이름은 제안이며 실제 테이블 생성은 하지 않았다. 저장소 규칙에 따라 마이그레이션 SQL은 준비하고 사용자가 SSMS에서 실행한다. GET 요청 시 CREATE TABLE을 수행하는 기존 방식을 새 이관 설계에 확대하지 않는다.

| 계층 | 제안 테이블 | 핵심 규칙 |
|---|---|---|
| 조사 명세 | FeatureCatalog, ScreenContract, EvidenceRecord | 메뉴 경로·역할·필드·동작·상태·미확인 항목·증거 시점 |
| 이관 배치 | ImportBatch, ImportRow, ImportError, SourceRevision | 원본 식별자·해시·기간·필터·페이지·건수·스키마 버전, 격리와 재실행 |
| 기준정보 연결 | ExternalCodeMap | 회사+원천+엔터티+외부코드→내부 PK. 이름 일치만으로 연결 금지 |
| 거래 연결 | BusinessDocumentLink | ECOUNT 전표·행↔주문·입고·출고·회계 전표 연결. 원본 번호의 연도별 재사용 고려 |
| 회계 | LedgerAccount, FiscalPeriod, Journal, JournalLine | 차변합=대변합, 통화별 금액·환율, 기장일·증빙일, 마감 잠금, 역분개·정정 이력 |
| 수금과 지급 | OpenItem, Settlement, SettlementAllocation | 다대다 배분·부분 결제·잔액·취소. 분개와 원자적으로 처리 |
| 은행과 카드 | ExternalAccountRef, BankFeed, CardFeed, ReconciliationMatch | 서비스의 불투명 참조 ID, 거래 고유키·취소 연결. 계좌번호 대신 토큰 사용 |
| 전자증빙 | ElectronicDocument, DocumentStatusEvent, ExternalRequest | 내부 초안·사업자 발행·국세청 결과·메일 전달 상태 분리 |
| 자동작업 | JobRun, JobCheckpoint, IntegrationOutbox, AuditEvent | 멱등키·재시도·배타 잠금·중단 사유·수동 조치·전후 근거 |

금액은 DECIMAL 및 명시된 반올림 규칙을 사용한다. 원천의 공란·누락·0을 구분하고 파싱 실패를 0으로 바꾸지 않는다. 날짜는 KST 업무일과 원천 시간을 분리한다. 거래 중복키는 원천 고유 ID가 우선이며, 없으면 회사·원천·계좌토큰·일시·입출금·금액·잔액·원천 순번을 후보로 검증한다. 동일 시각·동일 금액 거래를 임의로 합치지 않는다.

수집 원문을 무조건 JSON으로 보관하지 않는다. 현재 지침상 계좌번호·개인정보·자격증명은 산출물·로그·저장소에 출력/저장 금지다. 스키마는 필요한 필드만 허용하고 마스킹·토큰화하며, 인사 등 개인 식별정보의 실제 이관은 별도 보관 정책과 권한 확정 전까지 합성 데이터로 설계한다. 세션 쿠키나 인증서를 수집 증거에 포함하지 않는다.

| 단계 | 자동 작업 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| 1 전체 목록 | 역할별 사이트맵과 기존 코드의 메뉴/API를 연결, 사용자 정의 메뉴 포함 | 미확인 메뉴도 추적 가능한 ID 보유 |
| 2 화면 계약 | 필터·열·검색·정렬·합계·Excel·상세·권한·상태 전이 조사 | 필드와 동작의 근거 존재. ECOUNT 쓰기는 실행하지 않음 |
| 3 수집 검증 | 공식 읽기 API→정상 Excel 내보내기→화면 읽기 순서로 선택 | 실제 필터/기간·전체 페이지·원본 건수·합계 확인 |
| 4 과거 이관 시험 | 대표 월·결산 경계·취소/반품 포함 소량 배치 → 격리 적재 | 건수·금액·기초/기말·미결 항목 대사, 재실행 중복 0 |
| 5 내부 회계 | 분개·기간·마감·채권채무 배분·감사 이력 구현 | 차대 균형, 부분 결제·취소·마감 후 정정·권한 테스트 |
| 6 업무 연결 | 기존 물류·판매·구매 화면을 내부 원장과 연결 | 실제 dnSpy·읽기 전용 DB probe·교차연도 계약 통과 |
| 7 외부 연결 | 은행과 증빙 어댑터, 비동기 작업·결과 재조회 | 계약/인증 준비, 샌드박스 검증, 중복 발행 방지 |
| 8 나머지 기능 | 자산·예산·계약·급여·근태·그룹웨어·확장 기능 | 기능별 명세·계산·역할·출력 동등성 |
| 9 병행 대사 | ECOUNT 읽기 결과와 네노바웹 결과 비교 | 최소 월마감 1회 포함 전 시나리오 통과 |
| 10 업무 전환 | 메뉴별 단일 입력 주체 전환, 최종 증분·잔액 이관 | 미결 처리·복원·담당자 인수 완료 |

첫 구현 묶음은 **읽기 전용 수집 검증 강화 → 기준정보 매핑 → 분개/채권채무 → 은행 수금 대사 → 전자세금계산서** 순서를 권장한다. 외부 계약 준비는 이 순서와 독립적으로 확인할 수 있다. 기간 추정은 전체 메뉴 수와 대표 기능 계약을 확정한 뒤 산정한다.

## 자동 작업의 실행 규칙

각 작업은 `DISCOVERED → SPECIFIED → READY → RUNNING → VERIFYING → DONE`으로 진행한다. 증거 부족은 `NEEDS_EVIDENCE`, 인증 만료는 `NEEDS_LOGIN`, 스키마 변경은 `SCHEMA_DRIFT`, 쓰기 의심은 `READONLY_VIOLATION`, 계약/SSMS 대기는 `WAITING_EXTERNAL`로 중단한다. 중단을 성공이나 0행 데이터로 처리하지 않는다.

회사·화면·기간별로 한 작업만 실행한다. 페이지별 체크포인트와 마지막 성공 커서를 기록하고, 지수형 재시도는 최대 횟수를 둔다. 로그인 만료·새 열·합계 불일치는 자동 재시도 대신 조사 대상으로 보낸다. 재수집은 겹치는 기간을 두고 원천 수정/취소를 검출한다. 완전한 원본 범위를 확인하지 못한 상태에서 사라진 행을 삭제로 판정하지 않는다.

ECOUNT 조회는 HTTP GET만 허용하는 식으로 단순화하지 않는다. 조회 POST가 있을 수 있으므로 관측된 URL·메서드·업무 동작의 허용 목록을 사용한다. 쓰기 요청과 알 수 없는 업무 요청은 차단하며, 정상 조회 가능 여부를 소량으로 검증한 뒤 확대한다. 새 스케줄은 검증된 작업만 대상으로 활성화한다. 읽기 수집과 은행 이체·세금계산서 발행 작업을 같은 실행기에 넣지 않는다.

전자증빙 발행은 Outbox에 고유 문서키를 확정한 뒤 전송한다. 타임아웃은 실패가 아니라 결과 불명 상태로 두고 동일 키의 처리 결과를 조회한다. 웹훅은 인증·중복·역순 도착을 처리하고 정기 결과 조회로 보완한다. 취소·수정은 원문 연결을 유지한다. 국세청 결과와 내부 UI 단계를 독립적으로 기록한다.

## 기존 수집기의 우선 보강 사항

`scrape-core.mjs`와 `run.mjs`에서 확인한 정적 코드 기준이다. 운영 실패가 재현되었다는 뜻은 아니다.

1. `collectOne`에 조회 기간 인자가 없고 기간 설정·확인 절차가 보이지 않는다. 요청 기간과 실제 화면 기간을 함께 기록해야 한다.
2. `screenRowCnt`가 파싱한 행 수에서 계산된다. 독립된 원본 전체 건수가 아니므로 누락 검증의 근거로 재사용하지 않는다.
3. 숫자 변환 실패가 0으로 바뀐다. 누락/형식 오류를 격리해야 한다.
4. 요청 가드는 이름 패턴과 읽기 키워드 예외에 의존한다. 전체 기능으로 확장하기 전에 관측된 조회 동작 허용 목록으로 검증해야 한다.
5. 실패 진단에 URL·스크린샷·팝업 원문이 저장될 수 있다. 세션·계좌·개인정보가 남지 않도록 진단을 메타데이터로 제한해야 한다.
6. 단발 실행은 0행을 모두 파싱 실패로 취급하고 마지막에 종료코드 0을 반환한다. 정상 공집합·부분 실패·전체 성공을 분리해야 한다.
7. 대조용 FLOAT·원문 Payload를 회계 정본으로 승격하지 않는다. 적재 실패나 RED 결과는 운영 원장과 분리한다.

이 문제를 고치기 전에는 기존 데몬의 조사 범위를 넓히지 않는다. 저장된 로그인 상태를 읽거나 다른 프로필로 복제하는 작업도 이번 설계에서는 하지 않았다.

## REA 적용 판단

[REA 공식 브라우저 가이드](https://rea.tools/guides/browser/)는 별도 Chrome 프로필과 로컬 디버깅 연결을 이용하여 선택한 동작의 요청, 응답 구조, 로드된 스크립트를 관측하는 방식을 설명한다. [공식 소개](https://rea.tools/)에는 바이너리·JavaScript·브라우저 분석 범위가 제시되어 있다.

이번 조사에는 이미 연결된 Chrome의 읽기 전용 화면 분석을 적용했다. 메뉴·열·버튼 확인에는 추가 설치가 필요하지 않았다. REA는 설치/실행하지 않았고 REA 기반 분석을 완료했다고 주장하지 않는다.

향후 화면만으로 판단하기 어려운 다운로드 구조·클라이언트 계산이 나오면 REA를 선택 도구로 추가한다. 먼저 버전·로컬 출력·필요 권한을 검토하고 합성 데이터 예제로 검증한다. ECOUNT의 세션·거래 응답을 무차별 캡처하지 않으며, 보안 설정을 완화하거나 쿠키를 복사해 연결하지 않는다. 실제 화면에서 허용된 읽기 동작만 관측하고 요청 본문 재실행이나 비공개 쓰기 API 호출은 하지 않는다.

서버 내부 계산, DB 스키마, 숨겨진 권한 규칙은 브라우저 분석만으로 복원할 수 없다. 화면·출력·문서에서 관측된 업무 계약을 작성하여 독립 구현하고 검증한다. `nenova.exe` 공유 원장의 분석은 프로젝트에서 정한 실제 dnSpy CLI와 DB probe를 계속 사용한다.

## 검증과 전환

필수 회귀에는 정상 거래, 동일 금액 중복 거래, 0·공란·음수·반품, 과세/면세/영세, 부분수금·과입금·상계, 연말 이월, 통화·소수점, 마감 후 정정, 권한 없는 사용자, 외부 응답 지연·중복·취소를 포함한다. 실화면 쓰기 테스트 대신 합성 fixture·공식 시험환경을 사용한다. 관측할 수 없는 ECOUNT 쓰기 규칙은 미검증으로 남긴다.

공유 ERP 변경은 `OrderYear + OrderWeek + CustKey + ProdKey`, 실제 dnSpy 근거, 동일 키 읽기 전용 probe, 부작용 표, 계약 JSON, 교차연도 fixture를 먼저 확보한다. `Estimate`, `ShipmentDetail.Amount/Vat/isFix`, `ShipmentDate`, `ShipmentFarm`, `WebProfitReport` 영향을 기록한다. 새 회계 원장 적재만으로 기존 물류 원장을 변경하지 않는다.

구현 PR마다 `test:erp-contract`, `test:nenova-dnspy-evidence`, 변경 기준 manifest/write guard, `build`를 통과시킨 뒤 CI→squash merge→Cafe24→운영 브라우저 확인을 수행한다. 스키마 변경은 SSMS 선행작업이 있는 PR로 표시하며 자동 병합 예외로 둔다. 이번 산출물은 설계 문서이므로 앱 배포 대상이 아니다.

전환은 기능별 단일 입력 시스템을 정하고 기준시각·마지막 원천 전표·기초잔액을 고정한다. 원천 판매 이력 이관 때문에 이미 존재하는 네노바 출고를 다시 생성하지 않는다. 과거 전표·기초잔액·외부 증빙의 중복 기장을 차단한다. 전환 후 오류 시 새 입력을 멈추고 마지막 검증본으로 조회를 복구하되, 이미 외부 발행/전송된 건은 삭제해 되돌리지 않고 조회·정정 절차를 사용한다. 이 조사/이관 작업은 ECOUNT 원본에 쓰지 않는다.

## 공식 참고 자료

- [팝빌 계좌조회](https://developers.popbill.com/reference/easyfinbank/java/api): 계좌 거래와 잔액 조회, 수집 작업과 결과 확인.
- [팝빌 전자세금계산서](https://developers.popbill.com/reference/taxinvoice/java/api): 발행·전송·상태 조회, 독립 테스트 환경.
- [팝빌 홈택스수집](https://developers.popbill.com/reference/httaxinvoice/java/api): 매입·매출 전자세금계산서 수집과 인증 관리.
- [팝빌 개발자센터](https://developers.popbill.com/): 현금영수증·사업자상태·예금주·메시징 서비스 목록.

- [금융결제원 오픈뱅킹](https://openapi.kftc.or.kr/service/openBanking): 조회와 이체 API가 별도 업무임을 확인하는 참고. 네노바 참여 자격을 확인한 것은 아님.
