# 외부 연동 화면·저장 로직 설계

2026-10-20. **설계 완료, 실행 구현 미완료.** 기계 판독 명세는 [external-integration-design.json](external-integration-design.json)이다. 공급자 중립 설계이므로 특정 사업자의 이용 자격·가격·API 지원을 확정하지 않는다. 기존 후보 목록은 [최초 이관 설계](../ECOUNT_REPLACEMENT_DESIGN_2026-10-20.md)의 조사 이력이며 공급자 선정 결과가 아니다. 이번 작성은 외부 문서의 최신 요금·지원 범위 검증을 수행하지 않았다.

이 문서는 외부 기능을 제외하지 말고 화면과 저장 로직을 설계하라는 사용자 요청을 구체화한다. API 연결·가입·동의·인증서 등록·이체·발급·전송·운영 DDL은 실행하지 않는다. 원본 ECOUNT는 조회·다운로드만 허용한다. 기존 공유 ERP 원장은 변경하지 않는다.

## 현재 구현과 이 설계의 경계

- 현재 `ecount_work`는 안전하게 투영한 조회 스냅샷의 불변 Version, 현재 Head, 변경 Audit를 지원한다. 가져오기·정정·활성 버전 복원이 대상이며, 외부 요청 엔진이 아니다. [현 작업영역 계약](../ECOUNT_WORKSPACE_CONTRACT.md)
- 현재 감사는 import/activate 중심이며 동일 데이터 재수신의 모든 시도나 ECOUNT 직원 전체 작업을 기록하지 않는다. 아래 전체 시도 감사는 **추가할 설계**다.
- 은행·세금 관련 일부 원본 조회 화면, 안전 수량/금액 자료, 미검증 버튼의 비활성 표시는 구현돼 있다. 은행 대사·전자발행·기관 결과 확인·외부 취소 엔진은 구현 완료로 취급하지 않는다.
- 기존 `lib/ecountWorkbench.cjs` 저장 계획은 합성 초안이다. 아래 테이블·상태·제약은 그 초안을 확장한 설계이며 실제 테이블이 있다는 뜻이 아니다.

## 기능별 화면과 저장 단위

|---|---|---|
| 은행 입출금·잔액 | 연결 계좌토큰 선택, 기간, 수집 이력, 거래 revision, 잔액 대사, 미연결 수금/지급 | 거래·잔액을 독립 보존. 금액만으로 전표 연결하지 않음. 실제 계좌 정보 표시/이체 없음 |
| 법인카드 | 카드토큰/기간, 승인·청구·취소 탭, 원승인 연결, 대사 차이 | 승인·매입·청구·취소는 별도 사건. 원승인 없는 취소는 격리 |
| 카드매출·PG | 거래/정산 탭, 수수료·환불·입금 대사, 차지백 상태 | 주문·결제·정산·은행입금 독립 키, 정산 revision 보존 |
| 홈택스 증빙 수집 | 문서종류/기간, 수집 작업, 승인번호 참조, 수정 연결, 대사 | 국세청 문서 식별자+revision. 외부 발행분과 내부 발행분은 연결표로 대조 |
| 전자세금계산서·계산서 | 초안, 검토, 발행요청, 사업자 접수/국세청 결과/전달 상태, 수정 요청 | 불변 문서 버전·수정 원문 참조·Outbox. 현재 금액 스냅샷과 별도 모델 |
| 현금영수증 | 발행초안/검토, 수집, 원승인·취소 이력 | 발행과 수집 키 별도, 원승인 연결. 필수 민감 입력은 정책 확정 전 금지 |
| 계좌·급여이체 | 지급요청, 수취 토큰 검증, 이중승인, 처리불명 검토, 결과 대사 | 지급요청 버전별 단일 Outbox. 조회 권한으로 이체 가능하다고 가정하지 않음 |
| 사업자·예금주 확인 | 검증요청/결과/관측시점/만료 | 대상 토큰·검증 종류·시점. 성공 결과를 영구 유효로 저장하지 않음 |
| 문자·알림톡·팩스·메일 | 내용 버전, 검토/승인, 발송요청, 전달/실패 이력 | 수신자 토큰·채널별 요청키. 접수와 전달 분리 |
| 전자계약 | 문서 버전/해시, 검토, 서명요청, 서명자별 단계, 철회 요청 | 문서 해시 및 사건 순서. 체결본 수정은 덮어쓰지 않음 |
| 세무·보험 신고/통관 | 기관별 별도 양식, 검토, 접수/수리/반려, 정정·취하 | 기관·신고종류·기간·제출 버전. 단일 통합 API가 있다고 가정하지 않음 |
| 환율 | 공급원·통화쌍·종류·고시시각·정정 이력 | 고시값 원문 정밀도/단위 보존. 전표 적용율과 별도 |
| 쇼핑몰·배송 | 채널 주문/결제/반품, 배송/인수, 불일치 검토 | 주문행·결제·출고·배송 독립 상태. 기존 원장 연결은 별도 가드 적용 |

필수 식별자 원문에 개인정보가 들어가는지 먼저 분류한다. 사업자·계좌·카드·수신자·서명자·배송 대상은 불투명 참조를 우선한다. 토큰을 되돌리는 원문 저장소는 현재 범위에 없다. 공급자가 원문을 요구하면 별도 동의·보관·접근 정책이 확정될 때까지 `BLOCKED_POLICY`이며, 가짜 정보로 실행하지 않는다.

## 원천키·중복·정정 계약

모든 키는 tenant/provider/connection 범위를 포함한다. 아래는 제안키이며 제공사 실제 필드·고유성 확인 후 확정한다.

| 기능 | 원천 식별키 제안 | revision |
|---|---|---|
| 은행 입출금·잔액 | institution+accountToken+sourceTransactionId | sourceRevision 또는 normalizedPayloadHash |
| 법인카드 사용내역 | issuer+cardToken+approvalId+approvalDate+currency | 승인/취소 이벤트ID 또는 sourceRevision |
| 카드매출·PG 정산 | provider+merchantToken+transactionId; settlementId는 별도키 | transactionRevision 및 settlementRevision 별도 |
| 홈택스 매입·매출 전자증빙 수집 | tenant+authorityDocumentId+documentKind | authorityRevision/statusEventId 또는 normalizedPayloadHash |
| 전자세금계산서·계산서 발행 | tenant+internalDocumentId+documentVersion+operation | immutable internal version 및 provider document revision |
| 현금영수증 발행·수집 | tenant+internalReceiptId+version+operation; 수집은 authorityApprovalId | provider event revision 또는 payload hash |
| 계좌·급여 이체 | tenant+paymentRequestId+version+operation | requestVersion 및 provider executionEventId |
| 사업자상태·예금주 검증 | tenant+checkRequestId+subjectToken+checkKind | observedAt+sourceResultVersion |
| 문자·알림톡·팩스·메일 | tenant+messageId+version+channel+recipientToken | providerMessageId+eventId |
| 전자계약 서명 | tenant+contractId+documentVersion+operation | documentHash+providerEventId |
| 세무·보험 신고/통관 | tenant+agency+filingKind+period+submissionId+version | receiptId+correctionSequence |
| 환율 수집 | provider+currencyPair+rateType+effectiveAt | publicationRevision 또는 payload hash |
| 쇼핑몰·배송 연동 | provider+shopToken+orderId+lineId; shipmentId 별도 | sourceRevision/eventId |

동일 식별키+동일 revision+동일 해시는 재수신으로 처리하되 **시도 감사는 남긴다**. 동일 키/revision에 다른 해시가 오면 충돌로 격리한다. 새 revision은 기존 원문을 덮어쓰지 않고 append한다. 명시된 취소/정정 사건 없이 이전 수집에 있던 행이 사라졌다는 이유로 삭제하지 않는다. 원천 ID가 없을 때 날짜·금액만으로 합치는 대체키는 금지하며 검증된 충돌 정책을 먼저 계약한다.

## 상태 전이와 응답 불명

저장초안 → 검증 → (외부 쓰기이면 승인대기) → 대기열 → 전송중 → 사업자접수 → 최종결과의 순서다. `accepted`는 업무 성공이 아니다. 세금계산서는 국세청 상태, 메시지는 전달 상태, 이체는 결제 결과를 별도 보존한다. 서비스별 업무 상태는 JSON의 `services[].stateModel`에 있다.

전송 후 타임아웃은 `unknown`으로 기록한다. 동일 요청키로 제공사 결과를 조회하며, 권위 있는 결과 조회 수단이 없으면 격리·수동 검토한다. 실패로 간주해 새 키로 자동 재전송하지 않는다. 제공사가 미접수를 확정한 재시도 가능 오류만 재시도한다. 취소·수정은 원문 참조를 가진 새로운 요청이며, 각 기관의 허용 단계·사유·기한을 확정하기 전 실행하지 않는다.

웹훅은 서명·재생 방지 확인 후 안전 사건을 내구성 있게 기록하고 응답한다. 사건ID 중복과 역순을 처리하며 이전 revision이 현재 상태를 낮추지 못한다. 원문 payload에는 민감정보가 있을 수 있으므로 현재 정책에서는 그대로 저장하지 않는다. 웹훅 누락은 정기 결과 재조회로 보완한다. 실제 서명 알고리즘·허용 시차·응답 제한시간은 공급자 확인 항목이다.

페이지 체크포인트는 검증된 임시 적재 이후에만 전진한다. 전체 범위·건수·금액을 대사하고 공개 포인터를 원자적으로 변경한다. 인증 만료/스키마 변화/개인정보 위반/업무 거부/쓰기 결과 불명은 일반 재시도 대상이 아니다. 로그인 장애나 지연 응답을 조회 0건으로 처리하지 않는다.

## 인증·권한과 저장 트랜잭션

`IntegrationConnection`에는 secretRef, credentialVersion, scopeSet, consentRef, 만료시각만 보관한다. 키·인증서·쿠키 원문은 코드/SQL/로그에 넣지 않는다. 실제 secret manager 및 인증서 보관 방법, 역할별 접근, 갱신 주체는 구현 전 결정한다. 갱신은 작업 정지 → 새 자격의 읽기 검증 → 참조 전환 → 구 자격 폐기 순서이며 진행 중 결과불명 요청의 키는 유지한다.

제안 저장 구조는 JSON `proposedStorage`의 8개 테이블이다. DDL은 미작성·미적용이다. 공통 저장 절차는 다음과 같다.

1. 역할·테넌트·필수값·민감필드 정책·정확소수·업무키를 검증한다.
2. 초안 revision 충돌을 검사하고 불변 문서 버전 및 감사 이벤트를 한 트랜잭션으로 저장한다.
3. 외부 쓰기는 별도 업무승인 이후 고유 requestKey에 UNIQUE를 걸어 Outbox를 예약한다.
4. 작업자가 lease를 획득하고 실제 호출을 수행한다. DB 트랜잭션을 잡은 채 장시간 외부 응답을 기다리지 않는다.
5. 안전 응답 사건·시도 감사·요청 상태를 원자 반영한다. 타임아웃/프로세스 종료는 결과불명 경로로 복구한다.
6. 외부 최종결과와 내부 금액·문서 연결을 대사한 후 업무 완료 상태를 공개한다.

실제 이체·발행·신고에는 역할/한도/승인 정책을 별도 확정한다. 조회서비스 사용 승인만으로 쓰기 권한을 부여하지 않는다. 공유 주문·출고·회계 원장은 이 설계의 저장 대상이 아니다.

## 감사·복원·외부 보상

모든 시도(동일 데이터 재수신·실패·재시도 포함)에 작업자, 요청키, 작업범위, 시작/종료시각, 전후 해시, 상태 전이, 사유코드, 제공사 결과코드, 근거 참조를 기록한다. 행 원금액·계좌번호·이름·연락처·토큰·세션 URL은 로그에 쓰지 않는다. 작업자에게 감사 수정/삭제 권한을 주지 않는 append-only 구조와 훼손 탐지·보관기간은 추가 구현 항목이다.

내부 복원은 이전 불변 버전의 공개 포인터를 revision 검사 후 되돌리고 복원 사건을 남긴다. **외부에서 완료된 이체·발행·전송은 이 포인터 복원으로 취소되지 않는다.** 지원되는 취소/수정/회수 요청, 별도 승인, 권위 있는 결과 확인 및 재대사가 필요한 보상 절차다. 보상이 불가능한 서비스는 불가능 상태와 수동 조치를 기록한다.

복원 연습은 격리된 비운영 환경에서 백업 복구 → 네트워크 호출 없이 안전 사건 재생 → 해시/커서/포인터 검사 → 결과불명 외부 요청의 읽기 재확인 순서로 수행한다. 메타데이터 백업 RPO 24시간/RTO 4시간은 제안일 뿐 합의된 보장값이 아니다. 웹훅 수신 영수증은 응답 전에 내구 저장해야 한다. 보관 기간은 법률·계약·회사 정책 검토 전 특정 연수로 단정하지 않는다.

## 구현 착수·완료 판정

공급자별 지원표/자격, 인증·개인정보 정책, 실제 API/필드/고유키 계약, 상태 전이, 샌드박스 또는 안전한 검증환경, 운영 승인 정책이 확보되어야 어댑터를 활성화할 수 있다. 중복0·충돌격리·부분취소·응답불명·역순 웹훅·인증 만료·교차연도·체크포인트 재시작·로그 민감정보0·복원 연습을 서비스별 fixture로 검증한다. 이번 JSON의 requiredTests는 검사 목록이며 실행한 테스트 결과가 아니다.

현재 완료한 것은 목록별 화면/저장/복구 **설계**다. 어댑터·스케줄러·외부 상태 엔진·새 저장 테이블·외부 전송은 미구현이며, ECOUNT 전체 동등성이나 전환 완료를 뜻하지 않는다. 현재 운영 스냅샷 검증과 이 설계의 구현 완료를 혼동하지 않는다.
