## 고정된 결정

- 호텔은 전산 거래처 검색이 아니라 이름 직접 입력으로 추가한다.
- 새 호텔은 별도 결산 탭이며 전산 거래처를 만들거나 ERP 동기화를 하지 않는다.
- 신라 업로드 → 확인 → 명시 저장 순서. 기존 엑셀 차수/이익배분 규칙 유지.
- 기존 수기 매입단가·품목 연결을 임의 삭제하거나 평균으로 대체하지 않는다.
- 운영 시험 업로드/저장/호텔 추가는 하지 않는다.

### 1. 호텔 추가와 신라 업로드

**Q.** 손익계산서에 호텔 추가, 신라 업로드와 저장이 필요함. 호텔 이름은 직접 입력.

**A.** 이름 입력 모달과 WebPnlHotel 등록부, 인증 API, 동적 탭과 선택 복원을 구현했다. 새 호텔은 표준 견적서 업로드를 미리 검증하고 수동 저장하며, 전역 매입단가/전산 원장은 건드리지 않는다. 신라 업로드 및 저장 위치를 명확히 했다.

**결과.** lib/pnlHotelRegistry.js, pages/api/raum/pnl-hotels.js, components/raum/PnlHotelAddDialog.js, pages/raum/pnl.js 및 migration.

### 2. 시네신스 화이트 기존행 2개 오류

**Q.** PRESERVATION_COLLISION이 같은 품목에 반복되어 저장되지 않는 원인 확인.

**A.** 기존 처리가 동일 이름·판매가 후보 2개를 무조건 충돌로 판단했다. 원본 위치/내용을 사용한 일대일 보존으로 교체하고 같은 행 재사용을 차단했다. 원본 행 수가 달라 서로 다른 수기원가/품목 연결을 확실히 보존할 수 없으면 쉬운 문구로 확인을 요청한다. 사용자 운영 오류의 정확한 차수와 기존 두 행은 직접 조회하지 못했으므로 개별 원가가 동일하다고 단정하지 않는다.

**결과.** lib/raumPnlPreservationMatch.js 및 회귀 fixture. 원본 행의 수량·금액을 합치거나 기존 운영행을 삭제하지 않았다.
