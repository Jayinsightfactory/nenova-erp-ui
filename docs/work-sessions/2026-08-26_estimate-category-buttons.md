## 고정된 결정

- 사용자의 마지막 요청은 “수정작업만 실행”과 견적서 버튼별 검증이다. 운영에 반영하거나 고객 자료를 +1/-1 시험하지 않는다.
- 수국 수량 수정은 실제 변경 품목의 국가·품종으로 확정 범위를 한정한다. 다른 품종을 같이 취소하지 않는다.
- EXE의 확정 단위는 CountryFlower이므로 같은 품종의 다른 거래처가 포함되는 범위 자체를 거래처 단위로 바꾸지는 않는다.
- 단가만 수정하는 기존 경로는 확정취소·재고계산 없이 유지한다. 수량 자동 사이클은 중간 합산 생략, 마지막 재계산을 유지한다.
- 업체 선택과 조회 범위가 바뀌면 이전 조회/저장 콜백이 새 화면을 덮지 않는다.
- 테스트 통과와 운영 저장 검증을 구분하며 잔여 위험을 숨기지 않는다.

### 1. 전체 품종 확정취소 원인

**Q.** 수국만 바꾸는데 왜 네덜란드·중국장미·카네이션 등 전체를 확정취소하는가?

**A.** 로그에는 변경 품종이 있었지만 실제 공용 처리에는 빈 품종 배열이 넘어가 전체 범위로 해석되는 경로가 있었다. 실제 EXE의 선택 CountryFlower 전달과 운영 프로시저 정의를 읽기 전용 대조한 후, 변경 ProdKey를 서버가 확인하여 품종별 요청으로 분리했다. 부분 취소 성공 뒤 실패하면 성공이 명확한 품종만 복구한다. 미확정 품종을 임의 확정하거나 불명확한 응답을 자동 재실행하지 않는다.

**결과.** `lib/estimateCategoryCycle.js`, `pages/api/shipment/fix.js`, `pages/estimate.js`, 새 계약·테스트·EXE 근거 문서 보강.

### 2. 업체 선택 유지

**Q.** 견적서에서 업체가 갑자기 다른 업체로 돌아가는 원인은 무엇인가?

**A.** 목록 재조회가 첫 업체를 다시 선택하고, 느린 상세/불일치 응답 및 저장 후 콜백이 이전 업체 상태를 덮을 수 있었다. 현재 선택을 유지하고 연도·차수·거래처·필터와 요청 순서를 대조한다. 추가 품목 후보도 업체/품목/모달 회차가 다르면 적용하지 않는다.

**결과.** `lib/estimateSelectionState.js`, `lib/estimateAdditionalProductContext.js`, 관련 페이지·모달·회귀 테스트. 가짜 자료를 사용한 로컬 실제 브라우저에서도 업체 선택→재조회 유지 확인.

### 3. 수정작업 및 버튼별 검증

**Q.** 수정작업만 하고 견적서관리의 버튼별 기능도 검증해 달라.

**A.** 조회·요일·선택·수량·단가·업체 지정단가·네 등록 버튼·품목정보·선택 차감 삭제·확정현황·인쇄·엑셀의 handler/API/원장 영향과 실패 경로를 정리했다. 사전검증 조회 실패를 정상으로 간주하던 동작과 출력 조회 실패 업체가 조용히 빠지던 동작도 수정했다. 기존 네 등록 버튼과 단가 전용·선택 삭제 계약은 유지한다.

**결과.** `docs/work-reports/2026-08-26_estimate-button-audit.md`에 수정 완료/미수정 위험/검증 범위 구분. 전체 ERP 계약, 견적, 삭제, 게시판, dnSpy 근거, 변경 범위, 쓰기 보호, 운영용 빌드 통과. 로컬 가짜 자료 화면에서 네 모달과 확정현황 조회 확인. 운영 저장 시험·배포는 하지 않음.

## 미완 및 제한

- 후속 재조회 공통화 수정본은 Chrome 연결 오류로 브라우저 클릭 시험을 완료하지 못했다. 이전 단계의 화면 시험 성공과 구분한다.

- 여러 종류 동시 `[수정 저장]`: 여러 요청 중 앞 요청만 성공할 수 있는 구조는 남아 있다.
- `[확정현황]` 여러 차수 수동 취소: 자동 편집 사이클과 별개의 순차 처리 부분 성공 위험은 남아 있다.
- 일부 수량 저장에서 잘못된 입력만 제외하고 나머지를 진행하는 문제는 남아 있다.
- 운영 DB의 수국 농장 연결 0건 등 기존 자료를 수정하지 않았다. 모든 실데이터 정합성/저장을 검증했다고 보고하지 않는다.
- 새 코드가 운영에 적용된 상태가 아니다. 실제 운영 실행 검증과 배포에는 별도 지시가 필요하다.

### 4. 모든 재조회 경로 통일

**Q.** 일반 조회·수량·단가 저장에서 업체가 바뀌고, 늦은 상세가 새 업체 화면을 덮으며, 검색어 입력만 해도 선택이 풀리는 원인을 제시한 뒤 “통일하는작업 실행”을 요청했다.

**A.** 저장 시작의 선택 범위를 보존한 공통 재조회로 통일했다. 검색어는 초안으로만 다루고 후보 선택/명시 해제만 실제 업체를 변경한다. 새 목록 요청은 같은 업체의 이전 상세·불일치 요청도 무효화한다. 이전 업체의 늦은 오류·저장 완료·편집 기준값 갱신이 현재 업체의 상세나 입력값을 덮지 못하게 했다. 결과가 없는 업체는 빈 상세와 안내를 표시하며 다른 업체로 이동하지 않는다. 저장 성공 뒤 조회만 실패하면 저장 실패가 아니라 다시 조회 필요로 안내한다.

**변경.** `pages/estimate.js`, `lib/estimateSelectionState.js`, 선택 상태/실제 페이지 함수 실행 검사, 기존 연도·선택 삭제·편집 작업권 검사, 검사 실행 연결, 계약/재발 방지 문서. 이번 후속 작업은 API/SQL/수량·단가 계산·확정 처리 정책을 바꾸지 않았다. 기존 미배포 품종 범위 수정도 보존했다.

**검증 범위.** 실제 페이지의 검색 콜백과 저장/조회 함수를 가짜 응답·타이머로 실행해 업체 전환과 응답 역전을 검증했다. 운영 EXE CLI 및 DB SELECT 대조만 실시했다. 브라우저 연결이 실패해 후속 화면 클릭 시험은 미완료다. 운영 원장 저장/삭제/확정 시험과 배포는 하지 않았다.

### 5. 확정 해제 지연·상세 로그·다른 화면 변경 안내 진단

**Q.** 수량 변경 시 확정 해제만 오래 표시되고 세부 로그가 없으며 다른 화면에서 변경됐다는 안내가 나온다. 원인과 대응방법을 찾아달라.

**A.** 배포본 `8600d16`과 운영 AppLog/현재 SQL SP/EXE CLI를 대조했다. 자동 저장이 34-02 전체 7개 품종군을 해제하면서 중간 재고 합산을 생략하고, 성공 취소 뒤 `WAIT_CALC`를 반복 끝에서만 해제하는 것이 원인이다. 90초 게이트와 60초 요청 제한이 충돌해 16:05:26~16:09:58 약 272.5초, 4개 성공/3개 실패를 확인했다. 자동 저장 모달에는 서버 세부 로그 조회가 연결되지 않았다. 부분 성공 시 편집 비교값이 갱신되지 않아 본인 해제도 외부 변경 안내로 나타날 수 있음을 배포 코드의 메모리 실행으로 재현했다.

**실제 상태.** 16:15 KST 34-02 네덜란드·중국장미·콜롬비아알스트로·콜롬비아카네이션이 미확정인 것을 SELECT로 확인했다. 이번 요청은 원인 조사이므로 복구·수량 수정·재확정하지 않았다. 실제 타인/EXE 변경 유무는 개별 작업 감사가 부족해 단정하지 않는다. 앞서 준비한 선택 유지/품종 제한 로컬 수정본은 여전히 운영 미반영 상태다.
