# 실패 인보이스 재검증

## 요청·권한

사용자 요청: 실패 구간 재시도 후 전체 검증. 단위·시트 기준은 사용자에게 다시 묻기 전에 기존 MD와 dnSpy 기준을 확인한다.

유료 AI 기존 추가 18회 승인 중 이전 작업 14회, 이번 4회 재시도까지 사용했다. 이후 실패 구간의 송장별 세분화를 위해 추가 최대 12회가 승인됐다. 호출 전 `outputs/three-cycle-audit/ai-calls.json`에 기록하며 성공 구간은 재호출하지 않는다. 운영 업무 데이터 저장, EXE/SQL 수정 없음.

## 완료된 재검증과 정정

- 기존 추출 결과 19개를 실제 변환기/입고 어댑터로 로컬 재실행했다. 19개 모두 결과 생성, ERP 저장은 하지 않았다.
- 관련 자동 테스트 46개 중 45개 통과, 선택 원본 fixture 1개 스킵, 실패 0개. 이것은 실제 원본 정확도나 ERP 저장 통과를 대신하지 않는다.
- NL 18-02는 원본 78행이다. 최초 독립 검토의 77행은 오집계이며 파서 78행이 맞다. 원본 4페이지 그룹별 재계수 근거 `nl-row-retry.json`.
- TH 37-01 원본은 23행, 3,300 stems 및 USD1,821.90다. 최초 전사의 가짜 50 stems/USD21 행을 제거했다. 원본 대시 표식의 불확실성은 유지하고 양수 요약과 따로 기록한다.
- NL date는 Arrivaldate, TH date는 Arrival/Shipment, EC 40-01 date는 원문 Shipment Date다. 송장 작성일과 다르다는 이유만으로 오류로 보지 않는다. EC 36-01의 D/M 해석 문제는 별도다.
- EC 병합은 기존 국가 프롬프트에서 요구한다. EC 40-01 DARK WHISPER 200+100→300, 35-01 ROYAL BLUE 200+100→300, DRK 200+200+100→500은 원본과 일치한다. 행수 차이만으로 누락을 판정하지 않는다.

## dnSpy/MD와 읽기 전용 DB 기준

실제 저장 decompile `C:/Users/USER/nenova-decompiled/Nenova/ExcelLoadingPackingList.cs`를 재확인했다.

- 97행: `dataSet.Tables[0]`을 읽는다. 이는 **변환된 EXE용 패킹리스트** 첫 시트 선택 규칙이다. 공급업체 원본의 임의 첫 시트를 검증 없이 저장하라는 뜻이 아니다.
- 243~247행: BOX, TOTAL BUNCH, TOTALSTEAM, SteamOf1Box, SteamOf1Bunch는 별도 값이다.
- 품목명+SIZE 정확 매칭, Product.OutUnit/EstUnit 기준 수량 선택은 `docs/exe-golden/FormWarehouseUpload.md`, `docs/DB_STRUCTURE.md` 및 FormWarehouseAdd에 근거한다. 품목명에 500g가 있다는 이유로 송이를 500배 또는 1배로 추정하지 않는다.
- 단가 산식 경로를 구분한다. `FormWarehouseAdd.cs:145`의 SteamQuantity×UPrice는 수동 상세 수정 규칙이다. `ExcelLoadingPackingList.cs:248~249`는 K/L열의 UPrice/TPrice를 각각 읽으므로 수동 산식을 원본 인보이스에 자동 적용하면 안 된다.
- 운영 읽기 `GET /api/products/search?q=500g`에서 확인한 중국 500g 품목 7개는 OutUnit/EstUnit 모두 단. SteamOf1Bunch는 29, 5, 0 등이 있어 동일 환산계수를 적용하면 안 된다. 0을 임의 1로 보정하지 않는다.
- `GET /api/products/search?q=loose blooms`: ProdKey630, OutUnit/EstUnit=단, SteamOf1Bunch=100, BunchOf1Box=17, SteamOf1Box=1700. 5,100 blooms→51단은 정상이다. 이전 보고의 포괄적인 ‘태국 단위 오류’ 설명은 축소 정정한다. 혼합 수량을 한 물리 단위로 합계 표시하는 문제와 개별 ERP 환산 오류는 별개다. 미매칭 화환은 별도 검증 미완료다.

조회 증거: `china-unit-db-probe.json`, `thai-unit-db-probe.json`. 원장/재고 쓰기 없음.

## 콜롬비아 재시도

원본 35/36페이지를 송장 경계에서 두 구간씩 분리했다. 71페이지가 빠짐·중복 없이 복사됐고 원본은 보존했다.

- 15-01 p1~18: 504 실패.
- 15-01 p19~35: 송장 13건 추출 및 변환, 산술 검사 통과. 원본 ID·행수·상품금액+명시 비용·총액·명시 수량·페이지 전체 범위 독립 대조 통과. **원본 전반부까지 통과했다는 뜻은 아니다.**
- 17-01 p1~18: 504 실패.
- 17-01 p19~36: HTML 응답으로 JSON 파싱 실패. 당시 HTTP 상태가 별도 보관되지 않아 504로 단정하지 않는다. 후속 검사기는 상태와 비JSON 응답을 보관한다.

새 승인 12회 내에서 실패한 54페이지를 송장 경계를 유지한 3~5페이지 묶음으로 재분할했다. 1~4페이지 제한으로는 12회 안에 전체를 담을 수 없어, 실행 전에 사용자에게 범위를 알렸다. 성공 구간은 재분석하지 않는다. 결과는 후속 절에 추가한다.

### 추가 12회 실행 결과

- 12회 모두 실행 완료. 누적 승인 호출 30/30회이며 추가 자동 재시도는 하지 않는다.
- 11개 구간에서 송장 36건, 상품 258행을 추출했다. 이는 정확도/ERP 검증 통과 수치가 아니다.
- 15-01 p10~14 구간만 HTTP 502 비JSON 응답으로 실패했다. 송장 3882, 273811, 127922, 127929의 AI 결과가 없다.
- 이전 성공 구간을 합치면 15-01은 35페이지 중 30페이지, 17-01은 36페이지 전체의 추출 결과가 있다. 전체 71페이지 중 66페이지이며, 지원/표지 페이지도 포함한 범위다.
- 일부 추출 날짜가 2017/04/26 또는 2026/02/04로 출력돼 원본 날짜 순서 대조가 필요하다. 결과 생성과 날짜 검증을 분리한다.
- 증거: `co-fine-retry-result.json`, `retry-fine-chunks.json`, 각 `.parsed.json` 및 실패 `.response.txt`. 원본과 운영 업무 데이터는 보존했다.

### 원본 대조·계약 확인

- 이전 성공 구간 포함 49개 송장/344개 상품행의 숫자 산술 및 메모리 내 변환기 실행은 통과했다(`co-fine-arithmetic.json`). 운영 카탈로그를 주입한 매칭률 검사나 입고 저장 검증은 아니다.
- 15-01 추가 성공 송장 10건은 원본 수량·단가·금액과 대조했다. FGD32189의 원문 `02/04/2026`과 같은 묶음의 날짜 근거는 4월 2일을 지지하지만 결과가 `2026/02/04`이므로 날짜 검토 대상이다.

- 17-01은 36페이지 전체/26송장의 원본 상품행·수량·금액 대조를 완료했다. 날짜 오류 2건과 아래 날짜 의미 검토는 남아 있으므로 파일 전체 무조건 통과는 아니다. 검토 초안의 80037865 추가 Bimba 행 주장은 실제 파싱 파일 재확인으로 철회했다. 실제 원본과 결과 모두 11행/3,600 stems/USD1,548이며 정정 이력을 보존했다.
- 106255는 송장 작성일 4월 16일/출고일 4월 17일 중 후자를 추출했다. CO 프롬프트는 날짜 의미를 지정하지 않아 단순 OCR 오류가 아니라 날짜 계약 명확화 대상으로 분류한다.

- 같은 CO 프롬프트의 마지막 검사는 상품금액 합계와 총액을 직접 비교하도록 적혀 앞의 부대비 포함 총액 설명과 충돌한다. 후속 수정에서는 상품금액+부대비=송장총액으로 일관되게 검증해야 한다. 이번에는 앱 프롬프트를 수정하지 않았다.

## 보존할 결론

최종 독립 검토 판정은 `FINAL_NOT_ALL_PASS`다(`retry-review-final.json`). 49개 콜롬비아 송장/344행의 수량·금액 원본 대조가 완료됐고, 71페이지 전부의 처리 상태를 기록했다. 그러나 실제 추출 범위는 66/71페이지다. 날짜 문제, 실패 구간 4개 송장, 중국 구형 운영 파서 미지원, ERP 품목/저장/원가 검증 미완료가 남는다. 추가 승인 12회까지 모두 소진했으며 새 유료 호출은 수행하지 않았다.

‘변환기 결과 생성’, ‘원본 수량·금액 대조’, ‘ERP 품목 정확 매칭’, ‘저장 사전조건’, ‘실제 저장·재고·원가 검증’을 분리한다. 원본에서 근거를 찾지 못한 통화/환산/날짜를 추정해 전체 통과로 만들지 않는다. 이번에는 앱 코드/배포와 운영 업무 데이터 수정 없이 재현 자료와 판정을 갱신했다.
