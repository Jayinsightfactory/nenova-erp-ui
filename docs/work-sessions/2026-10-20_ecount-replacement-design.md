## 이어받을 때 고정된 결정

- 목표는 ECOUNT와의 단순 연동이 아니라 네노바웹 독립 운영이다.
- ECOUNT는 조회 전용이다. 전체 기능 중 미확인 항목을 임의로 제외하지 않는다.
- 기존 네노바 물류 원장과 EXE 호환성, 교차연도 업무키를 유지한다.
- 외부 사실 수집·발행과 내부 분개·장부를 분리한다.
- 기존 수집기의 기간·독립 행수·숫자오류·진단 마스킹 검증이 확대 전 선행한다.
- REA는 공식 가이드 검토 완료, 설치·실행 미수행. 현재 Chrome 화면 관측을 적용했다.

### 1. 2026-10-20 기능을 100% 이관하고 자동 작업을 설계

**Q.** ECOUNT API로 모두 가져올 수 없어 자체 웹에 기능을 구현하고 싶다. 은행입출금·세금계산서 등 별도 API 목록과 DB화 및 자동 작업을 설계하고 REA 활용을 검토해 달라.

**A.** 최신 origin/master에서 별도 작업트리를 만들었다. 실사이트맵과 입출금/세금계산서 표·버튼을 읽고 기존 수집·은행·세금계산서 코드를 조사했다. 자체 DB 기능군, 외부 API 목록, 제안 데이터 구조, 단계별 작업과 게이트, REA 적용 한계, 전환·복구 기준을 설계했다.

**결과.** 설계서와 14개 의존 작업 JSON 작성. 전체 화면 동등성·운영 API·실제 과거 이관은 미검증. 실행 스케줄은 만들지 않았다.

## 다음 작업

- M01 역할별 전체 메뉴 목록부터 시작하고 M02 화면 계약을 완성한다.
- 실제 계좌·개인정보·자격증명은 문서나 로그에 남기지 않는다.
- 계약/인증·민감정보 보관·SSMS 단계는 실제 준비 여부를 확인한다.
- 현재 설계만으로 ECOUNT 해지나 운영 원장 전환을 완료 처리하지 않는다.

### 2. 2026-10-20 모든 탭 구현 시작, DB 쓰기 금지

**Q.** 실제 DB 입력·수정 없이 모든 탭을 목록화하고 구현을 시작한다. 외부 API 기능도 제외하지 않고 디자인과 저장 로직까지 설계한다.

**A.** 현재 로그인 역할의 사이트맵에서 8개 탭·537개 메뉴 경로(말단 423개)를 메타데이터만 추출했다. `/ecount/workbench`에 18개 기능군 기반 430개 선택 가능한 화면 계약과 공통 입력/조회/수정/검토/취소/이력을 연결했다. 외부 연동 말단 28개도 입력 및 Outbox·멱등키·상태·오류 복구 설계에 포함했다. 실제 운영 DB·외부 API·localStorage를 사용하지 않으며 합성 자료는 메모리에만 존재한다. 별도 shell로 인증/활동/리플레이의 부수 요청도 마운트하지 않는다.

**검증.** 전체 ERP 계약, dnSpy evidence guard, UI layout, manifest, write scope, 신규 430화면 계약 테스트 통과. 첫 production build 통과. 브라우저에서 합성 견적 생성/수정(v1→v2, 16,500→19,800), 은행/전자세금계산서 저장 설계 확인. 로컬 API 차단 서버에서 해당 조작 중 API 시도 0건. 검색 구두점 무시 및 선택 탭 hover 대비를 보완하여 최종 빌드 재검증 중. 좁은 뷰포트 실제 검증과 원본 개별 화면의 100% 동등성은 미검증.

**한계.** 모든 메뉴에 연결되는 초기 구현이다. 원본 상세 항목·버튼·권한·전표/급여/보고서 산식의 개별 구현 완료가 아니다. 현재 역할 외 메뉴도 미확인이다. 코드만 배포하며 마이그레이션/DB probe/원장 수정은 하지 않는다. PR/운영 배포 결과는 최종 응답에서 확인한다.

**다음.** 기능군별 실제 화면을 조회 전용으로 대조하여 개별 필드/상태 계약을 교체한다. DB 연결은 이번 범위 밖이다.
