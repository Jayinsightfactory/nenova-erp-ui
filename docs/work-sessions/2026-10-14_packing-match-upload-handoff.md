# 패킹 매칭 완료 → 입고 업로드 연결

## 사용자 요청과 결정
- Q: 매칭 완료 후 저장문서 조회가 아니라 업로드 버튼이 나와야 한다. 매칭 데이터가 남아야 하고 후보 선택 후 저장을 다시 누르지 않아야 한다.
- A: 후보 클릭/Enter로 기존 팀 공용 CAS 매칭 저장을 실행하고 성공 후 창을 닫는다. 실패·충돌은 창과 입력을 유지한다.
- 완료된 매칭표는 전체 보기로 유지한다. 명시적인 `입고 업로드 준비` 버튼으로 원문 검토·생성·기존 입고 작업 단계에 연결한다.
- 활성 파일 작업 중 저장문서 조회를 다음 단계로 노출하지 않는다. 파일이 없는 기존 문서 조회 기능은 보존한다.
- 팀 공용 매칭과 브라우저 작업 보관은 별개다. 파일·추출·적용한 검토는 동일 PC/계정의 IndexedDB에 보관한다. 복구는 로그인 재확인·원본 SHA-256·최신 ERP 품목/공용 매칭 재조회 후 적용한다. 서버 preflight/commit 허가를 복구하지 않는다.
- 검토창에서 아직 적용하지 않은 편집까지 저장한다고 보장하지 않는다. 저장 실패는 화면에 안내한다.

## ERP 호환성과 기준선
- `guard-nenova-erp-changes`, 메뉴 기본값, orchestration과 실제 ExcelLoadingPackingList의 MakeTempTable/CheckData/InsertMaster 근거를 확인했다.
- 이번 수정은 SQL/API/SP writer를 변경하지 않는다. Product 조회, 기존 팀 매칭 파일 저장 경로를 재사용한다. 주문·분배·입고·재고·견적·매출 원장 보존.
- 매칭 완료는 입고 완료가 아니다. 원문/수량/가격 확인과 기존 서버 검증·명시 저장은 그대로 유지한다.
- 적용: 1920×1080/100%, 작은 화면, 키보드 후보 선택, 실패 유지, 최신 팀 매칭 재적용. 해당 없음: 새 메뉴/shell, 인쇄 양식 및 ERP 수량 계산 변경.

## 검증 및 진행 상태
- 전체 `test:erp-contract`, dnSpy evidence, manifest, write guard, build 통과.
- 실제 `41-1 중국 해상 ci1.pdf` 7쪽/101행으로 로컬 브라우저 1920×1080 및 1280×800 확인. 후보 1회 선택 저장·닫기와 계정별 작업 복구 성공. 유료 분석 및 ERP 쓰기 없음.
- 최종 검토에서 XLSX 원본과 복구 추출값의 해시 연결을 보완했다. 모든 원본 형식에 SHA-256을 저장하고 복구 전에 실제 파일과 대조한다. 변경된 XLSX 거부 테스트 통과, 재검토 P0/P1 없음.
- 최종 빌드와 실제 PDF 브라우저 재검증 통과. 로컬 모의 팀 매칭으로 101행 전부 완료했을 때 CTA 노출·전체표 유지·원문 확인 게이트도 통과했다. 운영 품목 매칭을 시험 목적으로 변경하지 않았다.
- PR/배포는 아직 완료로 판정하지 않는다.
