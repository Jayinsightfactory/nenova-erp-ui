## 이어받을 때 고정된 결정

- 현재 한 대의 PC에서 카카오톡 매크로 작업이 이루어진다. 이는 사용자가 설명한 운영 현황이며 이번 작업에서 실행 상태를 점검하지는 않았다.
- 핵심 목적은 네노바웹에서 작업된 데이터나 작업 중 필요한 웹 데이터를 특정 톡방으로 전달하는 것이다.
- 반대 방향인 카톡 → 네노바웹 데이터 전달도 포함한다.
- 일회성 전송 기능으로 끝내지 않고, 업무 중 필요한 전송 기능을 계속 추가할 수 있게 기획한다.
- 두 프로젝트를 연계하는 것이 목적이며, 저장소를 하나로 합칠지는 아직 결정하지 않았다.
- 현재 요청은 기획 저장이다. 실제 메시지 전송, 자동화 활성화, ERP 등록은 수행하지 않았다.

## 질문 → 답변

### 1. 두 프로젝트를 함께 작업

**Q.** 네노바웹 작업과 GitHub 저장소 `Jayinsightfactory/nenovakakao`의 `main`, 로컬 `C:\Users\USER\Downloads\nenovakakao`, 실행 파일 `moyi_console.py`를 합쳐서 작업하고 싶다.

**A.** 저장소 통합과 시스템 연동은 서로 다른 선택임을 확인했다. 후속 설명을 통해 우선 목표를 웹과 카톡 간 업무 데이터 양방향 전달로 구체화했다. 저장소 통합은 확정하지 않았다.

### 2. 단일 매크로 PC를 활용하는 확장 가능한 양방향 전달

**Q.** 한 대 PC에서 카톡 매크로가 실행 중이다. 네노바웹에서 작업한 데이터를 특정 톡방으로 보내고 반대 방향도 연결하고 싶다. 작업하다가 필요한 웹 데이터를 계속 카톡으로 보낼 수 있도록 기능들을 추가하려 한다. 이 기획을 저장해 달라.

**A.** 확정된 목적과 아래 초기 설계안을 문서로 저장했다. 아래 설계는 구현 전 제안이며 코드와 현재 API를 확인해 구체화해야 한다.

## 초기 설계안 — 구현 전 제안

### 웹 → 카톡

1. 사용자가 웹의 업무 화면에서 보낼 데이터를 선택한다.
2. 대상 톡방과 메시지 내용을 확인한다. 업무별 메시지 양식을 재사용할 수 있게 한다.
3. 웹 서버가 전송 요청을 고유 ID와 함께 보관한다.
4. 매크로 PC가 요청을 가져와 지정 톡방으로 전송한다.
5. PC가 처리 결과를 서버에 돌려주고 웹에서 대기·전송 중·전송 확인·실패·결과 불명 상태를 확인한다.

PC 중단 시 요청을 보관하고 재연결 후 이어 처리하는 구조를 검토한다. 중복 실행 방지용 요청 ID와 점유/만료 규칙이 필요하다. 전송 직후 결과 보고가 끊긴 경우 자동 재전송으로 중복 메시지가 생기지 않도록 결과 불명 상태와 재확인 절차를 설계한다. 매크로가 관찰할 수 있는 전송 확인과 상대방 읽음은 구분한다.

### 카톡 → 웹

1. 매크로 PC가 설정된 톡방의 메시지를 수집한다.
2. 톡방 식별 정보, 원문, 수신 시각, 수집 식별자를 웹으로 전달한다.
3. 웹이 중복 수집을 판별하고 원문과 관련 업무를 연결한다.
4. 필요한 업무는 분석·매칭·검토 화면으로 이어진다. ERP 반영 방식은 기존 계약과 별도로 확인한다.

### 기능을 계속 추가하기 위한 공통 구조

- 톡방 연결 설정: 표시 이름과 실제 식별 정보, 수신/발신 용도를 관리한다.
- 전송 유형·메시지 양식: 업무 화면마다 공통 전송 기능에 유형과 데이터만 전달하도록 한다.
- 작업 이력 연결: 원본 웹 작업 ID, 카톡 수집 ID, 전송 요청 ID를 연결해 추적한다.
- 운영 상태: 매크로 PC 연결 상태, 마지막 응답 시각, 대기 건수, 실패 및 재시도를 보여준다.
- 자동 전송: 사용자가 지정한 업무 이벤트·대상 방·조건에 한해 설정하는 후속 기능으로 검토한다. '계속 전송'의 주기/이벤트 조건은 아직 미정이다.

## 다음 작업과 확인 항목

1. 두 저장소의 현재 코드와 실행·배포 구조를 읽고 기존 카톡 수집/전송 기능, API, 인증, 이력 저장 방식을 확인한다.
2. 실제 톡방 식별 방식과 PC 매크로의 전송 완료 판별 수준을 확인한다.
3. 첫 연동 업무를 정한다. 예: 선택한 주문/분배 결과 또는 잔량을 지정 톡방으로 전달. 이는 예시이며 첫 대상은 미확정이다.
4. 공통 데이터 계약, 중복 방지, 재시도, 오프라인 복구, 발신/수신 순환 방지를 설계한다.
5. 먼저 사용자 선택 전송으로 검증하고, 필요에 따라 이벤트 기반 자동 전송을 추가하는 방안을 검토한다.
6. 구현 시 네노바웹 화면 기준은 1920×1080 CSS pixel, 확대 100%로 검증한다.

현재 `docs/CODEX_SUBTASK_ORCHESTRATION.md`는 이 체크아웃에서 찾지 못했다. 후속 구현 전에 최신 저장소에서 해당 운영 문서를 확인해야 한다. 이번에는 하위 작업을 생성하지 않고 문서만 저장했다.
