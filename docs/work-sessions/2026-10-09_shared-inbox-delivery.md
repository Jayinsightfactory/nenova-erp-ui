# 영업방 공유 매칭·처리확인과 추가취소방 전달 근거

요청: 계정이 달라도 분배 매칭·처리확인을 공유하고, 현장 추가취소방 전송을 확인한 원문에 전달완료 표시.

- 성공한 분석은 정확한 원문과 전체 YYYY-WW-SS 키로 인스턴스 공용 저장. 기존 계정별 저장본은 동일 키의 최신 성공본만 안전하게 이전. 작성자·저장 시각 유지.
- 품목 매핑은 기존 공용 mappings API 사용. 개인 입력 초안·선택·완료 잠금·토큰은 공유 대상이 아니다.
- 수동 처리확인과 검증된 저장 이력은 기존 공용 서버 원장을 최초 진입 및 60초마다 다시 조회. 고비용 SQL 대조는 선택 갱신 유지.
- 추가취소방은 Orbit의 고정 방 SELECT 전용 피드를 조회. 동일 전체 원문, 고유 원본 식별값, 정확한 전송 시각·선택 연도가 맞을 때만 전달완료. 부분문·중복·생략·시각 불명확·이전 연도는 미확인 또는 재확인.
- 최근 7일 전달 조회. 최대 4000건 페이지 조회가 완료되지 않으면 실패. 실패 시 초록 표시 해제. 클라이언트는 건수·문자·UTF8 바이트로 요청 분할.

ERP 부작용: OrderDetail, ShipmentDetail, ShipmentFarm, ShipmentDate, Estimate, WebProfitReport, 재고·영업매출 원장 모두 보존. 전달 상태는 주문/분배 적용 상태와 별도이며 메시지 전송 기능은 호출하지 않는다. 신규 ERP SQL/DDL 없음. EXE 보존 경계 근거는 FormShipmentDistribution 계약을 따른다.

검증: 공유 분석 교차계정·교차연도·기존 저장본 이전 및 동시 작성, 전달 일치/부분/중복/추정/교차연도, API 인증·페이지 제한·오류, 클라이언트 배치/응답 범위 테스트. 1920×1080 및 1366×768 격리 실브라우저에서 전달완료 1건/미확인 1건, 오류 후 완료 0건, 가로 잘림·브라우저 오류·ERP 쓰기 0건 확인.

상위 피드 PR: https://github.com/Jayinsightfactory/mindmap-viewer/pull/12 (Node18/20/22 CI 및 관련 단위 테스트 23건 통과).

### 추가 Q&A — 전달 미확인으로 돌아가는 원인 조사

**Q.** 한 번 매칭된 전달 확인 데이터는 저장되어야 하는데 전부 전달 미확인으로 나온다. 원인을 찾아달라.

**A.** 운영 인증 조회 결과 영업방 222건, 전달 API HTTP 200, DELIVERED 131건 / UNCONFIRMED 87건 / AMBIGUOUS 4건으로 확인했다. 조사 시점에는 전체 미확인 현상이 재현되지 않았으며 당시 요청 실패 원인은 확정하지 않았다. 코드에는 전달 근거의 영구 저장 경로가 없고 React 상태만 사용한다. 원문 목록·계정·연도·차수가 바뀌면 결과를 초기화하며, 분할 조회 중 하나라도 실패하면 items 전체를 비운다. 화면은 근거 없는 상태를 모두 전달 미확인으로 표시한다. 서버의 최근 7일 재조회와 30초 메모리 캐시도 기존 확인 결과를 보존하지 않는다.

**고정 결정.** 사용자의 최신 요구는 검증된 전달 근거의 저장·유지다. 앞서 기록된 ‘실패 시 초록 표시 해제’ 정책은 이 요구와 충돌하므로 후속 수정 시 교체해야 한다. 저장된 확인 근거와 현재 재조회 실패를 별도로 표시하고, 아직 확인되지 않은 원문을 완료로 추정하지 않는다.

**결과 / 남은 작업.** 이번 요청은 원인 조사이며 기능 코드·운영 DB·배포 변경 없음. 전달 근거 공용 저장과 재조회 실패 시 확인 유지 구현은 아직 하지 않았다. 운영 probe 출력은 건수·상태만 기록했으며 원문·인증값은 문서에 저장하지 않는다.

### 추가 Q&A — 최근 3일 원문과 분석 값 유지 구현

**Q.** 영업방·추가취소방 내용은 3일치면 충분하며, 한 번 Claude 분석된 품목 매칭 값이 유지되는 것이 더 중요하다.

**A.** 한국시간 오늘 포함 최근 3일로 자동 조회와 날짜 선택 범위를 제한했다. 이전 7일 스냅샷과 새로 받은 원문에서 기간 밖의 확실한 서버 수신 원문만 목록에서 제외한다. 업로드·시각 불명확 원문은 자동 삭제하지 않는다. 원문 정리는 분석 저장소·처리 이력·ERP 원장에 영향을 주지 않는다.

**고정 결정.** 성공한 분석의 서버 키는 동일 연도 + 정확한 원문으로 변경했다. 분석 입력에는 차수가 없고 연도만 있으므로 같은 연도의 차수 전환에 재사용하며, 실제 ERP 검토·저장 키는 기존 전체 차수를 유지한다. 기존 계정별/차수별 성공 저장값을 작성자·시각과 함께 이전하고, 성공한 명시 재분석만 교체한다. 메모리 갱신 실패는 이전 성공값을 유지하며 새 Claude 분석을 시작하지 않는다. 전달 근거도 정확한 원문 식별·시각·연도별 공용 파일로 저장하며 신규 조회 실패/미일치는 기존 완료를 지우지 않는다.

| 기준 | 판정 | 근거 |
|---|---|---|
| 원문·매칭 유지, 실패 안내 | 적용 | 공유 저장·이전·재시작·다른 계정/차수·조회 실패 회귀 테스트 |
| 1920×1080, 100%, 작은 화면 | 적용 | 전달/숨김 브라우저 fixture 1920×1080 및 1366×768; 가로 잘림·콘솔 오류 없음 |
| 키보드 | 적용 | 전달 fixture에서 Enter 숨기기, Space 펼치기, 초점 복귀, Tab/Shift+Tab 확인 |
| 새 메뉴·shell·모달 | 해당 없음 | 기존 페이지의 조회·복원만 수정 |
| ERP 저장·분배·견적·매출·재고 | 해당 없음 | SQL/저장 API 변경 없음, 원장 전부 보존; 전달 사실과 ERP 적용은 별개 |
| 오래된 원문 영구 보존 | 예외 | 최신 사용자 요구에 따라 최근 3일만 표시; 분석과 처리 근거는 계속 보존 |

**검증.** 전체 ERP 계약, dnSpy 근거, 변경 manifest/write guard, production build 통과. 별도 분석 저장·전달 저장·클라이언트 테스트와 격리 브라우저에서 재조회 실패 후 완료 유지, 새로고침 후 저장 근거 및 품목 매칭 복원 확인. 실제 ERP 쓰기/카톡 전송 없음. 요청된 `docs/CODEX_SUBTASK_ORCHESTRATION.md`는 현재 저장소에 없어 제공된 AGENTS 역할·권한 경계를 적용했다.

**배포.** PR/운영 확인 결과는 후속 기록으로 갱신한다. `outputs/` 및 `.next-delivery-smoke/`는 커밋 대상이 아니다.
