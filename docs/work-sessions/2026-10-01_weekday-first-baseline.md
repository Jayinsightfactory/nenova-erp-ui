## 이어받을 때 고정 결정

- 최초 기준은 사용자가 주광 페이지의 확정 버튼을 누른 시점의 **현재 저장된 ERP 분배**다.
- 페이지 확정은 공용 EXE 확정/SP/isFix 변경이 아니다. 업로드/파란 초안은 최초 기준에 넣지 않는다.
- 최초 기록은 연도+전체 세부차수+업체별 최초 한 번 불변 보관한다. 재확정·수량취소로 덮지 않는다.
- 표는 전/현재/후 대차수 가로 연속이며, 차수당 최초01·목금토일·01잔량·최초02·월화수·잔량의 11열이다.
- 알스트로의 출고단위가 단이면 표시만 48(3)으로 한다. 실제 ERP 수량/단위를 환산 저장하지 않는다.
- 노랑은 최초 대비 변경, 보라는 수동 확인 선출고, 파랑은 ERP 미적용 초안이다.
- 선출고 원천은 자동 추정하지 않는다. 담당자 지정 미래 차수·실제 날짜수량 이하·출고단위를 검증한다.
- 관리 상세 합계(차감 포함)와 인쇄 합계(단가별 반올림)를 따로 읽어 일치/불일치/확인 필요를 보여준다.

## Q&A

### 1. 최초분배와 잔량 / 알스트로

Q. 알스트로 48(3), 최초분배·요일·최초기준 잔량을 표시하고 해당요일 수량과 금액만 출력해달라.

A. 최초 날짜분포까지 보관해 현재 분배 및 초안과 비교한다. 01잔량=최초01-목일 배분,
대차수 잔량=최초01+02-목수 배분이다. ERP 재고 또는 배송 완료로 주장하지 않는다.

### 2. 확정 시점과 범위

Q. 기준은 언제 고정하나? → “확정버튼을 누른시점.” / 공용 ERP 확정인가? → “지금 주광페이지에서만 확정하는거야.”

A. 전산값 미리보기 후 저장 직전 지문을 다시 확인하고 private runtime에 불변 저장한다.
다른 화면의 실제 분배 수량/날짜 변경은 그대로 읽어 최초 기준과의 차이를 보여준다.

### 3. 중심차수·품목명·변경 비고

Q. 좌우 버튼으로 중심차수 이동, 품종을 빼고 품목명 전체 표시, 변경값(최초값), 합계 옆 변경량 클릭해 떠 있는 비고창.

A. 실제 PeriodDay의 전후 cycle을 사용한다. 알려진 영문 품종 접두어만 화면에서 제거하며
ProdKey/원본명/인쇄명은 보존한다. 변경량과 비고 표식을 클릭해 floating 입력창을 열고
revision 동시수정 보호로 서버 비고를 저장한다. 새 표 열을 만들지 않는다.

### 4. 선출고와 견적 관리 수량

Q. 38차에 39차 물량을 사용한 선출고는 다른 색과 원천 차수 수량으로 표시하고 실제 견적관리 총수량과 매칭해야 한다.

A. 입고 후보만으로 실제 원천을 확정할 수 없어 담당자 수동 확인 기록으로 구분한다.
현재 날짜수량이 줄어 기존 선출고 기록보다 작아지거나 단위가 바뀌면 재확인을 표시한다.
견적관리의 실제 상세 GET과 공통 인쇄 SELECT를 읽고 차감·반올림·단위 차이는 숨기지 않는다.

### 6. 수량 감소 후 잔량 미반영·글씨 겹침·품목 행 강조

Q. 5→4 수량 변경에도 기준잔량이 바뀌지 않는다. 작은 숫자가 겹치며 마우스를
움직일 때 품목 전체 라인이 강조되어야 한다. 글씨 크기와 색도 진해야 한다.

A. 확정 기준이 없는 미확정 preview는 역사 잔량에 쓰지 않았고, 초안 예상잔량도
보조 숫자로만 표시하던 문제가 있었다. 역사값은 보존하면서 표시용 잔량을 분리해
유효한 편집 후 예상값을 주 숫자로 표시한다. 확정 전에는 미확정 예상, 편집 시에는
초안 예상으로 명시한다. 단위·범위·복수초안이 불명확하면 여전히 미확인이다.

수량/품목은13px·600굵기·진한 남색, 보조12px. 숫자와 차이 버튼을 다른 줄에 놓고
품목260px 고정 및33열 가로 연결은 유지하되 표 안의 가로스크롤과 차수 바로보기를
사용한다. CSS hover/focus-within으로 모든 칸에 선을 표시해 노랑/보라/파랑을 보존한다.
마우스 움직임마다 React state를 갱신하지 않는다. 견적 대조 상세는 버튼으로 연다.

검증: 순수 테스트5→4 예상잔량1/역사잔량0 보존; browser fixture2→1 예상1,
2→0 예상2 및 숫자/차이 분리, 전체 행 강조/노랑 보존. 1920×1080/100% 및1280
문서 가로잘림 없음. 기존 ERP 계약·dnSpy 근거·manifest·쓰기 가드 통과.
운영 preview36~40의01/02 모두200 확인, 실제 EXE dnSpy 재읽기 수행.
운영 원장/최초기준/비고 쓰기 시험 없음. ERP 적용은 여전히 별도 미완이다.
최종 로컬 브라우저에서13px/600굵기/진한 글씨와 차수 바로보기, 첫 화면21행,
숫자/차이 겹침 없음, 오류0 확인. 최종 build와 독립 읽기 검토 승인.
배포 여부는 PR 및 Cafe24 workflow 성공과 운영 읽기 전용 smoke로 판정한다.

### 5. 최초분배 칸이 모두 비어 있음 — 후속 수정

Q. 운영 화면의 최초분배 값이 표시되지 않는다.

A. 실제 운영에서 저장된 최초 기준이 0건이고, 기존 UI는 저장된 기준만 표시한 것이
원인이다. 미확정 차수도 기존 read-only preview를 자동 조회하여 현재 분배 수량을
표시한다. 머리글은 `미확정`, 셀 tooltip은 현재 ERP 분배량임을 명시한다. 이 값은
최초 잔량/날짜 변경/변경량 계산에 사용하지 않고, 확정한 불변 기준이 항상 우선한다.
자동 확정 또는 ERP 쓰기는 없다. 범위별 오류와 늦은 요청을 격리한다.

결과. 단위/연도/세부차수/중복/실패/0 테스트 및 모든 ERP 계약, dnSpy 근거, manifest,
쓰기 scope, production build 통과. 로컬 browser fixture는 1920×1080/100%에서 첫 화면
32행, 표33열, 초기 미확정6칸 모두 수량 표시, 확정2회만 명시 호출, 이후 원본 유지,
조회 실패/회복과 1280px 가로 스크롤/비고창 검사 통과. 실제 설치 EXE를 dnSpy CLI로
재읽어 공용 확정/재고계산 호출을 확인했고 이번 경로에서는 호출하지 않는다.
배포 및 운영 read-only smoke는 PR/workflow 확인으로 최종 판정한다.

`docs/plans/weekday-estimate-change-criteria.md`의 2026-10-01 기준과
`docs/contracts/estimate-weekday-workspace.json`, 이 기록을 먼저 읽는다.
기준 저장은 페이지 전용이고 공용 확정/원천 재배정이 아니다. 운영 상태는 해당 PR 및
Cafe24 workflow로 확인한 뒤 진행하며, 성공하지 않은 배포나 실제 ERP 적용을 완료로 주장하지 않는다.
