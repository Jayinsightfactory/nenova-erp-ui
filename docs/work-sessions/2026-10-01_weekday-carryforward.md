# 주광 차수 잔량 이월·수정 이력

| 항목 | 내용 |
|---|---|
| 화면 | /estimate/weekday |
| 기본 | 전산 달력 현재 업무주 +1 |
| 원장 부작용 | ERP/최초 기준 보존, private runtime 마감잔량 이력만 저장 |
| 배포/PR | PR850/851 병합·Cafe24 배포 성공·운영 read-only smoke 통과 |

## 고정된 결정

- 37차 잔량 수정 →38차 잔량에 이월 합산. 마감 수정 전후/담당자/시간/사유 보관.
- 최초분배 불변, 저장된 실제 출고·현재고·견적 수량과 금액은 변경하지 않는다.
- 수동 마감값부터 차수 연결, 명시0도 유효, 음수는 부족잔량으로 보존.
- 품목 단위/달력/출고 기준 불명은 임의0 금지. 초안은 이월 예상값으로만 표시한다.
- 한국 날짜+PeriodDay 기반 +1 중심; 수동 입력/좌우 이동은 기본 응답으로 덮지 않는다.

### 1. 날짜 형식 차단 진단

Q. 2026/40-01 수국 블루10/4 20→15,10/1 0→5 저장 시 PeriodDay 시각 오류.

A. 읽기 전용 API 확인: 주광533/품목866/출고Sdate124386,
ShipmentTimestamp `2026-10-04 00:00:00.000`, PeriodDay 표시 `2026-10-04`.
EXE 정확 조인 WeekDay1은 정상. 문자열형식 직접 비교가 차단 원인.
현재20박스 보존, 오류수정 배포·운영 보정은 별도 승인 미완.

### 2. 중심 +1 / 전차 잔량 수정

Q. 중심차수 +1 기본,37차 잔량을 수정하여38차에 합산,수정이력 보관.

A. page-only 마감잔량과 이월 ledger를 설계하고 기존 원장·최초·인쇄 수량과 분리한다.
계획 `docs/plans/weekday-carryforward-2026-10-01.md` 및 계약 JSON.

결과. 구현 완료. 신규 store/API26건 및 helper/calendar13건 통과, 기존 전체 ERP 계약·board·manifest/write guard·빌드 통과. 1920×1080/100%와1280×800 격리 브라우저 fixture에서 마감 저장·이력·다음차수 합산·초안 분리·팝업/스크롤 검증, 메인 스크린샷 확인. 독립 최종 검토 승인(잔존 P1/P2 없음). 취소0의 최초 원문 날짜합계는 편집키와 별도로 보존하는 회귀 포함.

### 3. 표시된 일요일 수량 편집 불가

Q. 캡처의 38-01 일요일7박스 입력이 안 된다.

A. 운영 read-only 브라우저에서 품목866 / 2026-09-20의 38-01 수량7과 38-02 취소0 원문을 확인했다. actualOrderWeeks에 0 기록도 포함되어 복수 업무차수로 차단됐다. 원문·합계·0 기록을 보존하고 유일 nonzero 차수만 편집 원천으로 선택한다. 양쪽 실제 수량·불명값·단위충돌은 계속 차단.
