# 업로드 지연과 서버 부하 조사 (2026-11-02)

## 운영 근거

- Cafe24의 최근 7일 Nginx 접근 로그 15개 파일을 읽기 전용으로 집계: 532,317 요청. `/api/work/activity?me=1` GET 308,792건, 같은 API POST 8,549건. 11월 2일 15시 GET만 7,441건이다. 기존 브라우저 기록기는 열린 탭마다 5초 간격으로 `identify()`를 호출했다.
- 분배 업로드 API는 10월 28~29일 504, 10월 29일 499가 있었다. 별도 감사 137번 381행 적용은 749초에 완료됐다. 따라서 응답 시간 제한과 장시간 처리 문제가 실제로 발생했다.
- PM2 웹 프로세스 오류 로그의 마지막 4MB에는 timeout 문자열 544건, DB timeout 유형 280건이 있다. 해당 로그에는 시각이 없어 특정 업로드와 인과관계를 확정할 수 없다.
- 커널 OOM 관련 메시지 15건은 모두 10월 26일 16~17시다. 11월 2일 지연을 OOM으로 설명하지 않는다. 11월 2일 16:38 현재 웹 프로세스 약 466MB, 호스트 free memory 약 2.6GB, load 0.12/0.22/0.24였다.
- 앱 DB 계정은 `VIEW SERVER STATE`가 없어 서버 전체 대기·블로킹·SQL 오류 로그를 볼 수 없고, Query Store는 OFF다. DB timeout의 정확한 SQL과 겹친 작업은 미확정이다.

## 수정

- 기록기의 `me=1` 확인 주기를 열린 탭당 5초에서 60초로 줄이고, 숨긴 탭의 정기 확인을 멈춘다. 로그인·로그아웃, 탭 복귀, 페이지 이동 시 즉시 확인은 유지한다. 이벤트 전송은 계속 5초 간격이다.
- 활동 기록의 파일/디렉터리 `fsync`는 웹 요청의 Node 메인 스레드에서 별도 worker thread로 옮긴다. POST 응답은 worker의 영속 저장 ACK 이후에만 성공하고, 서버 API 감사 실패는 기존 bounded retry queue에 남긴다. ERP SQL 쓰기·주문/출고 로직은 변경하지 않았다.
- 배포 파이프라인에 읽기 전용 진단 모드를 추가했다. 진단 dispatch에서는 배포 job을 실행하지 않고 PM2/Nginx 집계만 출력한다.

## 확인과 남은 한계

- 운영 진단 작업: GitHub Actions 41407554391, 41407718097, 41408091937, 41408829541. 원본 고객·URL·토큰을 출력하지 않고 집계했다.
- 활동 기록 클라이언트 9개, 서버 저장·복구 테스트 통과. 로컬 Next build는 컴파일 성공 후 11개 page-data worker 구동 중 Windows 페이징 파일 부족으로 실패했다. CI 빌드 및 배포 검증 필요.
- 업로드의 12분 처리 자체는 원장 쓰기 경로의 행별 SQL 작업을 별도 조사해야 한다. SQL 대기/실행시간 권한을 확보하거나 특정 작업에서 단계별 시간 집계를 추가하기 전에는 이 수정으로 749초 처리가 얼마나 단축되는지 확정하지 않는다.
