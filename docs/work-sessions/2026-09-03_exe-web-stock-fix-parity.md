# 2026-09-03 Nenova.exe · 웹 재고/확정 정합 세션

## 세션 정보

- 날짜: 2026-09-03
- 작업 범위: 붙여넣기 주문등록·출고분배·차수 확정·재고 표시·Nenova.exe 공유 SQL
- 상태: 원인과 설계 기준 기록 완료. 36-01 카네이션 운영 원장 보정이나 공용 SP 원복은 수행하지 않음.

## 사용자 의도

- 기존에 문제없던 `nenova.exe`가 웹 기능 수정 때문에 달라지거나 고장 나면 안 된다.
- 웹과 EXE 중 하나만 맞추는 방식이 아니라 양쪽이 같은 공유 ERP 원장을 안전하게 사용해야 한다.
- 화면에서 0으로 보이지만 내부 소수 오차 때문에 음수로 판정되는 품목, 성공으로 표시됐지만 실제 미반영된 주문/분배 같은 사례를 이후 작업에서 반드시 회귀 조건으로 사용한다.
- 작업 설계는 dnSpy와 운영 읽기 전용 근거를 먼저 확인하고, 하위 작업이 있더라도 승인·운영 쓰기는 메인 작업만 수행한다.

## 질문 → 확인 결과

### 붙여넣기 주문등록·분배

- 사용자는 취소와 추가가 같은 수량인데도 `취소량이 현재 출고보다 큼`, 기준수량 변경, 성공 결과 미표시, 재실행 때만 변경수량이 보이는 문제를 반복 보고했다.
- 전체 처리는 `CANCEL 전체 → ADD 전체` 순서의 단일 트랜잭션이어야 하며 한 건이라도 실패하면 주문·분배·출고일·이력까지 전부 롤백해야 한다.
- ADD는 같은 연도·차수·업체·품목의 활성 주문이 없을 때만 주문을 생성한다. 주문이 이미 있으면 주문수량은 보존하고 분배만 증가시킨다. CANCEL은 주문수량을 바꾸지 않는다.
- 성공은 서버가 raw Order/Shipment, `ViewOrder`, `ViewShipment`, `ShipmentDate`를 다시 읽어 의도값과 일치함을 확인한 뒤에만 표시한다. 결과 창은 즉시 표시하고 같은 완료 요청 재실행은 중복 가산하지 않는다.

### 36-01 콜롬비아카네이션 음수 진단

- 2026-09-03 운영 웹 `/shipment/fix-status` 읽기 전용 조회에서 실제 부족으로 표시된 품목:
  - `CARNATION Crimea`: 입고 18, 출고 20, 부족 2
  - `CARNATION Hermes Orange`: 입고 22, 출고 24, 부족 2
  - `CARNATION Novia`: 입고 57, 출고 60, 부족 3
  - `CARNATION rodas`: 입고 27, 출고 28, 부족 1
  - `CARNATION Yukari Cherry`: 입고 37, 출고 38, 부족 1
  - `Spray Carnation Caja B (Caesar, Romany Orange)`: 입고 0, 출고 1, 부족 1
  - `Spray Carnation Caja D (Pigeon Hot Pink, Purple)`: 입고 0, 출고 1, 부족 1
- 최초 조회에는 `CARNATION Hermes`가 입고 18·출고 18인데도 부동소수점 음수 오차로 포함되어 부족 `0.00`으로 표시됐다. 이후 재조회 목록에서는 제외됐다. 이 사례는 반드시 `raw negative but normalized zero` 회귀 fixture로 유지한다.
- 사용자가 제공한 EXE 화면에서 선택된 행은 `CARNATION Hermes`였고 상단 입고 18·출고 18·잔량 0은 정상이다. 왼쪽의 다른 품목 행까지 모두 잔량 0이라는 뜻은 아니다.

### EXE 화면과 웹 진단의 값 의미

- `FormStockView`의 현재 잔량은 선택 `StockMaster`에 연결된 `ProductStock.Stock` 저장 스냅샷이다.
- 웹 확정 화면의 값은 확정 후 예상값을 별도 계산한 값일 수 있다. 두 값을 모두 `잔량`이라는 이름으로 표시하면 사용자가 같은 값으로 오인한다.
- 이후 화면은 최소한 `EXE 저장 잔량`과 `확정 후 예상 잔량`을 분리해 표시하고, 계산 기준 차수·입고·조정·확정출고·미확정출고를 함께 노출해야 한다.

### 공유 SQL 변경 영향

- 운영 읽기 전용 probe 결과 `usp_ShipmentFix`, `usp_ShipmentFixCancel`, `usp_StockCalculation`에는 웹 작업 중 적용된 패치가 존재한다.
- 이 프로시저들은 웹 전용이 아니라 `nenova.exe`도 호출한다. 따라서 이들의 `ALTER`는 웹 수정이 아니라 **EXE 동작 변경**으로 분류한다.
- 2026-08-20 패치는 기존 기말 스냅샷에서 미확정 출고를 다시 빼던 이중차감을 막기 위해 적용됐고, 2026-08-26 패치는 확정/취소/재계산 동시 실행을 직렬화한다. 원인을 확인하지 않고 전체 원복하면 과거 이중차감·경합 문제가 재발할 수 있다.

## 확정된 설계 원칙

1. `usp_ShipmentFix`, `usp_ShipmentFixCancel`, `usp_StockCalculation`의 변경은 항상 EXE 변경으로 취급한다. 웹 기능이라는 이유로 직접 ALTER하지 않는다.
2. 공용 SP 변경이 필요하면 원본·현재 정의, dnSpy 호출 순서, 실제 업무키 읽기 전용 probe, EXE/웹 양쪽 replay fixture를 먼저 확보한다.
3. 웹의 동시작업 잠금·상세 오류·요청 멱등성은 가능하면 웹 전용 wrapper/API에 둔다. 최종 확정 부작용은 EXE와 동일한 권위 경로를 사용한다.
4. 목록 표시, 확정현황, 사전검사, 저장 직전 재검증, 저장 후 검증은 같은 계산 helper/SQL 계약을 사용한다.
5. 수량은 0.001 단위로 정규화한다. `abs(value) < 0.001`인 부동소수점 잡음은 0으로 표시·판정하고, 실제 `-0.001` 이하는 품목명·ProdKey·입고·출고·조정·부족수량을 표시한다.
6. EXE 저장 스냅샷과 웹 예상값을 한 컬럼이나 같은 라벨로 합치지 않는다.
7. 운영 DB 보정, 재고조정, 공용 SP 원복·재적용은 코드 배포와 읽기 전용 전후 대조 없이 실행하지 않는다.

## 필수 회귀 시나리오

- 입고 18 / 출고 18 / raw 계산값 `-0.000000...` → 표시 0, 음수 차단 안 함.
- 입고 18 / 출고 20 → 품목명과 부족 2를 표시하고 확정 차단.
- 부분확정 상태에서 확정출고와 미확정출고를 중복 차감하지 않음.
- `ProductStock.Stock` 저장값과 예상 잔량이 다르면 두 값과 기준 시점을 함께 표시.
- 웹 사전검사 통과 후 공용 SP 실패 → 성공 표시 금지, 전체 롤백.
- 공용 SP 원본/현재 시뮬레이션 결과가 다르면 배포 중단.
- 2025/2026 동일 `OrderWeek`가 있어도 선택 연도만 사용.
