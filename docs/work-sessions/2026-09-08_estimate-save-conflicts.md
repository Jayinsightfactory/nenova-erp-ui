## 이어받을 때 고정된 결정

- 서로 다른 페이지여도 공통 재고를 사용한다. 재고 게이트 제거·업체별 무조건 분리는 하지 않는다.
- 본인 저장의 지연 응답만 폐기한다. 실제 다른 사용자의 변경은 계속 차단한다.
- 저장 전 잠금 대기로 서버가 미저장을 명시한 경우만 최대 5회·총 15초 기다려 재시도한다.
- 실패 결과가 불분명하거나 실제 데이터 충돌인 경우 이 대기 경로로 자동 재실행하지 않는다.
- 기존 EZ Flower 차수 이동·게이트 복구와 별개 작업이다. 기존 복구를 재실행하지 않는다.
- 화면 검사는 1920×1080, 100% 기준. 운영 업무 저장 시험은 범위에서 제외한다.

### 1. 요청 — 반복 충돌 해결

**Q.** 견적서 관리페이지에서 수량 단가수정시 계속 충돌되는 원인을 해결해야해.

**A.** 별도 작업공간에서 하위 작업에 응답 순서, 서버 일관성, 잠금 대기 처리를 분할했다. 저장 전 확인 응답이 저장 후 기준값을 덮는 문제, 서버가 구 기준값과 새 원장을 섞어 읽는 문제, 상태 확인이 편집권 잠금을 보유한 채 원장을 기다리는 문제를 보강했다. 실제 외부 변경 보호와 기존 ERP 계산·쓰기 범위는 유지했다.

**결과.** [변경사항 #538](https://github.com/Jayinsightfactory/nenova-erp-ui/pull/538). 상세 근거는 [작업 보고서](../work-reports/2026-09-08_estimate-save-conflicts.md). 구현 a7f8a69, 기준 코드 85f29aa6.

## 검사 및 한계

- 견적 기능 검사, 편집 충돌 검사, 전체 ERP 계약, dnSpy 근거, 44개 계약 목록, 변경 API 2개 쓰기 보호 검사 통과.
- 운영용 빌드 103페이지 통과. 독립 검토 두 범위 모두 통과.
- 응답 순서 경쟁은 순수 coordinator/reducer 및 가상 query 실행 검사다. 실제 다중 사용자 운영 저장 시험으로 표현하지 않는다.
- 최근 4시간 견적 오류 원장 검색은 0건이었다. 개별 사용자의 모든 오류를 이번 원인으로 단정하지 않는다.
- 신규 운영 수량·단가·주문·재고·확정 데이터 변경, 게이트 해제, SQL 프로시저 변경 없음.
