## 이어받을 때 고정된 결정

- 계산식·금액·서버 검증 판정을 바꾸지 않는다. 상태와 버튼 표현을 개선한다.
- 원천 대조 전은 오류 확정이 아니다. 사용 가능은 동일 scope·화면지문·dirty/stale/취소 보호를 통과한 실제 verified에만 사용한다.
- 명시 추정·직접 오류·필수 금액 누락을 구분하며, 누락 영향액은 임의 0원이나 손실액으로 만들지 않는다.
- null 칸에 필드명·실제 원인을 보이게 하고, I/J/K와 합계에서 원천 항목·국가/품종을 연결한다. tooltip만으로 끝내지 않는다.
- DB 입력 부재와 승인 규칙 미매칭·운임 배분 대사 실패·웹 재평가 미지원은 다른 원인이다.
- profitTemplateDuty 변경은 새 진단 필드만 허용. 기존 조건/금액/null/판정/reason/입력 불변을 baseline 전체출력 대사로 검증한다.

### 1. 요청 — 수익률 상태 혼란과 버튼 불통일

**Q.** 계산 불가·검증 보류·추정 상태가 혼동되고 버튼 표현도 제각각이다.

**A.** 기존 gate는 전역 COVERAGE/STOCK/STALE 같은 제약을 여러 행에 전파한다. 이를 개별 국가 금액 오류로 단정하지 않고, 공통 제약은 별도 안내한다. 명시 추정은 추정 포함, 미실행은 원천 대조 전, 직접 오류는 확인 필요, 필수 금액 누락은 계산 불가로 구분한다. 분모 0은 충분한 영(0)·재고 근거가 있을 때 수익률 해당없음이며 무료 거래의 부재를 인증하지 않는다.

**결과.** `docs/plans/profit-report-status-toolbar-2026-11-02.md`, `docs/contracts/profit-report-status-toolbar.json`에 기준·부작용·회귀를 고정했다.

### 2. 요청 — 어느 숫자가 비었는지 화면에서 설명

**Q.** 계산 불가라고만 하지 말고 어떤 숫자가 비어 있어 계산할 수 없는지 보여 달라.

**A.** 실제 null 셀의 필드명·근거와 원천 확인 위치를 가시적으로 표시한다. 파생 매출원가/이익/수익률에는 기초·기말재고·통관비 등 실제 누락 원천을 연결하고, 합계에는 영향 국가·품종을 표시한다. 기존 숫자·입력칸·출력 수치는 보존한다.

**결과.** 독립 리뷰에서 K 셀의 느슨한 분모 판정과 합계 원인 연결 부족을 발견하여 보완 요청했고 수정 확인했다.

### 3. 요청 — 어떤 DB가 없는지 구체적으로 표시

**Q.** 어떤 DB 자료가 없는지 알려 달라.

**A.** 실제 설치 EXE FormStockView.GetData를 읽고, SQL SELECT-only로 2026/38·39·43 저장본 및43 canonical 파생 표를 점검했다. 원 저장본과 관세 파생 표의 단계가 다르므로 저장본 경고 수를 최종 UI 상태로 혼용하지 않는다.

43차 관측:

- 태국: 38입고행 중 승인 관세 정책 ProdKey 부재 14행. 매입/운임/환율/통화 연결은 존재한다. E/F 평균식·수량·기간·기존 비용 대사도 통과하지만 새 통관비가 null이라 후속 재평가가 보류된다.
- 중국: 98행 중01/02 범위96행. 정책 ProdKey 부재39행, 승인 규칙15행은 AWB 운임배분 conserved=false라 운임 적용값을 사용할 수 없다. 매입/환율/통화 누락으로 판정한 것이 아니다. 2행은 지원 반차수 밖이다. 기초는 product_cost 평가라 평균식 전용 관세 재평가가 지원되지 않고, 기말은 새 통관비 null에 종속된다.
- 에콰도르: 15입고행 중 정책 ProdKey 부재1행. 기초·기말은 no_stock 수량0으로 유지하며 통관비와 손익만 보류된다.
- 별도 raw presence 조회에서 WebCustomsWeekly의2026/43 저장행은0행이며 Category 표기 차이도 아니다. 테이블 자체 부재를 뜻하지 않는다. FreightCostDetail도 전체 부재가 아닌 현재 입고에서 사용할 실제 관세 스냅샷 근거 미확인으로 한정한다.

**결과.** 화면에는 정책 파일, WebCustomsWeekly.Customs1/2, FreightCostDetail.TariffKRW/SteamQty, WarehouseDetail.TPrice·WarehouseMaster.OrderNo, ProductStock.Stock, 저장본 평가메타를 실제 의미에 따라 안내한다. 43차 진단을 다른 차수에 하드코딩하지 않는다. SQL 쿼리 실패·재시도도 쓰기 없이 수행했다.

### 4. 검증 — 금액·동작 보존

**Q.** 표시를 바꾸다 계산이나 기존 업무가 달라지면 안 된다.

**A.** a6360410e 원 모듈과 baseline fixture는 import 경로 외 동일함을 직접 확인했다. 새 진단 키만 제거한 전체출력 비교31시나리오가 통과했다. 기존 페이지50개 버튼의 onClick/disabled AST 및 출력 실행 함수 해시를 비교했고, 상태/기존 검증gate/API 대상 테스트도 통과했다. null 비교 입력이 없을 때 가짜 불일치 진단을 만들지 않도록 보호했고, 품목별 평가에 평균 메타가 없는 것은 DB 누락이 아니라 평가 방식 차이라고 설명한다.

**결과.** 독립 타겟 검증 PASS. 이 기록은 full guard/build/CI/배포 성공을 대신하지 않는다.

## 미완료·다음 확인

### 검증 상태 갱신

- 부모 세션의 전체 `npm run verify:erp-change` 2차 exit0: 계약·dnSpy·UI·manifest·쓰기 가드·build 통과. origin/master 대비 명시 manifest174개/쓰기 가드0 API도 exit0이다.
- 이후 합계 K 설명만 좁게 보완했다. 개별 국가 K가 정상적으로 분모0이라 null인 경우를 합계 원가누락 원인으로 나열하지 않고, 합계 분자인 J와 분모 C/F의 실제 누락 행만 대상으로 삼는다. 합계 C+F=0도 원천 누락과 별도로 설명한다. 원 계산·금액은 변경하지 않았다.
- 보완 후 상태·금융parity31·50handler 타겟을 부모가 재통과했고 독립 상태 테스트도 재통과했다. 최종 build 재실행 및 PR/CI/배포/운영 검증은 결과 대기다.

- 전체 가드 첫 실행은 ProfitRangeOutput 소스 앵커 계약 1건에서 중단됐다. 테스트를 약화하지 않고 신규 스타일 props를 기존 year 앵커 뒤로 옮겨 수정했으며, 기존 UI 계약8개 및50개 동작 대사가 재통과했다. 전체 가드 재실행은 대기다.

- 최종 전체 ERP 가드·build·CI·PR/merge·Cafe24 배포 결과는 부모 세션이 진행/보고한다.
