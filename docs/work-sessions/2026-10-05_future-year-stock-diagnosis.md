## 고정된 결론

- 사진의 `2027 / 39-02`는 주문 존재의 증거가 아니라 재고 피벗 차수다.
- 운영 StockMaster에 미래 차수 한 건이 실제 존재한다: StockKey=288, OrderYear=2027, OrderWeek=39-02, OrderYearWeek=20273902.
- 생성 기록: 2026-09-28 16:38:43, CreateID=nenovaIC4. 계정 기록은 실제 사람 또는 메뉴 조작의 증거와 구별한다.
- 해당 차수 주문 API 원본은 0건. EXE 동일 피벗은 전재고 259행, 현재고 256행만 반환하며 주문·입고·출고 행은 없다.
- 현재고 256품목 중 255품목은 전재고와 수량이 같다. 나머지 한 품목과 전재고에만 있는 품목은 별도 영향 확인 없이 자동 보정하지 않는다.
- 실제 EXE CommonLogic.GetOrderWeek는 StockMaster를 연도·차수 내림차순으로 읽고, FormQuantityPivot.SetCombo는 첫 행을 기본 선택한다. 차수 콤보 본문은 OrderWeek만 표시하므로 `39-02`만 보고 연도를 구별하기 어렵다.
- 실제 운영 usp_StockCalculation 원문은 요청 연도·차수에 StockMaster가 없으면 생성하고, 이전 스냅샷 + 입고 - 확정출고 + 재고조정으로 ProductStock을 계산한다. 연도 경계를 넘어 이미 존재하는 후속 스냅샷도 재계산한다. 미래 차수 존재 자체를 오류로 차단하거나 삭제하면 안 된다.

## 질문 → 답변

### 1. 2027년 주문이 잘못 입력된 것 같은데 원인 확인

**Q.** 주문등록에 2027년이 보이는 이유를 찾아 달라.

**A.** OrderHistory의 2027년 검색 0건, 최근 30일 ORDER_WRITE 로그 86건 중 2027 payload 없음. 2026-09-01~2026-10-05 등록일 원본 9,029행 모두 2026년. 주문·입고·출고 View 기반 차수 목록은 최고 2026/43-02이며 2027이 없다. 이 확인만으로 전체 DB에 미래 차수가 없다고 결론 내리지 않았다.

### 2. EXE 사진: 2027/39-02에 전재고·현재고만 보임

**Q.** DB가 문제인지, 전재고·현재고로 표시된다.

**A.** 재고 차수 목록에서 2027/39-02 한 건과 생성 기록을 확인했다. 피벗 515행은 전재고 259 + 현재고 256이며, 사진의 네덜란드 운송료 952 등과 일치한다. 해당 연도·세부차수의 실제 주문은 0건이다. EXE의 기본 차수 선택 및 재고 조회 SQL로 표시 원인이 설명된다. DB 엔진 고장 증거는 없고 미래 재고 차수 데이터가 존재하는 문제다.

## 2026-10-05 추가 확인 — 재발 가능한 입력·생성 구조

**Q.** 어떻게 입력했길래 생성됐는가. 구조부터 문제가 있는 것 같다.

**A.** 설치 EXE의 FormOrderAdd와 FormWarehouseAdd를 dnSpy.Console로 다시 읽고, 운영 `usp_NenovaStockWeekGateEnter` 정의를 GET/SELECT로 확인했다. 저장 또는 SP 실행 테스트는 하지 않았다.

### 확인된 저장 코드의 허점

1. `FormOrderAdd` 신규 입력에서 `dteYear`와 `txtOrderWeek`를 따로 수정할 수 있다. 연도 기본값은 현재 날짜지만 사용자가 바꿀 수 있다.
2. `FormOrderAdd.CheckSave()`는 조건 없이 `return true;`다. 이것만으로 저장 전체에 검증이 전혀 없다고 말하지 않는다. 저장 본문에는 분배된 품목의 주문 0 변경 차단 등 다른 조건이 있으나, 해당 저장 경로에 미래 업무기간 승인 검증은 확인되지 않았다.
3. `btnSave_Click`는 `dtProduct.GetChanges(...)`가 NULL인 경우에도 OrderMaster 및 필요 시 ShipmentMaster를 저장한다. 상세 수량·OrderHistory는 변경된 품목이 있을 때만 기록하고, 신규 저장 성공 시 `uspStockCalculation(dteYear.Text, txtOrderWeek.Text, 0)`를 호출한다. 따라서 코드상 **수량 변경이 없어도 재고 차수를 생성할 수 있는 경로**가 있다. 이번 건의 실제 빈 OrderMaster 존재 여부나 실제 버튼 실행은 미확인이다.
4. 현재 운영 `usp_StockCalculation`은 입력 연도·차수에 StockMaster가 없으면 생성한다. 이전 스냅샷을 바탕으로 재고를 만들므로 그 차수에 주문·입고·출고가 없어도 재고 행이 존재할 수 있다.
5. 운영 gate는 연도 4자리·차수 NN-NN 형식 및 재고 계산 직렬 실행 소유권을 검증한다. 실제 달력의 허용 업무기간·미래 신규 차수 승인 여부를 확인하지 않는다. 이는 저장 형식 검증과 업무상 적합성 검증의 차이다.
6. 웹의 공통 `requireOrderYear`도 연도 존재·4자리·full 차수와 연도 일치를 검증한다. 형식이 올바른 미래 차수 입력을 이 함수 자체가 금지하지는 않는다. 웹 source별 다른 가드까지 모두 없다고 단정하지 않으며, 이번 생성의 웹 경로 증거도 없다.
7. EXE 피벗 기본 선택은 StockMaster의 최고 연도·차수다. 한 번 생성된 미래 차수가 이후 기본값으로 계속 등장할 수 있다.

### 가능한 흐름 — 원인 확정이 아닌 코드 기반 설명

연도 `2027` / 차수 `39-02` 입력 → 신규 저장 → 재고 계산 호출 → 없는 StockMaster 자동 생성 → 이전 재고 이월 → EXE 피벗에서 최고 연도 기본 선택.

이 흐름은 현재 주문 조회·이력이 0건인데 재고 차수만 존재하는 상태를 설명할 수 있다. 하지만 `nenovaIC4`가 실제로 이 버튼을 눌렀다고 단정하지 않는다. 입고·조정·다른 계산 호출도 후보로 남는다.

### 재발 방지 설계 방향 — 아직 구현하지 않음

- 연도·차수를 한 업무기간 선택지로 묶고 실제 달력 및 회사가 허용한 등록 기간을 검사한다.
- 먼 미래 신규 차수는 별도 권한·사유·명시 확인을 요구한다. 정상적인 연말 다음 연도 주문과 기존 후속연도 재계산까지 일괄 금지하지 않는다.
- 의도된 품목 수량 작업이 없는 신규 저장은 차단하거나 별도 초안 저장으로 구분한다.
- 재고 신규 차수 생성과 기존 차수 재계산을 구분한다. 공용 SP의 EXE·웹 호출 호환성과 정상 신규 주문·입고 경로를 검증한 뒤 변경한다.
- 기본 차수는 DB 최고 연도가 아니라 업무 달력의 기준 차수 또는 명시 선택값을 사용한다.
- 신규 StockMaster 생성 감사에 호출 화면·작업 종류·원본 업무키·요청 ID·사용자·선택 연도·차수·생성 사유를 남겨 계정만으로 실행 경로를 추정하는 상황을 없앤다.

추가로 사진 하단의 `거래처명/농장명 Is null or empty` 필터는 이름이 NULL인 재고 행을 남기고 업체·농장명이 있는 주문·입고·출고를 제외할 수 있다. 다만 이번 2027/39-02는 필터 없는 API 원본 자체에도 주문·입고·출고 행이 없다. 필터 해제만으로 미래 재고 차수 데이터 문제가 해결되는 것은 아니다.
