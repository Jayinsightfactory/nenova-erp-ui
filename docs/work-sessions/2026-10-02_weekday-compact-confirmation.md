# 주광 요일표 가독성 / 확정 선행 조건 재확인

## 사용자 합의와 범위

Q. 작업할 때 확정이면 풀고 수정 후 재확정하는가? 미확정이면 확정 후 처리하는가?

A. 기존 웹 weekday 저장은 기존 상세의 확정 상태를 보존하며 자동 확정 사이클을 돌리지 않는다.
확정 총량이 변하면 old-new 현재고·StockHistory·품목별 native 재계산은 수행한다.
신규 차수 이동 target 생성은 기존 확정 원천/확정 대상 Master 등 엄격 조건에서 새 확정 상세를
만드는 별도 예외다. 최초 기준 보관은 ERP 확정이 아니다.

Q. EXE 요일 변경은 확정된 상태여야 가능했던 것으로 기억한다. dnSpy로 위험을 확인해 달라.
메인차수 전체 확정돼야 견적서가 완전해야 한다.

A. 실제 CLI FormShipmentDistribution과 FormEstimateView를 재실행하고 고성능 독립 소스 검토.
선택 세부차수·CountryFlower에 확정행이 하나라도 있으면 rankType=A에서 저장버튼을
막고, 타 역할은 enable=false로 덮는 예외가 있다. 요일 저장 자체에는 '확정 필수' 검사가 없다.
EXE 인쇄는 각 정상출고행의 DetailFix=1/ViewOrder/정확 PeriodDay/양수 견적수량을 제한할 뿐,
전사 메인차수 모든 품종·세부차수의 전체 확정을 검사하는 조건이 없다.
따라서 '인쇄가 됨'과 '전체 물량 포함 최종 견적'은 다른 기준이다. 완전 확정 강제 인쇄 차단이나
자동 확정·해제·재확정은 이번 UI 요청으로 구현하지 않는다.

## 실제 확인과 남은 위험

- 운영 GET fix-status: 2026/39-01 176/176,39-02 822/822 양수 상세 확정.
- 40-01 1095 중330 확정으로 부분확정,40-02 4/4 확정,41-01/02 양수 출고 없음.
- 부분확정 메인차수에서 현재 인쇄는 미확정 정상출고를 제외하므로 전체처럼 보이는 부분 견적 위험.
- 웹 기존 상세 요일 변경 UPDATE가 대표 ShipmentDetail.ShipmentDtm을 변경하지 않는 경로 존재.
  날짜별 ShipmentDate와 EXE 업체표 대표 날짜가 달라질 가능성. 실제 View/운영 변경 테스트는 하지 않았음.
- 확정 유지 수량 저장은 EXE UI 작업 순서와 같다는 뜻이 아니라 기존 승인된 웹 방향별 저장 계약이다.
- 운영 재고 음수/상태 불일치가 기존 읽기 API에 표시됐지만 이 UI 작업이 발생시켰다고 단정하거나 보정하지 않음.

## UI 구현

- 수량 셀 중앙, 기본16px 진한 글씨. 합계·마감잔량·변경·견적을 압축 정렬한다.
- 반복되는 이월/미확정 설명은 accessible 내역 popup에 모으고 오류·초안·수동·불명 표시는 보존한다.
- 전후 차수 제목 옆 품종별 ERP 상세 확정 상태: 전체 거래처/모든 세부차수의 양수 분배 기준.

- 선택칸 내역 popup도 더 넓고 큰 글씨로 표시한다.
