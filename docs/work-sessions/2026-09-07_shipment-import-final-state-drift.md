# 36-01 카네이션 EXE/웹 출고분배 차이 원인

- 날짜: 2026-09-07
- 작업공간: `nenova-erp-ui`
- 상태: 원인 확인 및 재발 방지 구현·검증 완료, 운영 원장 보정은 미수행

## 사용자 의도

36-01 카네이션에서 `nenova.exe`와 웹/SQL 출고·재고 값이 왜 달라졌는지 실제 원장과 업로드 이력으로 확인하고, 양쪽이 함께 정상 동작하도록 재발 원인을 제거한다.

## 질문 → 답변 요약

1. **왜 다르게 저장되었나?**
   - `CARNATION Doncel`(ProdKey 389)은 엑셀 업로드 #50에서 양재동 5단, 미정화훼유통 2단을 포함해 저장됐다.
   - 뒤의 전체값 업로드 #60 파일에서 두 업체 열이 사라졌지만, 기존 판정은 현재 파일의 정확한 업체×품목 pair만 범위로 인정했다. 따라서 두 과거 분배 7단을 0으로 만들지 않고 남겼다.
   - 이후 EXE/개별 편집으로 희경·성남·여분·레바논 행도 변경되어, #60 최종값과 후속 웹 조정으로 계산한 130단보다 현재 `ViewShipment`가 6단 많은 136단이 됐다.
2. **SQL 변경 때문에 EXE가 잘못됐나?**
   - 단순 표시 차이가 아니라 공유 `ShipmentDetail` 최종값에 여러 저장 경로의 결과가 누적된 문제다. EXE와 웹은 같은 원장을 읽지만 업로드의 ‘이번 파일 범위’가 이전 행을 놓쳤다.

## 확인된 근거

- 2026 36-01 Doncel: 입고 135, 현재 출고 136, 잔량 -1.
- 업로드 #50: Doncel 14단, 양재동 5·미정화훼유통 2 포함.
- 업로드 #60: Doncel 최종 128단이지만 위 두 업체 pair 미포함.
- 붙여넣기 조정 8건 순변동: +2단.
- #60 + 후속 조정 기준 예상 130단, 현재 136단으로 +6단 차이.
- 정확한 차이: 성남 -1, 희경 +2, 여분 -3, 레바논 +1, 미정화 +2, 양재동 +5.

## 구현 결정

- 같은 `OrderYear + OrderWeek + 시트명`의 과거 성공 업로드에서 다룬 pair를 조회한다.
- 그 품목이 현재 같은 시트에도 존재하는 경우에만 과거 pair를 이번 최종값 범위에 포함한다.
- 현재 파일에서 업체 열이 사라졌다면 미입력 행으로 표시하고 분배를 0으로 맞춘다.
- 다른 시트·현재 시트에 없는 품목은 포함하지 않아 무관한 분배 삭제를 막는다.
- 기존 주문은 보존하며 `ShipmentDetail` 최종 분배만 기존 원자적 적용/사후검증 계약을 따른다.
