# 기초재고 전체 매칭 저장과 적용재고 원문 복사

| 항목 | 내용 |
|---|---|
| 날짜·화면 | 2026-10-12, 붙여넣기 주문등록 |
| 요청 | 기초재고 저장 전 전품목 매칭, 실제 분배 반영 후 원래 이름으로 복사, 배포까지 |
| ERP 부작용 | 기존 주문·분배 SQL 변경 없음. 기초재고는 기존 Favorite 저장 경로, 적용재고는 읽기·복사만 수행 |
| 작업 브랜치 | codex/stock-note-match-and-copy |
| 검증 | 신규 계약 2개, 저장/복사/작업복원 회귀, 1920×1080 및 1366×768 브라우저 |

## 고정된 결정

- 분배 ADD는 재고 감소, 분배 CANCEL은 재고 증가다. 원래 예시의 노비아 제거는 취소가 아닌 추가라는 사용자 정정을 적용한다.
- 문라이트1/노비아1/이케바나1에서 노비아1 추가 후 복사는 이케바나1/문라이트1이다. 복사 품명은 입력명, 정렬은 매칭된 DB ProdName 영문 A–Z다.
- 0인 품목만 제외하며 양수 소수는 유지한다. 음수·단위/매칭 미확인은 완료된 복사 값으로 만들지 않는다.
- 저장 클릭은 매칭 창을 열고, 모든 비제외 품목의 매칭과 수량 검증이 완료되면 한 번 저장한다. 취소·입력/차수 변경은 저장 의도를 폐기한다.
- 적용재고에는 실제 저장·검증된 분배 증감만 반영한다. 저장 전 예상 잔량/히스토리는 별도 참고 자료다.
- 성공 기록은 결과 닫기·실패·새로고침과 별도로 보존한다. 여러 업체 처리와 실패 후 재시도도 누적하며, 되돌린 작업은 무효화한다.

### 1. Q. 기초재고 입력 후 저장하면 매칭 창을 거쳐 100% 매칭 완료 후 저장되는 구조인가?

A. 기존에는 미매칭을 제외한 채 Favorite에 저장할 수 있었다. 저장 전 매칭 검토를 추가하고 잘못된 수량 줄도 조용히 빠지지 않도록 검증한다. 저장 후 재조회가 실패하면 이미 생성한 저장본을 다시 검증해 중복 생성하지 않는다. 키보드 검색/후보 선택, Escape 취소와 초점 복귀를 지원한다.

### 2. Q. 분배 작업 후 복사는 전산명이 아니라 원래 입력한 이름과 수량이어야 한다.

A. 원본 품명·단위·줄 구조를 유지하고 수량만 계산한다. 등록·분배 서버가 검증한 연도/차수 및 실제 분배 전후 수량을 확인하며, 단순 분석 초안·실패·롤백·되돌림·중복 결과를 적용하지 않는다. 명시 제외 줄은 같은 원문 제외 helper를 사용한다. 빈 줄은 정렬을 가로막지 않고 의미 있는 종류 헤더·구분자는 유지한다.

### 3. Q. 배포까지 진행해 달라.

A. 전체 ERP 계약·dnSpy 근거·변경 manifest/write guard·빌드 후 PR/병합/Cafe24 배포 및 운영 화면 확인까지 진행한다. 신규 API·ERP SQL·운영 데이터 보정은 없다. `docs/CODEX_SUBTASK_ORCHESTRATION.md`는 저장소에 없어 제공된 AGENTS 역할 경계로 하위 구현·독립 검토를 진행했다.

| 메뉴 기준 | 판정 | 근거 |
|---|---|---|
| 매칭·원문·실패 상태 | 적용 | 100% 저장, 실패/취소/재시도, 실제 성공만 복사하는 테스트 |
| 화면·키보드 | 적용 | 1920×1080 100%, 1366×768 가로 잘림 없음; Escape/Enter/후보 방향키·초점 복귀 |
| 페이지 스크롤 | 적용 | 기존 페이지 스크롤 보존; 매칭 모달·textarea는 허용된 예외 |
| 신규 메뉴/shell | 해당 없음 | 기존 페이지 내용만 수정 |
| ERP 원장 쓰기 변경 | 해당 없음 | SQL·저장 API 보존; 수량 증감은 기존 검증 결과 읽기 |

브라우저 fixture에서는 실제 운영 Favorite/ERP 쓰기를 하지 않는다. `outputs/`, `.next-delivery-smoke/`는 커밋 대상이 아니다. 배포 결과는 후속 기록으로 갱신한다.

### 운영 확인 후 초점 복귀 보완

기능 PR #1015는 master 4603a0118f06ddadf2a04b8a8d3f28f2e631f3a4로 병합되고 Cafe24 실행38200667865가 성공했다. 운영1920×1080에서 적용재고 복사 영역, 수량 불명확 원문의 매칭 창/저장 차단, Escape 닫기를 확인했다. 임시 원문은 비운 상태로 복원했으며 운영 Favorite·ERP 저장은 하지 않았다.

운영에서 Escape 후 BODY로 초점이 이동하는 문제가 추가 확인됐다. 자식 autoFocus가 실행된 뒤 모달 effect에서 이전 초점을 읽어 닫기 버튼 자신을 기록하는 것이 원인이다. 저장 클릭 시 호출 버튼을 먼저 기록하고 모달 닫기 때 그 버튼으로 복귀하도록 보완한다. 실제 페이지 브라우저 fixture에 호출 버튼 초점 복귀 검사를 추가한다. 이 보완도 전체 검사·빌드·CI·배포 뒤 재검증한다.

**최종 결과.** 초점 보완 [PR #1016](https://github.com/Jayinsightfactory/nenova-erp-ui/pull/1016), master `e8e4516b2874a4df5b23b8812d200023af9d40af`, [Cafe24 실행38202200142](https://github.com/Jayinsightfactory/nenova-erp-ui/actions/runs/38202200142) 성공. 전체 ERP 계약·dnSpy 근거·변경 manifest/write guard·빌드·CI·운영 hydration smoke 통과. 로컬 개발 서버 시작 지연으로 브라우저 검사를 운영 방식의 `next start` 서버에서 다시 실행해 성공했다. 1920×1080 및1366×768 fixture에서 미매칭 차단, Escape 취소/호출 버튼 복귀, 100% 한 번 저장, 원입력 보존, 오류/ERP 쓰기 없음 확인. 실제 모달 컴포넌트에서도 자식 autoFocus 이후 Escape 초점 복귀를 확인했다.

운영 로그인 브라우저1920×1080에서 적용재고 복사 영역·입력 화면 노출 및 가로 잘림 없음, 수량 불명확 임시 입력의 저장 차단·매칭 창·Escape 닫기·저장 버튼 초점 복귀(true)를 확인했다. 임시 원문/기준 입력을 비우고 viewport 설정을 해제했다. 운영 Favorite/ERP 저장을 실행하지 않았다. 적용재고 수량·정렬·0 제외·누적 및 롤백 검증은 격리 fixture와 순수 회귀로 확인했으며 운영 분배를 테스트 목적으로 실행하지 않았다. 이 최종 배포 결과 추가분은 로컬 세션 기록이다.
