## 이어받을 때 고정된 결정

- 계산 수량은 실제 원행 송이수로 정규화하고 단·박스는 원문 표시용으로 분리한다.
- 현재 Product 환산계수로 과거 송이수나 단가를 역산하지 않는다.
- 같은 품목의 기초+입고 가중평균을 쓰며, 기존 엑셀식 저장·확정본은 보존한다.
- 사용자 추가 확인: 기존 실제 중량/AWB 비용 배분은 유지하고 최종 원가만 송이당 환산한다. 비용을 새로 송이 비중으로 배분하거나 본표 총액에 맞춰 비례 확대·축소하지 않는다. 본표와 품목 금액 범위가 다르면 대사 차이로 표시한다.
- 역사 환율, 실제 원행 도착원가, 재고 환산, 양수 조정 취득원가가 불명확하면 수익률 정상 표시를 보류한다.
- 전수 조회와 원가 정상 판정은 다르다. 무활동 0원 품목은 양수원가 계산 성공 건수와 구별한다.

## 범위와 부작용

2026-10-29 기준 운영 PeriodDay의 현재 업무차수는 **44차(10/28~11/03)**다. 과거 1~43차와 진행 44차를 구분한다. 활성 입고는 1~44차 모두 존재하고 미래 입고는 없다. 계산 저장본은 1~43차 모두 존재한다. 현재본 도착원가에서 45차 이후 행은 이번 조회 시점 0건이다. 이전 문서에 나온 Import23의 연말 382행 격리 여부를 이 결과만으로 추정하지 않는다.

| 동작 | Warehouse/Product/Stock/Shipment/Estimate | WebProfitReport·계산본·도착원가 |
|---|---|---|
| 독립 검산 및 엑셀 비교 | SELECT만, 전부 보존 | SELECT만, refresh/저장 금지 |

실제 설치 EXE FormStockView를 dnSpy CLI로 재확인했다. ProductStock.Stock은 해당 차수 StockKey의 저장 잔량이고 OutUnit을 함께 표시한다. 입고·출고·조정으로 보고서에서 재고를 덮어쓰지 않는다. StockMaster.isFix를 임의 필터로 추가하지 않는다.

## 확보한 데이터와 미검증

- PeriodDay 365행, Product 3,534행, 2026 활성 입고 상세 22,786행.
- 2026 및 2025-52차 ProductStock 349,623행. 이는 모든 스냅샷 행 수이며 최신 기말 품목 수와 다르다.
- 2026 실제 재고조정 4,413행, 최신 계산본 메타 43차수, 현재 도착원가 10,210행.
- 최초 대형 SELECT batch는 장시간 대기로 취소했다. 순차 조회로 분리하고 45초 실제 Request.cancel 타이머를 적용했다.
- 최초 전체 출고 조인과 별도 축소 집계는 각각 45초 취소되었다. 후속 검증에서 같은 연도 활성 ShipmentMaster 키를 먼저 읽고, 검증된 키를 세부차수별 300개 이하로 나눠 상세를 조회했다. **확정 출고 원행 43,253행, 104개 세부차수, 105 SELECT, 14,174ms, 조회 오류 0건**을 확보했다. 45~50차는 헤더만 있고 해당 확정 상세는 0건이며 완료 차수로 계산하지 않는다. timeout 결과를 출고 0으로 바꾼 것이 아니다.
- SQL은 SELECT-only 검사와 execute/batch/Transaction.begin 차단을 적용했다. ERP·웹 DB 쓰기 및 자동 갱신 없음.
- `ProductStock`에는 당시 단위·송이수가 없고 `StockKey/ProdKey/Stock`만 있다. `ShipmentDetail`에는 SteamQuantity가 있지만 당시 SteamOf1Bunch/SteamOf1Box 컬럼은 없다. 역사 환산은 원행 송이/Out 비율 근거가 필요하다.

## 26~31차 실제 엑셀 수식 대조

사용자가 지정한 6개 파일을 수정하지 않고 XLSX 내부 XML에서 수식, shared-formula 속성, cached 값을 추출했다. 엑셀 실행 재계산은 하지 않았다.

콜롬비아 카네이션의 28~31차 본표 F8:

`(G8+H8)/SUMIF(구매현황!N:N,본표!B8,구매현황!D:D)*SUM(재고잔량!M30:M32)`

이는 품종 묶음의 구매 단수로 평균 도착원가를 만들고 묶음 재고단수에 곱하는 방식이다. 26·27차 F8은 수식이 아닌 직접 입력값이다. 31차 네덜란드 F12, 태국 F14, 중국 F15, 에콰도르 F16 역시 직접 금액이다. 이 직접 숫자의 상세 산식은 해당 셀만으로 확정할 수 없다.

|26|7,485|7,530|144,300|28,824|29,004|
|27|8,085|8,085|155,700|31,341|31,341|

27~31차 외화 총액은 일치하지만 단수는 28·29·31차에서 다르다. 26차는 외화도 180 차이가 난다. 이 단계는 품종 현재 분류 기준 대조이며 차이의 개별 원본행 귀속은 추가 확인 대상이다. 송이 원가로 변경한 웹과 엑셀의 차이를 모두 오류라고 볼 수 없으며 다음을 분리해야 한다.

1. 입력 수량/매입액 자체의 차이.
2. 스탠다드·미니 등의 단당 송이수를 섞은 평균과 송이 정규화 평균 차이.
3. 재고 평가를 품종 전체 평균으로 할지 품목별 취득원가로 할지의 정책 차이.
4. 엑셀 직접 입력·기초 이월·수기 반올림 차이.
5. 양수 재고조정 취득원가 불명, 환율·통관비·운임 누락 및 추정치.

### 국가별 원본 수식과 새 계산 정책의 차이

6개 원본의 첫 시트 `주차별 매출이익 보고서` E/F/I/K를 셀별로 확인했다. `shared` 수식의 자식 셀에 수식 텍스트가 없더라도 직접 입력으로 분류하지 않고 shared-formula 원점을 함께 읽었다.

| 국가·품종 | 26~31차 원본의 기말 F 산식 | 송이 기준 새 웹과의 차이 |
|---|---|---|
|콜롬비아 수국·카네이션·장미·루스커스·알스트로(F7:F11)|26~27차 직접 금액/빈칸,28~31차 `(G+H)/품종 구매수량×품종 잔량`|품종 전체 당차 평균 대신 같은 품목의 기초+입고 송이 가중평균. 포장단/판매단이 혼재한 수량 평균을 피함|
|베트남(F21)|28·29·31차 위 평균식,26·27·30차 직접 금액/빈칸|품목별 원가와 이월분을 구분.30차를 수식 확인 차수로 과장하지 않음|

|호주(F13)|6차수 모두 직접 금액|기초 이월·품목별 매입 근거를 SQL에서 연결하되 본표 직접값을 단순 평균식으로 단정하지 않음|
|태국(F14)|26~30차 빈칸/0,31차 직접1,149,859.79원|31차 F14 자체는 산식이 아닌 저장 숫자. 새 웹은 실제 품목 취득원가·송이로 재현 가능한 부분만 계산|

일반 국가 I는 `E+G+H−F`, K는 `J/C`다. 이스라엘·뉴질랜드·일본은 I=`E+G+H`, K=`J/(C+F)`라는 예외를 6개 파일 모두 유지한다. 단위 통일을 이유로 이 예외나 합계의 분모까지 바꾸지 않는다. 수식이 없는 직접 금액을 ‘엑셀이 틀렸다’고 판정하지 않으며, 원본 엑셀 재계산은 이번 읽기 검증에서 수행하지 않았다.

## 완료 판정의 한계

입고 1~44차 원천 분류, 확정 출고 원행 전수 조회, 엑셀 26~31차 수식 확인은 완료했다. 새 웹 계산 결과 전체차수 대조, 역사 재고 환산 충돌 해소, 원가 누락 해결, 브라우저·배포 검증은 이 문서 작성 시점 미완료다. 누락 품목을 제외한 부분금액을 전체 정상 수익률로 제시하지 않는다. 원천 분류·엑셀 비교는 생산 원가 계산 함수를 import하지 않았다. 후속 웹 엔진 실행 검증은 이 독립 검산과 구별해서 기록한다.

## 최종 코드 재검증 — 원장 무수정

명시0 수수료 보존·기본비용 출처 표시·무활동 구분까지 반영한 코드로 다시 실행했다. 2026년 1~43차와 진행44차에 필요한 **90개 세부차수 비용 근거, 2,431 SELECT, 41,353ms, 오류0, 쓰기0**을 재수집했다. 물량 원천은 앞서 확보한 자료를 그대로 재사용했다.

## 사용자 Q&A

### 1. 송이인지 단인지 계산기준을 통일해 달라
**Q.** DB는 수정하지 말고 웹 원가 계산은 송이, 표시는 단·박스로 통일하고 엑셀과 비교·전체차수 검증 후 배포.

**A.** 원행 송이수와 정확한 WdetailKey별 도착원가 금액을 사용한다. 기존 단가×서로 다른 단위 Out수량을 새 원가에 사용하지 않는다. 기초+입고 품목별 평균과 기존 엑셀 품종묶음 평균의 정책 차이를 구별한다. 송이 미정 중량상품은 임의1송이로 만들지 않는다. 기존 보고서/ERP 저장본은 그대로다.
