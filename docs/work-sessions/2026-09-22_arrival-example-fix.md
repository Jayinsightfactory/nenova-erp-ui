## 고정 결정
- 정상 누적 과거 시트 저장 정책 유지. 명시 예시 시트만 제외한다.
- 업로드 후 실제 저장행 중 파일명 차수 우선, 없으면 최신 차수로 조회한다.
- 37-2/37-02는 동일 차수, 연도는 필수.
- 원본 엑셀은 수정하지 않는다. 운영 파일 전체 재업로드 금지.
- 배포 후 확인된 예시 32행만 비활성화, 감사 기록으로 복구 가능하게 한다.

### 1. 업로드했는데 조회되지 않음
**Q.** 37-2 NL 원가자료 업로드 후 도착원가가 조회되지 않는 이유.
**A.** 저장 #23은 성공했으나 이전 화면 필터를 유지. 차수 문자열 정확 비교도 37-02/37-2 불일치를 유발. 예시 시트가 파일명 차수로 오인되어 #23 16행, 자동 #22에도 16행 혼입.

### 2. 작업 처리
**Q.** 작업처리해줘.
**A.** 공통 예시 제외 정책, 업로드 성공 조회 scope, 목록/품종/누락 조회 차수 predicate 공유 구현. 실제 파일은 2032→2016행, 37-2는 69→53행으로 정상 시트만 유지. ERP 계약·dnSpy·manifest·쓰기 가드·빌드 통과. 배포/보정/브라우저 결과는 후속 기록.

### 3. 완료 결과
- PR726 및 요청 형식 보완 PR728 모두 CI/병합/배포 완료. 최종 버전51223578.
- 운영 #22/#23 예시32행만 비활성화. 각 행 BeforeJson/사유 감사 이력32건으로 복구 가능. 정상행 전체 내용 해시 동일.
- 37-2 정상53행, 38-2 정상18행 보존. 1920×1080 브라우저에서 37-02로도 정상 원가 조회. NL 화면55행=정상53+기존 원가 미업로드 안내2.
- 실제 업로드 재실행은 역사 자료 덮어쓰기 방지를 위해 하지 않음. 업로드 화면전환은 실제 handler 격리 실행 및 API wire 형식 테스트로 검증.
- 원본 소수점 원가와 DB 기존 정수 원가는 차이가 있으나 원 단위 반올림 표시 기준53행 모두 일치. 이번 범위에서 정밀도 저장 정책은 미변경.
- `.tmp/repair-arrival-example.cjs`는 이 사건 전용 로컬 보정 도구로 미커밋. 기본 읽기 전용, 적용하려면 배포 확인 환경값과 --apply 필요. 재실행은 대상32행 없음으로 중단.

### 4. Aisha 검색·잘못된 표시 원인 (진단만, 미수정)
**Q.** 네덜란드 원가 업로드에서 aisha 검색이 안 되고 이상한 품목이 표시됨.
**A.** 운영 Product에는 `Lily Oriental Double Roselily Aisha 2+` #3170이 활성 상태로 존재. #23 37-2 원본62행(ArrivalLineKey42422)은 원본명이 정확하지만 ProdKey1211 `ROSE`로 저장. 같은 NL 원본의 현재본11행도 동일 오매칭. 다른 중국 Aisha #2751과는 별개다.
- 실제 matchProduct 함수를 격리 실행하여 ROSE→정확한 백합 순서 후보에서 빈 mappings/로컬 mappings 모두 #1211 반환 재현.
- 포함문자열 점수0.92와 품종 보너스0.08이 정확일치1점과 동점. Roselily를 장미로 해석하는 품종 추론이 ROSE에 보너스를 주고, `>`만 비교해 먼저 나온 ROSE를 유지한다.
- 운영 매칭/원가 데이터나 코드는 아직 변경하지 않음. 후속 수정은 정확일치 우선과 품종 경계 인식, 동점/모호 후보 자동저장 방지 및 배포 후 오매칭 행 이력 보정 검토.
