## 고정 결정

- 원본 시트 `39차`와 `39차-2`를 별도 결산으로 저장한다. `39-2차`는 후자의 표기 변형이다.
- canonical `39-2`는 NVARCHAR(4)에 그대로 저장한다. 하위 기간 1..9, 대차수 1..99. 잘못된 값은 잘라내지 않는다.
- 연도+호텔+전체 기간으로 preview/선택/snapshot/저장/수기원가·품목 연결 보존을 처리한다.
- ERP 조회 참조에서만 baseMajor 39를 파생하며 웹 시트 -2를 ERP 39-02로 추정하지 않는다.
- 가격·합계 오류를 숨기지 않는다. 정상인 39-2만 선택 저장 가능하며 기존 39차 원본 합계 불일치는 유지한다.
- 같은 기간 표기 중복은 계속 차단한다. 자동 저장이나 운영 원본 보정은 하지 않는다.

### 1. 요청 — 시트 기반 차수 구분

**Q.** 신라호텔 손익 업로드에서 39-2차를 인식하지 못하니 시트 기반으로 구분해 달라.

**A.** 실제 첨부 파일에는 `39차`(9월 29일)와 `39차-2`(10월 2일)가 있다. 기존 파서가 두 시트를 39로 묶어 호접 행의 보존 충돌을 유발했다. 충돌 방어는 유지하고 전체 기간 키를 공통 helper로 보존하도록 수정했다.

**결과.** 실제 원본 파싱은 총 40개 기간. 39-2는 2개 품목, 매입 299,928원, 매출 389,200원, 이익 89,272원으로 검증 통과. 기존 39차의 합계 불일치는 별개로 유지한다.

## 읽기 근거

- dnSpy CLI FormOrderAdd 실행 성공, OrderYear+OrderWeek 업무키 확인. 웹 결산과 EXE 주문/분배는 별도다.
- 운영 SELECT: MajorWeek NVARCHAR(4). 활성 기존 기간은 01..39. 신라 2026년 39차 PnlKey60/10행/매출28,636,904. 이번 작업에서 쓰지 않았다.
- Chrome 운영 화면에서 39차 11행과 39차-2 4행이 같은 39차 호접으로 충돌한 안내를 확인했다.
- 상세 설계: `docs/work-plans/2026-10-05-shilla-sheet-period.md`.

## 검증 및 모델 역할

- 설계/최종 검토 gpt-6.1-sol xhigh. 지정 gpt-5.6-sol 용량 제한으로 대체.
- 확정 구현 gpt-6-sol high. 지정 gpt-5.6-terra 도구 미지원으로 대체.
- 하위 작업 P0_LOCAL만, 외부·DB 쓰기 없음. 메인이 입력·의존성·읽기 근거 사전 준비.
- helper/parser/선택/트랜잭션 fake DB/단가·매칭 scope/표시·Excel 회귀 추가. 39-2-only 신규/재업로드, 다른 연도·호텔·기존39 보존, 실패 rollback 검사.
- 빌드, dnSpy evidence, manifest, ERP write guard, UI layout 및 전체 ERP 계약 검사 통과. 최종 경계값 보강 후 전체 ERP 계약 검사 재실행도 통과했다.
- 최종 리뷰: 소수점·유니코드 하이픈 등 잘못된 시트 기간을 정상 기간으로 잘라 병합하지 않도록 차단했다. 혼합 39/39-2 연쇄 매칭에서 NVARCHAR(4) 전체 키와 중간 실패 전체 롤백 회귀도 통과했다.
