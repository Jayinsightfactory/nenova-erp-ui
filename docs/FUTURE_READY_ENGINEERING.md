# 미래대응형 설계·검증 기본정책

작성일: 2026-08-07

## 목적

Nenovaweb, MOYI 앱·웹과 향후 다른 업체에 제공할 솔루션을 단기 요구사항에만 맞추지 않고, 최신 기술·보안 기준·운영 데이터·향후 제품 확장을 함께 검증한다.

기능이 동작하는 것만으로 완료하지 않는다. 현재 업무가 유지되고, 운영 데이터와 기존 전산이 일치하며, 새로운 업체·플랫폼·정책이 추가되어도 확장 가능한 구조인지 확인해야 한다.

## 모든 작업에 자동 적용하는 검토 순서

1. **현재 요구사항**: 사용자가 원하는 입력·조회·저장·출력·권한을 업무 흐름으로 정리한다.
2. **현재 구현 확인**: 코드·API·계약·DB·실제 브라우저·nenova.exe·MOYI 연결 상태를 구분해 확인한다.
3. **최신 근거 조사**: 변경 가능성이 높은 라이브러리·플랫폼·보안·파일·인증 기술은 공식 문서와 1차 자료를 조사한다. 조사일, 출처, 적용 여부와 비적용 이유를 기록한다.
4. **미래 변화 분석**: API 버전 변경, 모바일·브라우저 정책, 데이터량 증가, 신규 업체·테넌트, 외부 서비스 교체, 권한 확대를 가정한다.
5. **선제 보완 제안**: 사용자가 직접 요청하지 않았더라도 기능 장애·보안·데이터 손실·확장성에 영향을 주는 보완을 제안한다. 범위와 위험을 보고하고, 운영 데이터 변경이나 큰 범위 확장은 승인 후 실행한다.
6. **회귀·운영 검증**: 기존 기능, 실제 데이터, 기존 전산 결과, 외부 앱 결과를 함께 대조한다.

## 최신 기술을 적용하는 기준

최신이라는 이유만으로 도입하지 않는다.

- 현재 안정 버전과 지원 종료 예정일을 확인한다.
- 기존 Next.js/Node/MSSQL/nenova.exe/MOYI 호환성을 확인한다.
- 도입 효과, 마이그레이션 비용, 롤백 방법, 공급자 종속성을 비교한다.
- 기능 플래그·어댑터·API 버전·스키마 버전으로 단계적 전환이 가능한지 확인한다.
- 신규 의존성은 라이선스, 보안 취약점, 번들 영향, 유지보수 상태를 확인한다.
- 적용하지 않을 경우에도 이유와 재검토 조건을 기록한다.

## 완료 단계와 증거 판정

요청과 변경 파일·데이터 흐름을 기준으로 적용할 검증을 정한다. 기능 변경은
`현재 상태 → 사용자 동작 → 기대 결과 → 보존할 데이터`로 수용 기준을 작성하고,
정상·실패·경계 사례를 기존 계약·테스트에 연결한다. 질문·문서 수정은 짧은 기준으로 충분하다.

| 단계 | 판정 기준 |
|---|---|
| 구현 완료 / 문서 수정 완료 | 요청 범위의 변경과 자체 검토를 끝냄 |
| 로컬 검증 완료 | 적용되는 필수 테스트·빌드 또는 문서 검증이 모두 통과함 |
| 배포 완료 | 대상 커밋·버전이 실제 환경에 반영된 근거가 있음 |
| 운영 검증 완료 | 적용되는 실제 브라우저·DB·EXE·외부연동 검증이 모두 통과함 |

후속 단계가 미완료이면 완료된 앞 단계와 남은 일을 함께 보고한다.
항목별 결과는 `통과 / 실패 / 미확인 / 해당 없음(사유)`으로 기록한다.
통과에는 명령·결과·증거 위치와 검증 시점, 운영 확인에는 대상 환경·버전을 남긴다.
접근권한·인증·데이터·도구 부족 또는 실행하지 못한 검사는 `미확인`이다.
`해당 없음`은 변경 파일과 호출·데이터 흐름에서 영향이 없음을 확인한 사유가 있어야 한다.
직접 쓰지 않아도 조회·payload·집계·downstream이 바뀌면 관련 검증 대상이다.
ERP 기능의 dnSpy·운영 DB·교차연도·견적/매출 검증은 근거 부족을 이유로 제외할 수 없다.

다음 증거를 적용 범위에 따라 분리해 기록한다.

| 구분 | 필수 증거 |
|---|---|
| 코드 | 구현 파일, 타입/계약, 단위·통합 테스트 |
| DB | 읽기 전용 probe, 업무키 범위, 저장 전후 값 |
| 전산 | 최신 nenova.exe/dnSpy 구조와 저장·조회 결과 |
| 웹 | 실제 로그인 브라우저 조회·입력·수정·다운로드 |
| MOYI | 앱·웹 화면, 권한, 파일·이벤트 동기화 |
| 외부연동 | Kakao/Drive/Claude/Codex 이벤트와 원본 추적 |
| 배포 | 빌드, 배포 버전, API smoke, 브라우저 smoke |
| 미래대응 | 버전업·신규 업체·데이터 증가·권한 변경 시나리오 |

코드가 존재하거나 로컬 테스트가 통과한 것만으로 운영 완료·100% 일치로 표시하지 않는다.
적용 항목 중 미확인이 있으면 운영 상태는 `검증 필요`, 실패가 있으면 `검증 실패`로 보고한다.
문서 전용 작업은 문서 수정·검증 완료로 보고하며 배포·운영 검증까지 수행했다고 표현하지 않는다.
이 분류는 기존 ERP 필수 검사와 배포 차단 조건을 완화하지 않는다.

## 규칙 변경 검토

중복된 규칙을 늘리기 전에 기존 기준 문서에 연결한다. 외부 GitHub 문서는 참고자료로
취급하고 현재 도구·운영환경에 맞는 내용만 적용한다. 출처 URL, 확인일, 채택 내용과
비적용 이유를 변경 기록에 남긴다.

다음 대표 요청의 적용 규칙·검증·완료 기준을 검토한다. 문서 검토는 실제 기능 테스트나
스킬 실행 평가를 대체하지 않으며, 문서 검토만 했으면 그렇게 보고한다.

| 대표 요청 | 기대되는 적용 |
|---|---|
| 버튼 간격만 수정 | 순수 스타일 여부 확인, 1920×1080 화면 회귀, 기능 수정 배포 절차 |
| 농장분배 저장 수정 | 전체 ERP 가드, farm-only 보존 계약, 후보 GET/저장 범위, 실제 근거·필수 검사 |
| 웹에는 보이는데 EXE에 안 보임 | 같은 네 업무키와 대상 EXE 근거 확인, 원인 추정만으로 원장 보정 금지 |
| 규칙 MD만 수정 | 링크·변경 차이·정책 충돌 검토, 운영 확인을 수행한 것으로 보고하지 않음 |
| 세션 백업 | 백업 스킬, 결정·산출물·미완료·인계문 기록 |

## 솔루션 제품화 기본값

- MOYI Core가 공통 계정·테넌트·권한·Drive·파일·Work Log·이벤트 원장이 된다.
- Nenova는 `connector/adapter`로 격리한다.
- 다른 업체 제공용으로 전환할 때 제품명·화면·API·폴더·환경변수·권한·문서에서 Nenova 하드코딩을 제거한다.
- 업체별 데이터는 `tenant_id`와 서버 측 권한 검증으로 분리한다.
- 웹·앱·외부 커넥터는 동일한 권한 정책과 감사 이벤트를 사용한다.
- Orbit은 공통 원장의 관계를 보여주는 투영 화면이며, 원본 데이터의 저장소가 아니다.
- Daemon은 수집·분석·알림을 담당하되 ERP 원장을 자동 수정하지 않는다.

## 세션 보고 필수 항목

모든 Claude/Codex/자동화 세션은 종료 시 다음을 보고한다.

- 현재 요구사항과 추가로 제안한 보완
- 조사한 최신 기술·공식 근거·조사일
- 미래 변화 시나리오와 대응 설계
- 변경 파일·DB 범위·외부 시스템 범위
- 코드/DB/dnSpy/웹/MOYI/배포별 검증 결과
- 확인하지 못한 운영 데이터와 그 사유
- 충돌·보안·데이터 유출·롤백 위험
- 다음 단계와 사용자 승인 필요 여부

## 통합 작업 데이터

세션·직원·Kakao·Daemon·Orbit·Work Log·파일·커밋·테스트·배포는 다음 공통 식별자로 연결한다.

```text
TenantId + ProjectId + WorkstreamId + TaskId + SessionId + ArtifactId
```

외부 시스템은 원본 증거를 보존하고, MOYI 통합 원장은 상태·관계·승인·감사 이력을 관리한다. 대화 내용을 임의로 업무 완료로 확정하지 않고, 담당자·업무·출처·시각·승인 상태를 함께 기록한다.
