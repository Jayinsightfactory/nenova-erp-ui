## 데이터 계약

업무키는 OrderYear + 전체 OrderWeek + CustKey + ProdKey, 실제 상세 PK는 SdetailKey.
요청은 작업 UUID, 사유, 대상 거래처, 각 year/week/product의 완전한 조회 기준 날짜/수량,
변경할 날짜별 최종 OutUnit 수량을 갖는다. 0은 취소다. 누락 날짜는 기존값 보존이다.
조회 응답은 상세 단가·환산수량·금액·확정 상태, 마스터 상태 및 상품 단위환산 기준을
포함한 서버 digest를 발급한다. 저장은 같은 정규화 기준으로 digest를 재검증한다.
digest가 없는 오래된 조회 자료는 다시 불러오기 전 저장하지 않는다.
표 합계가 여러 상세를 포함하면 임의 분배하지 않고 구체적 오류로 차단한다.
기존 상세가 없는 양수 등록은 기존 신규 분배 코어와 활성 주문/EXE 조인 규칙을 만족해야
한다. 구현되지 않은 신규·이동 경로는 성공으로 표시하거나 조용히 일부 적용하지 않는다.
이전/다음 차수 사이 편집도 한 거래이며 교차연도는 명시 연도 및 달력 검증을 요구한다.
조회 기준과 저장 기준이 다르면 409, 모든 앞선 변경도 rollback한다.

## 기존 전산 이력 활용

설치 EXE `FormShipmentHistory`를 dnSpy CLI로 다시 확인했다.
`ShipmentHistory → ShipmentDetail → ShipmentMaster`로 연도/차수/업체/품목을 연결하고
ChangeDtm·ChangeID·ShipmentDtm·ChangeType·BeforeValue·AfterValue·Descr를 표시한다.
운영 SELECT API의 CustKey=533 /2026 37~39 /ProdKey866·3124에서 기존 이력 13건을
확인했다. 예: 38-02의 2026-09-20 출고수량 13→0, 39-02의 2026-09-27 0→7.
따라서 기존 이력은 버리거나 웹 새 테이블로 대체하지 않는다.
웹 저장도 같은 transaction에 날짜별 ShipmentHistory를 기록해 EXE에서 조회되게 한다.
웹 전용 감사는 UUID 멱등성, 담당자 사유, 여러 날짜/차수의 원자 작업 연결 및
삭제 후에도 남는 완전한 전후 스냅샷을 보완한다. 근거 없이 두 출처를 추정 합치지 않는다.

기존 EXE 조회는 살아 있는 상세·마스터에 조인하므로, 완전 취소로 상세행을 삭제하면
ShipmentHistory 행 자체가 남아 있어도 EXE 이력 화면에서는 조회되지 않을 수 있다.
이는 기존 조회의 한계이며, 웹 전용 감사가 삭제 전 업무키와 전후 값을 별도로 보존한다.
삭제된 상세키는 잔존 이력 및 KeyNumbering 상한까지 포함해 다시 사용하지 않아야 한다.

## 검증 진행 상태

순수 정책·클라이언트 검사와 1920×1080/100%의 격리 브라우저 fixture를 실행했다.
이 결과만으로 운영 SQL 호환성이나 배포 완료를 인정하지 않는다.
독립 검토에서 상세키 재사용, 날짜별 환산 반올림, 주문 생성 차단,
금액·확정·환산 기준의 stale 검증을 추가 확인 대상으로 지정했다.
`npm run test:weekday-distribution-sql`은 지정된 loopback Docker SQL에만 연결하며,
운영 수량 변경을 검증 수단으로 사용하지 않는다. 최종 재검토와 배포 결과는 별도로 기록한다.

실제 기존 38-02 날짜가 일요일인 경우가 있다. 현재 원장의 업무키를 달력의 01로
자동 변경하지 않는다. 기존 날짜 수정/취소는 실제 날짜 PK·정확 timestamp·전체 조회
스냅샷으로 검증하고, 새 날짜 배정은 정의된 01 목~일/02 월~수 달력을 적용한다.

## 날짜별 견적 인쇄와 가격 보존

선택 요일이 여러 개면 날짜별 단일 범위로 읽고, 각 날짜의 수량·금액을 별도 견적서로
생성한다. 공통 EXE-compatible HTML의 9pt 본문·8pt 품목·16pt 제목 및 여백은 유지한다.
한 날짜라도 응답 범위·금액이 불완전하면 전체 미리보기를 차단한다. 자료 없는 요일은
가짜 0 견적을 만들지 않고 안내한다. 초안은 출력에 포함하지 않는다.

2026-10-01 최종 독립 검토에서 날짜 단가와 상세 단가가 다른 경우 수량 이동만으로
금액이 바뀔 수 있음, 잘못된 원천 단가가 유일 단가 판정에서 제외될 수 있음,
재고 무변경 검증에서 원본 정밀도를 잃을 수 있음을 발견했다.
가격 변경은 이번 요청 범위가 아니므로 단가가 모호하거나 이동 전후 금액이 달라지는
경로는 차단하고, 실제 재고 쓰기가 없으면 원본 정밀도를 보존하는 회귀 검증을 추가한다.
이 항목들과 격리 SQL adversarial 검사·최종 재검토가 통과하기 전 배포 완료로 보고하지 않는다.

## 기존 메뉴의 이력 번호 보호

최종 검토에서 주광 완전 취소 후 기존 adjust/distribute/stock-status/import의 활성
상세 MAX+1 allocator가 삭제된 최고 SdetailKey를 재사용할 수 있음을 재현했다.
기존 EXE History→Detail→Master 조인은 이전 이력을 다른 업체·품목에 잘못 연결한다.
따라서 네 로컬 allocator의 ShipmentDetail/SdetailKey 분기만 공유 이력 보호 helper로
위임한다. 다른 테이블 채번과 각 메뉴의 주문·분배·재고·확정 동작은 그대로 유지한다.
완전 취소→각 기존 경로 신규 상세 생성→기존 키 미재사용 및 네이티브 이력 오귀속 없음의
교차 경로 실행형 검증이 배포 조건이다. 이것은 이미 잘못 귀속된 운영 이력 보정이 아니며,
과거 운영 자료를 자동 수정하지 않는다.
