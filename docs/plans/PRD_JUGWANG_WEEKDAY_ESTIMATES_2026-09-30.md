# PRD — 주광 요일별 출고·견적 관리

- 작성일: 2026-09-30
- 상태: 메뉴 진입 및 업로드 검토·수동 배분 초안·읽기 전용 전산 대조 구현 / ERP 적용·EXE 견적 인쇄·영속 작업이력은 차단된 후속 범위
- 요청 근거: `주광 요일별 출고량.xlsx` 및 현재 대화
- 범위: Nenovaweb의 주광 기본·타 거래처 선택형 요일별 계획 업무. 구현 기준은 `docs/plans/weekday-estimate-change-criteria.md`; 화면 초안은 메모리만 사용하고 ERP 원장을 변경하지 않는다.

## 1. 제품 목표

### 최신 합의 (2026-09-30, 아래의 초기 제안보다 우선)

- 업무 대차수는 **목→금→토→일→월→화→수**의 7일 묶음이다. 콜롬비아 기준 01은 목~일, 02는 이어지는 월~수다. 다른 국가의 공급 일정은 별도 설정이며 이 규칙을 모든 국가에 강제하지 않는다.
- 날짜는 ISO 주차 추정이 아니라 `PeriodDay`의 해당 대차수 목요일을 기준으로 연결한다. 월~수 날짜의 PeriodDay 주차가 다음 번호여도 견적 대차수는 원래 묶음으로 유지한다.
- **견적 차수 / 실제 출고일 / 실제 사용 입고차수**를 독립 필드로 관리한다. 39-01 입고를 38차에 앞당겨 출고할 수 있다. 입고차수를 견적 차수로 강제하거나 원 입고 차수를 변경하지 않는다.
- 37·38·39차는 동시에 연결해서 조회한다. 기준 38차는 요일별 `출고수량·잔량·변경량`과 합계, 앞뒤 차수는 이월/선출고 연결 및 차이 요약을 표시하고 펼쳐 동일 상세를 본다. 조회 창 밖의 연결도 버리지 않는다.
- 38차 전체 견적과 단일/부분/전체 요일별 **각각의** 견적이 필요하다. 복수 요일 선택은 요일별 별도 문서를 만들며 대차수 합산 견적과 구분한다.
- 화→월 이동은 이전/이후 일자·수량을 하나의 이동 ID로 묶는다. 38차 화→39차 목 이동은 원차수 감소와 새차수 증가를 같은 이동 이벤트 및 트랜잭션으로 처리한다. 단순 삭제+추가 이력만으로 끊어 보여주지 않는다.
- 변경 시 담당자·시간·사유·변경 전후 날짜/차수/분배수량·재고수량 전후값과 증감량·확정 전후·ERP 적용 결과를 별도 불변 이벤트에 남긴다. 직접 재고수정과 분배 변경에 따른 재고증감을 구분한다. 화면에만 저장한 초안을 적용 이력으로 표시하지 않는다.
- dnSpy 확인: EXE 분배 수량 편집은 기존 ShipmentDate를 지우고 기본 출고일로 재생성한다. 웹에서 이 동작을 제거했다고 주장하지 않는다. 확정된 요일별 웹 기준본과 실제 ERP 날짜분포를 재조회하여 초기화/외부 수정을 감지하고 작업자에게 차이를 표시한다.
- 최신 정정: 사용자가 변경한 것은 **입고 원천이 아니라 재고수량**이다. 입고 원천 변경/재배정 입력은 이번 범위에서 제외한다. 입고 차수는 읽기 전용 참고로 유지한다. 기존 `ShipmentFarm`은 FarmKey·수량·SdetailKey만 저장하므로 특정 입고차수 사용을 증명하지 못한다. 농장명 또는 같은 수량으로 사용 입고차수를 추정하지 않는다.
- 잔량은 입고−주광분배라는 단순 차이를 실제 재고로 표시하지 않는다. 전체 거래처 출고·이월·조정·확정상태를 포함한 ERP 재고와 웹 계획 변경 후 예상량을 분리한다. 재고수정 이력은 실제 재고 전후값·증감량을 표시하고, 근거가 없으면 `미확인`이다. 수량 변경만으로 입고기록을 수정하지 않는다.

#### 화면 골격

| 품목 / 사용 입고차수 | 38-01 목 | 금 | 토 | 일 | 38-02 월 | 화 | 수 | 38차 합계 |
|---|---|---|---|---|---|---|---|---|
| 원본 품목 + 원천 39-01 | 수량/잔량/변경 | 동일 | 동일 | 동일 | 동일 | 동일 | 동일 | 수량/차이 |

위에는 `37차 ← 38차 → 39차` 연결 요약, 옆에는 선택행의 이동 이력(예: `38-02 화 10 → 39-01 목 10, 사용입고 39-01 유지`)을 표시한다. 원장 차수와 권장 요일 세부차수가 다르면 실제 원장값을 유지하면서 별도 표시한다.

#### 저장·확정 로직

1. 원본/초안/기준 확정/ERP 반영/인쇄를 별도 상태로 둔다. 기준 확정은 출고 ERP 확정과 다르다.
2. 변경 계획을 전산 현재 스냅샷과 비교하고 날짜별 출고합=Detail.OutQuantity 및 OutUnit/EstUnit 환산을 검증한다.
3. 확정행은 기존 EXE/SP 사이클을 따른다: 영향 차수와 후속 확정 범위를 확인 → 역순 확정취소 → 원자적 분배·날짜·이력 저장 → 재고 재계산 → 순서대로 재확정 → 사후대조. 직접 isFix 토글 및 자동 재고보정 금지. 입고 원천은 변경하지 않는다.
4. 같은 총량의 요일 이동은 총 출고/주문량을 보존한다. 다른 견적 차수 이동은 차수별 분배를 이동하되 기존 주문은 보존하고, 도착 차수 주문이 없으면 기존 양수 주문 생성 계약을 적용한다. 재고 변동은 전산 재계산 결과와 직접 재고수정 이력을 구분한다.
5. 동시수정·중복요청·중간실패는 요청키/기준 버전으로 검증한다. 외부 SP 사이클의 중간실패는 `분배저장 완료·재확정 실패`처럼 정확히 보고하고 복구 이력을 보존한다. 전체가 한 트랜잭션이라고 거짓 보장하지 않는다.

#### 실제 확인과 미완료 구분

2026-09-30 승인 계정 API 인증 및 주광농원 CustKey=533 조회 성공. 37/38/39의 01/02 여섯 차수는 확정 상태였다. 38-01 ShipmentKey=6443의 날짜는 9/17·9/20, 38-02 ShipmentKey=6458은 9/20이었다. 운영값을 자동 변경하지 않았다. 현재 구현은 초안/조회 단계이며 영속 이력·재고수정 전후값 연결·원자적 차수간 ERP 이동·확정 사이클 연결·요일별 출력은 아직 완료되지 않았다. 이 범위는 최종 목표에 포함하며 사용자가 별도 요청해야 할 범위로 축소하지 않는다. 입고 원천 재배정은 최신 정정에 따라 요구 범위가 아니다.

주광의 기존 요일별 출고 엑셀을 기준자료로 등록하고, 품목별 계획량을 해당 연도·대차수 안의 세부차수(예: `38-01`, `38-02`)와 출고일에 명시적으로 배분한다. 등록 전에는 엑셀 총량·계획량·현재 전산 분배량 차이를 확인하고, 사용자가 적용을 확정한 뒤에만 기존 Nenova 출고분배 규칙으로 ERP에 반영한다. 적용 후에는 선택한 요일(하루/여러 요일/전체)별 견적서를 기존 Nenova.exe 견적 인쇄 규칙과 대조해 출력하며, 수량 변경 이력과 미해결 차이를 같은 화면에서 확인한다.

핵심 원칙은 “엑셀 계획”, “웹 임시안”, “ERP 적용 결과”, “견적 인쇄본”을 서로 다른 상태·자료로 보존하는 것이다. 업로드나 미리보기만으로 주문·출고·재고·확정 상태를 바꾸지 않는다.

## 2. 업로드 엑셀에서 확인한 사실

읽기 전용으로 `주광 요일별 출고량.xlsx`를 검사했다. 원본 파일은 수정하지 않았다.

- 시트 1개: `주광 카장수알 38차 현장`; 78행 × 43열, 병합셀 포함.
- 제목은 `2026년 9월 20일 일요일 오전 출고`.
- 카네이션·장미·수국·알스트로메리아 구역이 있고, 하단에는 호주/중국 품목 행도 있다.
- 헤더에는 `(17일) 선출고(목요일)`, `총 발주 수량`, `발주수량(박스)`, `발주수량(단)`, `(20일) 일요일 출고 예정`, `(22일) 화요일 출고 예정`, `(27일) 일요일 출고 예정`이 구역별로 반복된다.
- 일부 구역은 선출고/총량/요일별 열이 다르고, 어떤 행은 숫자 외에 `2단`, `2+14단` 같은 텍스트 값이 있다. `Z/AA`에는 “수요일 사용/목요일 사용” 값이 있다.
- 합계 셀은 수식이며, 일부 행에는 `38-2차` 같은 비고가 있다. 이것만으로 전체 품목을 세부차수에 자동 귀속할 수는 없다.

따라서 열 번호 고정 파싱, 모든 수치를 같은 단위로 취급, 메모를 수량으로 자동 변환, `38-2차`를 파일 전체 차수로 간주하는 동작은 금지한다. 가져오기 전에 구역·열 의미를 확인시키고, 품목별 원본 셀·단위·날짜·값을 보여주는 검토 화면이 필요하다. 템플릿 버전과 변형된 양식 탐지를 구현 범위에 포함한다.

## 3. 사용자와 대표 작업

담당자가 주광 출고 계획을 주차별로 작성·수정하고, 영업/현장에 요일별 견적서를 전달한다. 한 대차수에 세부차수가 여러 개 있으며, 실제 출고일 계획과 전산 세부차수는 구분해서 관리해야 한다.

### 기본 작업 순서

1. **차수 이동**: 연도와 기준 대차수를 고른다. 선택한 차수 앞·뒤 대차수를 각각 한 개까지 함께 탐색한다. 각 차수의 세부차수·확정 상태를 표시하고 연도 경계를 넘을 때도 연도를 유지한다.
2. **양식 업로드**: 파일/시트를 선택하고 구조를 분석한다. 템플릿 감지 결과, 인식한 구역·헤더·수식·텍스트 메모와 오류 행을 원본 좌표와 함께 미리보기한다.
3. **품목 연결**: 원문 품목명을 ERP 품목에 연결한다. 후보가 복수거나 화종/국가/규격/단위가 충돌하면 자동 선택하지 않고 담당자가 확정한다. 행별로 `원본 행 → ProdKey → 연결 근거`를 남긴다.
4. **세부차수·출고일 배분**: 품목별로 `대차수 총량 → 세부차수별 → 세부차수 안의 출고일별` 계획을 입력한다. 업로드의 날짜별 수량을 초기값으로 보여주되, 세부차수 연결이 원본에 명확하지 않으면 직접 선택하도록 한다.
5. **비교·검증**: 기준 엑셀, 선출고, 이번 업로드 계획, 현재 ERP 분배량, 수정 후 계획, 차이를 품목·세부차수·출고일 축으로 대조한다. 오류/경고가 무엇인지와 해결 조작을 같은 줄에서 제공한다.
6. **적용**: 검증 통과 후 적용 범위와 주문/출고 영향 요약을 보여주고 별도 명시 확인을 받는다. 적용 완료는 전산 재조회까지 성공한 경우에만 표시한다.
7. **요일 인쇄**: 하루, 선택 요일 복수, 전체 요일을 선택하고 견적 인쇄 미리보기 후 출력한다. 차수/업체/요일을 인쇄물 머리말에서 확인할 수 있어야 한다.
8. **이력 확인**: 각 행에서 기존값→변경값, 변경 사유, 작업자/시간, 적용 결과, 전산 키, 인쇄본 버전을 확인한다.

## 4. 화면 정보 구조 (1920×1080, 확대 100%)

새 메뉴 이름은 **주광 견적서**로 한다. 주광을 기본 거래처로 제안하되, 사용자가 거래처를 바꾸면 다른 업체도 같은 요일별 견적 조회·인쇄 흐름으로 사용할 수 있다. 주광 이름과 정확히 일치하는 거래처가 하나일 때만 자동 선택하며, 찾지 못하거나 중복되면 사용자가 목록에서 직접 선택한다. 기본 페이지는 브라우저 전체 스크롤을 우선하며, 내부 독립 스크롤은 긴 표에서만 사용한다.

### 구현 단계 구분

- **현재 구현**: 새 `주광 견적서` 작업 화면, 주광 외 업체 선택, 업로드 파일 임시 분석, 원문 셀/구역/수식/텍스트 후보 표시, 명시적 ERP 품목 연결, 세부차수·날짜 계획 초안, 연도 격리된 전산 주문/분배/날짜행 읽기 대조.
- **후속 차단 범위**: 초안 서버 저장·변경이력 영속화, 실제 ERP 분배 적용, EXE 대조 견적 인쇄. 저장·적용·인쇄 완료처럼 오인할 버튼/상태는 제공하지 않는다. 정확한 근거·정책 및 운영 데이터 확인 뒤 별도 계약으로 연다.

- 상단: 연도·대차수 선택, 앞/현재/뒤 대차수 이동, 세부차수 탭, 확정/잠금 상태.
- 작업 단계 표시: `업로드 → 품목 연결 → 차수·요일 배분 → 대조·적용 → 견적 인쇄`.
- 중앙 표: 화종/품목, ERP 연결, 단위, 원본 총량, 선출고, 세부차수×출고일 계획, 전산 분배, 차이, 검증 상태.
- 행 펼침: 업로드 원본의 실제 구역/행/셀과 변경 로그를 확인. 변동이 없는 세부를 기본 접어 밀도를 유지한다.
- 우측 또는 선택 행 보조영역: 현재 선택 품목의 수량 변경 이력 및 적용/인쇄 기록. 카톡 연동은 이 PRD의 필수범위가 아니다.
- 하단 고정 작업영역: 현재 오류/경고 건수, 적용 전 요약, `임시 저장`, `검증`, `ERP 적용`, `요일 인쇄`를 역할/상태에 따라 활성화한다. 적용 버튼은 오류가 남으면 실행 불가다.

좁은 화면에서는 열을 고정 폭으로 잘라내지 말고 가로 스크롤·열 표시 선택을 제공한다. 첫 화면에서 차수, 업로드 상태, 검증 요약, 현재 작업의 주요 버튼에 접근 가능해야 한다.

## 5. 업무 데이터와 기준

### 5.1 분리할 데이터 계층

| 데이터 | 목적 | 변경 주체 |
|---|---|---|
| 업로드 원본/파싱 스냅샷 | 원본 파일 해시, 파일명, 시트/행/셀, 원문 값·수식, 파서 버전 보존 | 불변 스냅샷 |
| 배분 작업안 | 선택 연도·대차수, 품목 매핑, 단위, 선출고, 세부차수·출고일별 목표 수량, 수정 사유 | 사용자가 임시 저장/수정 |
| ERP 적용 이벤트/결과 | 적용 전 기준값, delta, 요청 idempotency key, ERP 키, 성공·실패·재조회 대조 | 적용 API만 기록 |
| 견적 인쇄 스냅샷 | 대상 요일, 선택 세부차수 범위, 생성시각, 출력 행/수량 합계, 인쇄 레이아웃 버전 | 읽기 전용 생성 기록 |

위 데이터가 기존 ERP 테이블에 모두 들어간다고 가정하지 않는다. 구현 전 `docs/DB_STRUCTURE.md`, 실제 DB 컬럼/키, 트리거/프로시저, 마이그레이션 경로를 확인해 웹 전용 작업안·이력 저장소의 필요 여부를 확정한다. 임시안/로그를 `Estimate`에 끼워넣지 않는다.

### 5.2 업무 키와 기간 연결

- 기본 업무 식별자는 기존 계약에 따라 `OrderYear + OrderWeek + CustKey + ProdKey`다. 세부차수 `OrderWeek`는 `NN-NN` 전체를 보존한다.
- 대차수 요약/견적의 EXE 범위와 세부차수 분배 범위를 혼동하지 않는다. 기존 불변식상 raw `ShipmentMaster.OrderYearWeek`는 `연도+대차수`다.
- 모든 API 조회·검증·쓰기에는 선택한 연도와 세부차수를 명시한다. 같은 `OrderWeek` 문자열이 전년도에 있어도 섞지 않는다.
- 요일은 화면의 월~일 표기와 EXE SQL 요일코드를 명확히 변환한다. 기존 EXE 계약의 코드(일=1, 월=2, …, 토=7)를 단일 매핑 함수로 사용하고 전 요일 왕복 테스트를 둔다.

### 5.3 수량 및 단위 불변식

- 원본 수량은 각 열의 단위를 포함해 보존한다. 박스/단/송이 변환은 Product `OutUnit`, `EstUnit`, `BunchOf1Box`, `SteamOf1Box` 및 기존 공유 변환 헬퍼를 사용한다. 임의로 한 단위로 환산하거나 `EstQuantity=OutQuantity`로 복사하지 않는다.
- 정합성은 반올림 전 정밀도와 허용오차를 계약으로 정의한다. 화면 표기 반올림 때문에 저장/대조가 통과하는 것을 허용하지 않는다.
- 선출고가 총량에 포함되는지, 요일별 계획 합계에 포함되는지 원본 열 이름과 템플릿 매핑으로 명시한다. 포함 규칙을 파서가 추측하지 않고 미리보기의 총량식으로 보여준다.
- 각 품목×연도×대차수에 대해 `원본 기준 총량 = 선출고 + 계획 대상량 + 명시된 미배분 잔량`이 성립해야 한다. 사용자 승인 없이 잔량을 마지막 요일에 몰아넣지 않는다.
- 계획 입력 기준, 현재 ERP 값, 적용 delta, 적용 후 재조회 값은 각각 분리한다. 적용은 절대값 덮어쓰기보다 현재값을 재검증한 뒤 차이를 계산하는 기존 정책을 따른다.

## 6. 적용 동작과 ERP 부작용 계약

`주광 견적서`는 신규 화면이더라도 새 임의 SQL 쓰기 경로를 만들지 않는다. 기존 `/api/shipment/distribute` 또는 `/api/shipment/distribute-import-apply`와 계약/검증을 공유하거나, 같은 순수 정책·트랜잭션 규칙을 계약 테스트로 증명해야 한다.

| 사용자 동작 | OrderMaster/Detail | ShipmentMaster/Detail | ShipmentDate | Estimate | 재고/확정 |
|---|---|---|---|---|---|
| 업로드/파싱/품목 연결/임시 저장 | 보존 | 보존 | 보존 | 보존 | 보존 |
| 분배 계획 편집 | 보존 | 보존 | 보존 | 보존 | 보존 |
| 적용: 대상 주문이 없는 양수 추가 | 기존 `week-pivot-distribution` 계약 적용(양수 주문 생성) | 출고 증가 | 날짜별 행 갱신 | 직접 변경 금지 | 확정 주/품목은 차단 또는 기존 승인된 사이클만 사용 |
| 적용: 활성 주문이 있는 양수 추가 | 주문수량 보존 | 출고 증가 | 날짜별 행 갱신 | 직접 변경 금지 | 기존 확정 가드 유지 |
| 적용: 취소/감소 | 주문수량 보존 | 출고 감소 | 날짜별 행 갱신 | 직접 변경 금지 | 기존 확정 가드 유지 |
| 견적 인쇄 | 보존 | 보존 | 보존 | 보존 | 읽기 전용 |

출고일별 다중 분배는 `ShipmentDetail` 1행과 `ShipmentDate` N행 구조를 유지한다. 출고일마다 `ShipmentDetail`을 복제하지 않는다. 상세차수마다 별도 ShipmentDetail이 필요한 경우에도 차수·거래처·품목 업무키로 기존 행을 재사용하고 중복 마스터를 만들지 않는다. `ShipmentFarm`이 이 기능의 적용 범위라면 별도 저장/대조/영향 계약을 확정하기 전에는 변경하지 않는다.

필수 보존 조건:

- `OrderMaster.Manager`는 실제 `UserInfo.UserID`; `OrderYearWeek`는 연도+대차수.
- `ShipmentDetail.CustKey = ShipmentMaster.CustKey`, 유효한 PK 발급, 상품/거래처 삭제 상태 필터.
- 출고일은 `Customer.BaseOutDay`와 기존 차수 달력 헬퍼로 결정하고 `ShipmentDetail`/`ShipmentDate` 및 `PeriodDay.BaseYmd`가 EXE 조회와 정확히 맞아야 한다.
- 수량 환산 필드 전체를 갱신하고, 한 ShipmentDetail 아래 ShipmentDate 수량합과 변환된 총 출고량을 검증한다.
- 같은 파일/작업안의 재시도는 중복 반영하지 않는다. 요청 키와 적용 전 원장 스냅샷으로 stale preview를 거부한다.
- 적용 도중 부분 성공은 전체 트랜잭션 롤백 또는 행별 명시 결과로 처리한다. 일부 행 성공을 전체 성공 배너로 표시하지 않는다.

## 7. 대조·오류 설계

검증은 오류(적용 차단), 경고(설명 후 허용), 정보로 분류한다. 오류마다 행·원본 셀·기존값·계산식·고칠 입력 위치를 연결한다.

**적용 차단 오류**: 시트/구역/헤더 미인식, 차수/연도 미지정, 업체/품목 연결 미확정 또는 다중 후보, 필요한 단위 불명, 텍스트 수량 해석 불가, 음수·비정상 값, 합계 불일치, 계획일이 차수 범위 밖, 확정 차수·품목, 전산값이 미리보기 이후 바뀜, 중복 키/PK 위험, 적용 재조회 불일치.

**확인 경고**: 전산 대비 추가/감소, 총량은 맞지만 일정이 바뀜, 비고/메모 셀을 수량으로 읽지 않았음, 수량 0/미분배 행, 과거 선출고를 계획에 포함했음, 앞뒤 대차수 자료와 유사 품목이 있음. 경고를 숨기거나 “완료”로 자동 승격하지 않는다.

대조 표의 최소 열: 품종/품목, 단위, 원본 총량, 기존 선출고, 원본 요일 수량, 선택 세부차수 계획, 전산 등록 수량, 적용 후 조회 수량, 증감(delta), 상태.

## 8. 견적 인쇄 호환

- 기존 `estimate-print` 계약과 `FormEstimateView.GetPrintDetail` / `ReportEstimate` 흐름을 재사용한다.
- 단일 요일/선택 요일/전체 요일은 체크박스 방식으로 고르며, 선택 일자·요일·세부차수·업체를 출력 전 명시한다. 전체 선택은 실제 일정이 있는 요일을 대상으로 하며 빈 날짜는 사용자 선택으로 별도 포함하지 않는 한 출력하지 않는다.
- 인쇄 쿼리는 선택 연도와 대차수, 업체, 요일을 서버에서 다시 검증한다. 정상 출고는 EXE 기준 `ViewShipment + ViewOrder`, `DetailFix=1`, 양수 `ShipmentDate.EstQuantity`, `PeriodDay` 날짜 일치 조건을 통과한 행만 표시한다.
- 기존 `Estimate` 차감/수정행은 정상 출고와 다른 원천이다. 요일 메타데이터가 없다는 이유로 등록된 Estimate 행을 조용히 빼지 않는다. 일별 인쇄 시 기존 EXE 출력 포함 규칙을 따르고, 출고일 귀속을 확인할 수 없으면 사유를 표시한다.
- 인쇄 렌더링은 기존 형식/금액·단위/표시명/적요/합계 규칙을 사용한다. 웹 전용 재정렬·재합산으로 EXE 행을 바꾸지 않는다.
- 인쇄는 읽기 전용이며 재분배/확정/Estimate 저장을 수행하지 않는다.
- 현재 저장소에 dnSpy 기반 SQL/요일 계약은 있지만 이 요청과 동일한 실제 EXE 출력물의 레이아웃 대조 자료는 확인되지 않았다. 구현 완료 조건에 동일 거래처·차수·요일의 EXE 견적 PDF/출력 캡처와 웹 미리보기 행·수량·금액의 대조를 추가한다. 서식 픽셀 유사성을 확인했다고 주장하려면 해당 샘플이 필요하다.

## 9. 수량 변경 이력

변경 이벤트마다 다음을 남긴다: 작업안 ID/버전, OrderYear/OrderWeek, CustKey/ProdKey, 출고일/요일, 단위, 변경 전·후 값, 계산 delta, 사유, 사용자/시각, 원본 파일 hash·행/셀, 요청 idempotency key, ERP 응답과 재조회 값, 출력 스냅샷 연결.

이력은 추가 전용으로 보존하고 편집/삭제하지 않는다. 정정은 반대 delta 또는 새 버전 이벤트로 기록한다. 화면 기본은 최신 이력과 차이 요약, 펼치면 상세 근거를 보여준다. “적용됨”은 DB 재조회 후 목표와 일치할 때만 표시한다.

## 10. 실패·복구 시나리오

- 파일 업로드 중 오류: 기존 저장안·ERP 값 보존, 오류 행을 다운로드/재검토할 수 있게 한다.
- 품목 매칭 후 마스터 변경: 적용 직전 ProdKey·단위·삭제상태·확정상태를 재검증하고 변경이면 적용 취소.
- 네트워크 timeout: 같은 idempotency key로 적용 결과를 조회하고 신규 분배를 반복 실행하지 않는다.
- transaction 일부 행 실패: 롤백한다. 롤백 불가능한 경로면 행별 실제 성공 여부를 재조회하고 재시도 차이를 산출한다.
- ERP 적용 성공 후 웹 응답 유실: `적용중/결과확인 필요` 상태로 두고 원장 재조회로 복구. 성공 배너를 추측해서 표시하지 않는다.
- 견적 인쇄 중 브라우저 오류: 읽기 전용이라 ERP 원장은 그대로이며 저장된 인쇄 조건/스냅샷에서 재시도한다.
- 현재 차수 확정 또는 stale 작업안: 적용을 차단하고 최신 전산값으로 다시 불러오기/재대조를 요구한다.

## 11. 구현 전 미결정 사항 및 권고

다음은 원본/저장소만으로 확정할 수 없어 구현 전 UI/계약으로 닫아야 한다. PRD 권고안은 기본값으로 제안하며 자동 추정으로 확정하지 않는다.

1. **원본 수량의 적용 의미**: `총 발주 수량`은 `OrderDetail` 목표이고 날짜별 수량은 `ShipmentDetail/ShipmentDate` 목표인가? 권고: 각각 분리 저장·대조하고, 첫 릴리스는 명시적 `분배 적용`만 지원하며 주문수량 변경은 별도 선택 액션으로 둔다.
2. **선출고와 일자별 수량의 관계**: 선출고 수량이 총량 안에 포함되는지, 이미 ERP에 등록된 출고와 어떻게 중복 제거할지? 권고: 선출고는 원본 입력으로 별도 표시하고 ERP 기존 수량과 별도 대조하며, 동일 출고로 확인되지 않으면 자동 차감/추가하지 않는다.
3. **요일→세부차수 대응**: 원본은 날짜/요일 중심이고 전 품목의 `38-01`/`38-02` 연결은 표현하지 않는다. 권고: 품목별 계획 행에 세부차수를 필수 선택시키고, 날짜는 실제 캘린더로 계산 후 `OrderYearWeek` 차수 범위와 검증한다. `H39` 비고의 `38-2차`는 그 행의 메모로만 취급한다.
4. **업체 식별자**: 파일명/시트명은 “주광”을 나타내지만 적용 거래처의 실제 `CustKey`를 증명하지 않는다. 권고: 최초에는 거래처를 직접 선택·확인하고 이후 권한 있는 기본값으로만 제안한다.
5. **기존 EXE 인쇄 서식**: 현재 dnSpy SQL/계약 문서로 데이터 규칙은 일부 확인되지만 실제 출력 샘플이 부족하다. 권고: 동일 데이터 조건의 EXE 출력 PDF/캡처를 골든 기준으로 수집하고 항목·행순서·단위·금액·요일별 합계 대조 후 레이아웃 승인.

## 12. 수용 기준 / 필수 테스트

### 가져오기

- 제공된 파일에서 1개 시트, 네 화종 구역, 반복 날짜 헤더, 병합 셀, 수식 합계, 텍스트 값(`2단`, `2+14단`), 비고(`38-2차`)를 손실 없이 인식하거나 검토 필요로 분류한다.
- 선출고/총량/각 날짜 수량의 열 매핑과 수량 단위를 검토 화면에 표시한다. 헤더가 이동/누락/중복되면 자동 적용하지 않는다.
- 수식 셀의 Excel 캐시값만 신뢰하지 말고 업로드 파서가 재계산/독립 합계를 검증한다. 계산할 수 없는 식은 차단 오류로 표시한다.
- 동일 파일을 반복 업로드해도 ERP 쓰기가 발생하지 않고, 중복 여부/새 버전 여부를 사용자가 구분한다.

### 분배/저장

- 01/02 세부차수와 한 품목 다요일 출고를 포함한 fixture에서 각 세부차수 합계, 날짜 합계, 대차수 합계, 환산 수량이 일치한다.
- 동일 OrderWeek가 전년도에 존재하는 near-miss fixture에서 선택 연도 데이터만 변경한다.
- 주문 없음/활성 주문 있음/취소·감소/확정/재고 0 및 음수 잔량/동일 요청 재시도/동시 수정에 대한 양성·차단 fixture를 둔다.
- `ShipmentMaster/Detail`, `ShipmentDate`, `OrderMaster/Detail`, `Estimate`, 재고/확정 각 테이블의 변경 전후를 확인한다. 견적 인쇄는 모든 ERP 원장을 보존한다.
- 적용 뒤 `/api/shipment/distribute-diagnose`, `ViewOrder`, `ViewShipment`, `ShipmentDate`, 견적 노출 진단 결과와 계획을 재대조한다.

### 인쇄

- 요일 코드 일~토 각각, 하루 선택, 복수 선택, 전체 선택, 선택 없음, 해당 요일 데이터 없음의 테스트.
- 단일·복수 세부차수, 다른 연도 같은 차수, 확정/미확정, 누락 PeriodDay, 기존 Estimate 차감행, 0/음수, 단위 환산 fixture.
- 웹 출력과 EXE 샘플의 대상 행, 일자, 수량, 단위, 금액, 비고, 합계를 비교하고 불일치 0건을 승인 기준으로 한다.
- 1920×1080/100% 화면에서 가로 잘림, 겹침, 고정 영역 가림, 표 스크롤, 오류/성공 알림, 인쇄 미리보기 이탈을 확인한다.

### 운영 게이트

`npm run test:erp-contract`, `npm run test:nenova-dnspy-evidence`, 변경분 ERP write guard, `npm run build`와 관련 테스트를 통과해야 한다. 실제 구현 시 현재 체크리스트/매니페스트 요구를 기준 브랜치에서 재확인한다. 운영 DB 쓰기 및 배포는 별도 승인·배포 요청 없이는 수행하지 않는다.
