# 신규 업체 온보딩 질문지 — 기준정보·SQL 스키마·AI 사전분석

- 목적: 개발 전에 업체의 기준정보(특히 품목·분류·단위)와 기존 SQL 저장구조를 파악해, 공통 ERP 스키마와 초기 마스터 데이터를 설계한다.
- 사용 시점: 킥오프 전 사전 작성 + 데이터/업무 담당자 워크숍.
- 중요: “품종·국가·꽃”은 꽃 도매 예시다. 모든 업종의 고정 필수 컬럼으로 강제하지 않는다. 먼저 업체의 실제 식별·검색·거래 규칙을 알아낸 뒤 표준 필드, 관계 테이블, 업종 확장으로 분류한다.

## 1. 업체에 먼저 요청할 자료

자료가 없거나 신규 업체여도 괜찮다. 기존 DB가 없다면 기존 엑셀/프로그램 양식과 실제 입력 예시로 대체한다.

### 기존 SQL/프로그램이 있는 경우

- DB 제품/버전, 스키마 목록, ERD 또는 스키마 전용 DDL
- 테이블/컬럼 데이터 사전: 자료형, NULL 허용, 기본값, PK/FK, 인덱스, unique 제약
- 품목·거래처·단위·창고·국가 등 마스터 테이블의 **개인정보 제거 표본 20~50행**
- 주문/구매/입고/출고/재고 원장 관련 테이블의 헤더+행이 서로 연결되는 표본 거래 각 3~5건
- 관련 View/SP/Trigger의 정의, 문서 저장 시 호출되는 프로그램/API 흐름
- 파일 업로드/다운로드 샘플과 현재 출력물
- 삭제, 수정이력, 확정/마감, 재고 반영 기준을 설명하는 담당자

### 아직 시스템/DB가 없는 경우

- 현재 쓰는 Excel·종이 양식과 실제 사례를 가명으로 작성한 샘플
- 초기 등록할 품목/거래처/단위/창고의 CSV/Excel 목록 또는 예상 규모
- 신규 ERP에서 새 코드를 발급해도 되는지, 기존 코드가 외부 거래에 쓰이는지
- 예시 거래를 주문부터 재고/회계 반영까지 손으로 따라간 결과

### 전달 금지/안전한 전달

- DB 비밀번호, 운영 접속키, 토큰, 인증서 개인키는 전달하지 않는다.
- 주민번호, 개인 연락처, 실제 계좌 등 업무 설계에 불필요한 개인정보는 삭제 또는 가명 처리한다.
- 운영 DB 직접 접속 대신 schema-only export, 스테이징 DB, read-only 제한 자료를 우선 사용한다.
- AI 분석은 업체 승인된 환경에서 최소 자료로 수행한다. AI에게 운영 쓰기 권한을 주지 않고 SQL 적용은 별도 리뷰/승인/테스트 후 담당자가 실행한다.

## 2. 업체 인터뷰 질문지

각 질문의 답은 예/아니오만 받지 말고 실제 값 예시를 최소 3개 받는다. “모름/미정”을 허용하고 미정은 설계 가정으로 숨기지 않는다.

### A. 품목을 무엇으로 식별하나요?

1. 품목 한 개를 고유하게 구분하는 코드는 무엇인가요? 코드가 없다면 시스템에서 새로 발급해도 되나요?
2. 같은 상품의 이름이 바뀌거나 공급처가 다른 이름을 써도 같은 내부 품목인가요? 별칭/거래처 품번을 관리하나요?
3. 다음 중 실제로 검색·집계·가격·재고를 나누는 기준은 무엇인가요? 사용하지 않는 것도 표시해 주세요.
   - 품목군/분류/카테고리(계층형인지)
   - 품종/모델/브랜드/규격/색상/사이즈/등급/길이/포장형태
   - 원산국, 공급업체/농장, 제조사
   - 창고/로트/제조번호/유통기한/시리얼
4. 위 항목 중 무엇이 **상품 자체를 달리하는 SKU**이고, 무엇은 공급처·입고 건·거래행에 붙는 출처 정보인가요?
5. 예: 꽃 도매에서 같은 장미 품종이라도 색상·길이·등급에 따라 코드/가격/재고가 달라지는지, 국가/농장이 달라도 같은 SKU인지?
6. 품목 코드 중복이 발견되면 자동 합치면 되나요, 담당자 승인 대상인가요? 폐기/대체 코드의 과거 거래는 어떻게 조회해야 하나요?
7. 품목별 필수 입력 필드가 다른가요? 예: 서비스에는 단위만, 꽃에는 품종·색상·원산지, 식품에는 유통기한/로트.
8. 업체/공급처에서 제공하는 품목코드와 우리 내부 코드는 각각 필요한가요?

### B. 단위·포장·수량 환산은 어떻게 하나요?

1. 구매/입고, 판매/출고, 재고, 가격 입력에 각각 어떤 단위를 쓰나요? 예: 박스·단·송이, 케이스·개, kg·g.
2. 한 품목에 여러 단위가 있나요? 구매는 박스, 판매는 단, 재고는 낱개처럼 서로 다를 수 있나요?
3. 환산식과 기준은 무엇인가요? 예: 1박스=10단, 1단=10송이. 품목마다 다른가요?
4. 환산비율은 항상 정수인가요? 소수 수량, 중량별 실측치, 개봉 박스, 손실/폐기 허용 여부를 알려주세요.
5. 환산 규칙이 공급처·포장·시기별로 달라지나요? 바뀌면 과거 거래의 환산값은 보존해야 하나요?
6. 단위별 표시 소수점과 반올림 시점은 어디인가요? 행별, 문서 합계, 세금 계산 중 무엇을 기준으로 하나요?
7. 가격은 어느 단위 기준인가요? 환율·통화·부가세·할인·운임 포함 방식도 예를 들어주세요.
8. 바코드/라벨이 있나요? 같은 품목에 박스 바코드와 낱개 바코드가 따로 있나요?

### C. 원산지·공급처·창고 등 관계 기준

1. 국가는 품목의 고정 속성인가요, 매입/입고 차수마다 달라지는 원천인가요?
2. 공급처/농장/제조사는 거래처 마스터와 같은 종류인가요, 별도 관리 대상인가요?
3. 한 품목이 여러 국가·공급처에서 조달될 수 있나요? 공급처별 품번·리드타임·포장·단가를 관리해야 하나요?
4. 창고/매장/차량/위탁처별 재고가 필요한가요? 창고 간 이동과 재고실사를 기록하나요?
5. LOT/입고 묶음/유통기한/제조일/시리얼을 추적해야 하나요? 출고 시 선입선출 등 할당 규칙이 있나요?
6. 꽃 도매라면 품종·색상은 SKU 구성 요소인가요? 국가/농장은 실제 입고에만 연결하나요? 둘 다 가능한 예시를 받아 확인합니다.

### D. 기간·차수·확정이 마스터/거래에 미치는 방식

1. 차수/주차/시즌을 사용하나요? 예시 라벨과 연도가 바뀌는 경우를 알려주세요.
2. 주문 대상 기간, 실제 입고일, 출고일, 회계 귀속 기간은 각각 별개인가요?
3. 같은 물량을 다른 판매 차수에 배정할 수 있나요? 실제 입고 차수와 판매 배정 차수를 둘 다 조회해야 하나요?
4. 언제 재고가 증가/감소하나요? 주문 저장, 검수, 입고확정, 출고확정 중 어느 이벤트인가요?
5. “확정”은 무엇을 잠그나요? 누가 할 수 있고, 확정 후 수정/취소/재오픈 절차는 무엇인가요?

### E. 초깃값과 마스터 데이터 운영

1. 첫날 필요한 품목/거래처/창고/단위 수와 매년 늘어나는 대략적인 규모는?
2. 기존 코드/엑셀에서 어느 열이 내부 품목코드·표시명·분류·단위·공급처인가요?
3. 공통 코드(국가코드, 통화, 단위, 세금코드)는 업체가 정한 표준이 있나요?
4. 새 품목 등록은 누구나 하나요, 담당자 승인 후 사용하나요? 중복 후보를 누가 검토하나요?
5. 품목 중지/대체 후 기존 거래·보고서에 과거 이름과 코드가 보존되어야 하나요?
6. Excel로 대량 등록/수정할 때 미리보기, 오류행 다운로드, 중복 매칭, 승인 절차가 필요한가요?

### F. SQL 및 입력 실례 확인

1. 화면에서 품목을 저장하면 어느 테이블이 insert/update되고 PK는 무엇인가요?
2. 판매·구매·입고·출고·재고원장 행은 어떤 FK로 연결되나요?
3. 앱에서 저장하는지, SP/trigger에서 추가 행·수량환산·재고 전기를 만드는지?
4. 유일성은 어떤 컬럼 조합으로 지키나요? 같은 품목코드가 회사/사업장별로 재사용 가능한가요?
5. 삭제는 물리 삭제인가요, 사용중지/삭제 플래그인가요? 변경 전후를 남기는 테이블/감사로그가 있나요?
6. 금액/수량/환산 계산이 SQL, 앱, 엑셀 중 어디서 이루어지고 각 값의 기준은 무엇인가요?

## 3. 업체가 채워줄 품목 샘플 템플릿

| 내부코드 | 표시명 | 분류경로 | 품종/모델 | 색상/규격 | 원산국 | 공급처/농장 | 구매단위 | 판매단위 | 재고단위 | 환산식 | 추적(LOT/기한) | 사용여부 | 예외/메모 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 예: FL-0001 | 예: Rose Mondial 50cm | 절화/장미 | Mondial | 화이트/50cm | CO | 공급처 A | 박스 | 단 | 단 | 1박스=10단 | 입고 묶음 추적 | 사용 | 실측수량 변동 여부 확인 |

위 예시는 형식 설명용 가상값이며 신규 업체의 실제 기준이나 정답으로 취급하지 않는다. 업체는 각 열을 채우거나 `해당 없음/미정`으로 표시한다.

## 4. 기준정보 SQL 논리 모델 — 업체 확인 후 선택

공통 시작점 후보는 아래와 같다. 꽃/농산물의 모든 속성을 모든 업체에 강제하지 않는다.

```text
ItemCategory(CategoryId, ParentCategoryId, CategoryCode, Name, SortOrder, IsActive)
Item(ItemId, ItemCode, DisplayName, CategoryId, BaseUnitId, ItemType, Status, RowVersion)
ItemAlias(AliasId, ItemId, SourceSystem, AliasCode, AliasName, SupplierPartyId NULL)
Unit(UnitId, UnitCode, UnitName, QuantityPrecision, IsActive)
ItemUnit(ItemId, UnitId, ConversionToBaseNumerator, ConversionToBaseDenominator,
         UsageType, EffectiveFrom, EffectiveTo)
Party(PartyId, PartyCode, Name, PartyType, Status)
ItemSource(ItemId, SupplierPartyId, SupplierItemCode, CountryId NULL,
           PurchaseUnitId, LeadTimeDays NULL, EffectiveFrom, EffectiveTo)
Warehouse(WarehouseId, WarehouseCode, Name, SiteId, Status)
ItemAttributeDefinition(AttributeId, AttributeCode, Label, DataType, RequiredForCategoryId NULL)
ItemAttributeValue(ItemId, AttributeId, ValueText, ValueNumber NULL, ValueDate NULL)

-- 선택 적용(꽃 도매 등에서 실질적으로 독립 마스터일 때)
Country(CountryId, ISOCode, Name, IsActive)
Variety(VarietyId, VarietyCode, Name, CategoryId)
Color(ColorId, ColorCode, Name)
Farm(FarmId, FarmCode, Name, CountryId)
ItemVariant(ItemVariantId, ItemId, VarietyId NULL, ColorId NULL, Grade NULL, Length NULL,
            PackSpec NULL, UniqueSkuCode)
```

설계 선택 규칙:

- 분류 계층은 카테고리 테이블로, 품목을 구분하는 SKU 요소는 품목 또는 variant로, 거래 당시 바뀌는 국가/공급처/LOT는 입고/공급처 관계로 둔다.
- 품종/국가/꽃 색을 단순 텍스트 컬럼으로 둘지 독립 FK 마스터로 둘지는 코드값 공유, 다국어, 변경 이력, 보고서 필터/집계 필요성으로 결정한다.
- 모든 검색/보고서에서 쓰는 식별값을 자유 텍스트 JSON에만 저장하지 않는다. JSON/EAV는 진짜 가변 속성에 한정한다.
- 기본 단위 변환은 정확한 분수 또는 decimal 계약으로 정의하고, 저장 당시 환산비율/기준수량을 거래행에 스냅샷한다. 마스터 변경으로 과거 거래를 재계산하지 않는다.
- 업체별 별도 DB라서 CompanyId를 모든 FK에 반복할지는 배포/추후 통합/백업 복구 모델과 함께 결정한다. 사용자 제공 SQL을 확인하지 않고 현 ERP의 컬럼명을 그대로 복사하지 않는다.

## 5. AI 자동분석 단계와 결과물

AI는 자동 DDL 실행기가 아니라 스키마 조사 보조자다. 아래 순서로 근거와 불확실성을 남긴다.

1. **입력 분류**: 파일 manifest, 테이블·컬럼·키·뷰/SP 정의, 샘플 파일, 표본행을 파일 종류별 정리. 민감정보 탐지·마스킹 상태 확인.
2. **스키마 읽기**: PK/FK/unique/index, 이름·자료형·nullability, 뷰/SP SQL을 읽고 직접 근거와 추정 근거를 구분.
3. **마스터 후보 탐지**: 코드·명칭·상태·분류 열로 품목/거래처/단위/창고/국가 후보 찾기. 같은 이름·코드 중복과 별칭 후보를 따로 보고.
4. **관계/업무 추론**: FK, 같은 키의 표본 연결, 저장 SP/뷰 참조를 이용해 문서 header-line, 입고-재고, 품목-단위 관계 후보 생성.
5. **값 품질 프로파일**: null 비율, distinct 개수, 포맷 혼재, 잘린 코드, 참조 누락, 중복, 단위별 수량/환산 이상치, 사용중/삭제 상태 값 목록을 계산.
6. **질문 생성**: 결정 근거가 부족하거나 상충하는 항목은 “업체 확인 질문”으로 출력. 예: 국가가 품목 속성인지 입고 출처인지, 박스 환산율이 품목별인지 입고별인지.
7. **설계 초안 생성**: canonical ERD/필드 매핑 표, SQL DDL 초안, 엑셀 import mapping/seed CSV, 오류·미확정 목록, read-only 검증 query, 화면 폼 초안 생성.
8. **사람 검토**: 업체 업무 담당자와 DBA가 코드 유일성·단위·삭제/수정·차수/확정 영향·외부 연동 계약을 각각 승인하거나 수정.
9. **검증 후 배포 준비**: 빈 스테이징 DB에 migration 적용, 샘플 import, 참조 무결성/합계/검색/보고서 테스트, rollback/reseed 확인. 운영 적용은 승인된 change window에서 담당자가 별도 수행.

### AI 산출물에 붙일 근거/신뢰도

모든 필드 매핑은 `원본 객체/컬럼 → 제안 객체/필드 → 변환 규칙 → 근거(DDL/FK/SP/샘플 행) → 확신도 → 미해결 질문 → 승인자`로 기록한다. 근거 없는 매핑을 확정 상태로 표시하지 않는다. 낮은 확신도, 샘플 부족, 컬럼 의미 충돌, 환산식 불일치는 구현 전 차단 항목으로 올린다.

### 금지하는 자동화

- AI가 운영 SQL에 CREATE/ALTER/INSERT/UPDATE/DELETE 실행
- 품목 중복을 이름 유사도만으로 병합하거나 코드를 재발급
- 샘플에서 추론한 단위/세율/국가/품종 의미를 사람 승인 없이 확정
- 확정/재고/회계 원장을 표본만 보고 변경
- 스키마/API 계약 없이 JSON 속성으로 중요 업무필드를 임의 은닉

## 6. 완료 수용 기준

- 업체가 품목 식별 방식, 분류축, 단위/환산, 국가·공급처 귀속 시점을 사례로 확인했다.
- 대표 품목 최소 20개(실제 운영 시드 가능하면 전체)와 단위/환산표의 출처가 명확하다.
- 기존 SQL이 있으면 PK/FK 및 document save/update/post 경로를 표본 거래로 연결했다. DB가 없으면 이 요구지의 샘플 템플릿을 통해 새 코드·시드 정책을 승인했다.
- ERD/DDL 초안의 각 컬럼이 필수/선택/업종별로 분류되고, 타입·NULL·unique·FK·삭제/비활성 정책이 정해졌다.
- AI가 추론한 값, 직접 관찰한 값, 업체 승인 값을 구분했다. 미확정 질문이 0건이거나 출시 보류로 합의돼 있다.
- staging에서 DDL과 표본 import를 재실행/검증했고, 참조무결성·중복·단위·대표 보고서가 통과했다.
- AI/개발자가 운영 DB에 직접 쓰지 않았으며, 별도 운영 적용 절차·담당자·백업·복구계획이 문서화됐다.
