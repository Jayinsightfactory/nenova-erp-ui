# 데스크톱 자동 실행 설계와 업로드 지연 조사

목적: PC 로그인 후 업무 앱을 찾는 수고를 없애고, 한 사람의 업로드가 다른 직원의 일을 막는 원인을 확인한다. 연결 목표 g13·g18. 설계/조회 단계이며 구현·배포·직원 PC 설정 변경은 하지 않았다.

## 자동 실행 설계

- 기준 코드 b018e7e18, Desktop 1.3.80 / Electron 44.6.0 / 사용자별 NSIS 설치. 현재 로그인 자동 실행 등록 없음. main.cjs:59의 단일 인스턴스 잠금은 이미 있음.
- Windows 전원 인가가 아니라 사용자 로그인 후 시작한다. 설치된 정식 앱만 사용자별 Run 등록을 수행하며 관리자 권한이나 별도 상주 데몬을 추가하지 않는다.
- 새 startup.cjs에서 setLoginItemSettings({openAtLogin:true,path:process.execPath,args:['--autostart'],name:'NenovaDesktop'})를 관리한다. NSIS 설치이므로 Squirrel Update.exe 경로를 사용하지 않는다. 조회도 동일 path/args로 수행한다.
- 최초 업데이트 실행 시 한 번 기본 활성화하고 등록 결과를 읽어 검증한다. 사용자가 앱 또는 Windows 시작 앱에서 끈 상태는 다음 실행/업데이트에서 강제로 켜지 않는다. 등록 이력과 사용자 선택을 구분해 저장한다.
- 기존 앱 설정에 'Windows 로그인 시 자동 실행'과 실제 등록 상태를 표시한다. 실행 실패는 비밀값 없는 오류 코드로 안내한다. 삭제 시 자신이 등록한 Run 항목만 정리한다.
- --autostart에서는 우선 로컬 홈 창을 열고 네트워크 요청 시작을 15~45초 무작위로 분산한다(설계값, 실측 아님). 직원이 직접 기능을 누르면 즉시 시작한다. 복구 탭은 선택할 때 조회한다. 네트워크 미연결 시 상한 있는 지수 지연 재연결만 수행하고 업로드/저장을 자동 재실행하지 않는다.
- 기존 단일 인스턴스 잠금과 수동 실행의 창 포커스를 유지한다. 자동 시작 중 수동 실행해도 창이 중복되지 않아야 한다. 로그인이 만료되면 로그인 화면을 표시한다.
- 약점: 앱을 한 번도 실행하지 않은 구버전 PC에는 앱 내부 등록만으로 적용할 수 없다. 설치 완료 실행 또는 승인된 카나리 업데이트에서 첫 실행을 확인해야 한다. Windows에서 차단된 시작 앱도 성공으로 표시하면 안 된다.

## 구현 순서와 완료 기준

1. startup 정책 모듈, main.cjs 연결, 기존 설정 IPC/화면, NSIS 제거 처리, package.json 버전 및 가이드 연결을 같은 변경으로 처리한다.
2. 격리 테스트: 미등록/등록됨/사용자 해제/Windows 해제/경로 변경/등록 실패/미패키징 실행. 실제 Windows 테스트: 재부팅→로그인, 중복 실행, 업데이트, 제거, 네트워크 미연결, 로그아웃 상태.
3. 직원 PC 한 대에서 로그인 후 60초 내 앱 1개 실행과 홈 표시, 서버 요청 분산을 확인한 뒤 확대한다. 60초는 수용 기준이며 달성 실측이 아니다.
4. 되돌리기: 앱 설정에서 자동 실행 해제 및 등록 readback. 기존 ERP 원장·업로드 기록은 변경하지 않는다.

공식 API 근거: https://www.electronjs.org/docs/latest/api/app#appsetloginitemsettingssettings

## 업로드 지연 조사 근거

- 2026-11-02 조사 문서에는 381행 처리 749초, 504/499, DB timeout이 기록돼 있다. 지난주(11/16~22)의 원인으로 소급 단정하지 않는다.
- lib/db.js:19의 공용 pool 최대 연결은 20. 이것만으로 pool 고갈을 확정할 수 없다.
- lib/shipmentImport.js:2274의 withTransaction 내부에서 2308행부터 targetRows를 순회한다. 긴 트랜잭션/행별 SQL이 DB 대기를 늘릴 수 있다는 가설이며 실제 blocker는 미확인이다.
- 운영 진단: https://github.com/Jayinsightfactory/nenova-erp-ui/actions/runs/45089140667 (diagnose_performance_only=true). 배포 job 제외 확인. 개인·고객 정보 대신 집계만 확인한다.
- 직접 SSH는 키 인증 불가로 중단했고 기존 GitHub Actions의 읽기 전용 진단 경로를 사용했다.

### 우선순위

1. 개발 자체와 운영 배포를 구분한다. 업무 중 연속 배포를 묶고, 원장 업로드 완료를 기다리는 기존 배포 잠금을 보존한다. 일반 조회까지 무중단인지 별도 검증한다. 현재 규칙 변경/배포 제한은 적용하지 않았다.
2. 11/19 17시대의 5xx 세부 코드·분 단위 분포·업로드 재시도율과 위4회 reload를 대조한다. 현재7일 요약은 세부 코드와 요청시간을 보존하지 않아 원인 확정에 부족하다.
3. 기존 drive-ingest는 이미 동시2개·대기24개·15초 대기·Retry-After5초 제한과 별도 저장 프로세스를 갖는다. 따라서 '격리 없음'이라고 진단하지 않는다. 송신측이 재시도 지연을 지키는지와 정상 처리/혼잡 거절/worker 실패를 분리 확인한다.
4. 활동 기록 worker 경로/배포 누락을 격리 재현한다. 오류가 실제 조회 중단으로 전파되는지는 별도 검증한다.
5. DB 잠금/쿼리 개선은 대상 화면과 시간대가 좁혀진 뒤 ERP 가드·dnSpy·읽기 전용 probe를 거친다. 아직 원장 변경 없음.

DB 대기이면 쿼리 횟수·실행계획·잠금 시간을 먼저 측정한다. 원장 원자성을 깨는 임의 분할 커밋이나 NOLOCK 추가, 연결 수 무작정 확대는 해결책으로 채택하지 않는다. CPU/메인 스레드 지연이면 파일 해석·압축 같은 무거운 부분만 격리한다. 메모리 재시작이면 파일 크기/동시 수 제한과 스트리밍을 우선 검토한다. 실패 응답 후 저장 결과 불명 상태는 기존 작업번호 조회로 확인하고 자동 재업로드하지 않는다.
