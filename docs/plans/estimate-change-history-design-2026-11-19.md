# 네노바 견적 변경 이력 — 양식 분석 및 화면 기획 (2026-11-19)

범위: 사용자 제공 견적 변경요청서의 구조 조회와 독립 메뉴 설계까지. 새 메뉴/API/DB/원장 쓰기 구현은 하지 않았다. 실제 예시값·개인정보는 이 문서에 기록하지 않는다.

9시트: 7.6 / 7.10 / 7.13 / 7.14 / 7.16 / 7.22 / 8.26 / 9.3 / 9.21. 시트명에 연도가 없으므로 연도를 추정하지 않는다. 공통 제목 A1:I1, 날짜 영역 A5(문자열 또는 날짜서식 숫자), B5:G5 병합 빈칸, 작성자 H5:I5. 6행 헤더 A 차수/B 업체/C 품목/D 색상/E 단위/F 변경전/G 변경후/H:I 비고. 상세 7행부터. F/G는 직접 입력 숫자(일반/회계형 숫자서식)이며 변경대상 종류를 확정하는 메타데이터가 없다. 수식/검증/Excel Table 모두 없음.

7.16/7.22/8.26은 인쇄영역 밖 입력행이 있어 출력 누락 우려. 7.6 A8:B13/A15:B19/A21:B26 병합이 차수·업체 묶음을 표현한다. 9.21 C:E 병합으로 품목·색상·단위 독립 칼럼이 없다. 가져오기를 만들 때 원본 시트/행/셀/병합그룹과 원본텍스트를 보존하고, 공란은 병합범위 안에서만 상속해야 한다. 해당 품목/값으로 수량 또는 단가라고 자동 단정하지 않는다.

화면 제안: 사용자 지정 독립 메뉴 **네노바 견적 변경 이력**. 견적서관리에는 연관 이력과 바로가기를 둔다. 내부 탭은 ①요청 목록(연도/원차수/적용차수/업체/상태) ②요청·원본 대조(원본 셀, 현행 원장값, 요청 전/후, 변경항목, 사유) ③처리 이력(요청/검토/반영/확인 시각 및 사용자). 원본 날짜/요청 등록시각/ERP 적용일/엑셀 다운로드시각/판매등록확정시각/이카운트 실제 입력일을 분리한다. 없는 기록은 미기록. 다운로드 성공만으로 판매등록완료를 만들지 않는다.

일반 견적행은 ShipmentDetail.SdetailKey + 일별 ShipmentDate 행/ShipmentDtm, 별도 차감행은 Estimate.EstimateKey. 공통 범위는 ShipmentMaster.OrderYear+OrderWeek+CustKey+ProdKey. 같은 품목이 여러 출고일/차감행에 반복되므로 품목명/차수만으로 자동 연결하면 안 된다. 기존 pages/api/estimate/index.js byDate와 Estimate UNION, update-entry.js EstimateKey 범위 검증을 재사용할지 후속 구현에서 native 근거와 계약으로 확정한다. EstimateDtm은 수정가능한 업무일자이며 저장감사시각과 다르다.

엑셀 경로: pages/estimate.js handleEcountExcel → GET /api/estimate(view=excelDetail,year,week,custKey,weekDays) → lib/estimateEcountExcel.js downloadEcountUploadWorkbook → XLSX.writeFile. 인쇄형은 downloadEstimatePrintWorkbook. 현재 이 경로는 다운로드 날짜 감사이력을 저장하지 않는다. 파일명 날짜를 과거 다운로드 이력으로 역산하지 않는다. 판매등록확정은 WebSalesSnapshot REG_CONFIRM TakenAt이며 이카운트 실제 입력 확인이 아니다.

후속 구현 전 확정할 핵심: 변경대상이 수량/단가/금액 중 무엇인지, 원차수와 적용차수, 여러 실제행 중 대상키, 요청서 원본/현재 ERP의 변경전 불일치 처리, 승인 및 실제 반영 계약. 새 독립 메뉴 개발 시 desktop 카탈로그/버전/가이드 의무 포함.
