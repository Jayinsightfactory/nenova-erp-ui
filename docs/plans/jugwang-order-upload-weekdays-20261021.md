# 주광 주문 업로드 원본 요일수량 적용 — 사전 조사

날짜: 2026-10-21. 상태: 조사 완료, 실제 업로드 원본 파일 확보 전 구현·배포·운영 적용 미완료.

사용자 요청: 주광 업로드 엑셀의 품목별·요일별 수량을 그대로 적용하고 부작용을 확인한다. 웹에 저장된 요일 설정을 복제하는 요청이 아니다.

## 확인한 사실
- 일반 주문 업로드는 orderImportParse → 품목 매칭 → mergeRegisterItems → FINAL_SNAPSHOT 경로다. 현재 등록 payload는 품목별 총량만 전달한다. 요일별 수량을 보존하는 계약이 없다.
- 주광 전용 weekday-upload-preview는 별도 파서로 날짜 후보 셀을 읽는다. 수식은 재계산하지 않고 formula-review로 분리한다. 기존 화면 addSourceRow는 날짜 헤더/선택일과 단위·매칭을 확인하는 별도 흐름이다. 이 선택일 fallback을 무인 업로드에 복제해서는 안 된다.
- 설치 Nenova.exe ClassShipmentDate를 dnSpy.Console로 재실행했다. Insert는 ShipmentDtm/ShipmentQuantity/EstQuantity/Cost/Amount/Vat/SdetailKey를 기록한다. 요일 저장은 표시만의 변경이 아니며 견적 금액에 연결된다.
- 운영 SELECT: 주광 CustKey533, 2026/44-01 활성 주문48행, 활성 출고 헤더의 상세0행. 2025/44-01에는 주문93행과 확정 상세89행이 있다. 단위 혼합 총량은 업무수량으로 해석하지 않았다.
- 2026/43-01에는 10/22와10/23 출고일행이 있다. 다른 차수의 날짜를 재사용하지 않는다.
- 실제 이번 원본 파일은 아직 제공되지 않았다. 알려진 로컬 runtime 템플릿 경로 두 곳에도 파일이 없다. 과거38차 템플릿은 이번 원본 검증을 대체하지 못한다.

## 적용 전 해결할 위험
1. 엑셀 날짜/요일과 연도·세부차수: PeriodDay 정확 날짜와 연결하고 모호한 요일·여러 차수는 중단한다.
2. 동일품목 여러 행/요일: 원본 셀 좌표를 보존하며 합계·요일을 각각 집계한다. 동일 수량을 모든 날짜에 복제하지 않는다.
3. 단위: 박스/단/송이 및 품목 OutUnit을 환산해 총량과 요일합을 비교한다. 소수 반올림·수식 캐시를 임의 승인하지 않는다.
4. 선출고/기출고·윌슨·합계열: 새 출고요일 수량에 재포함하면 중복된다. 원본에서 역할을 명확히 구분한다.
5. 재업로드/기존 분배: 현재 snapshot을 비교하고 변경·확정 출고를 조용히 덮어쓰지 않는다. 이미 저장된 요청은 더하지 않는다.
6. 원자성: 주문과 요일분배가 절반만 저장되지 않게 동일 transaction의 실패 rollback과 readback을 검증한다. timeout 자동재시도 금지.
7. downstream: ShipmentDate/Detail 환산·금액, 대표일, 견적 조회·확정상태·재고 보존 여부를 검증한다. 업로드를 자동 확정으로 취급하지 않는다.

## 후속 조사 — 기존 파일 발견 및 처리 기준

앞선 템플릿 경로 두 곳의 부재는 기존 파일 전체 부재를 뜻하지 않았다. 다운로드 폴더까지 검색해 아래 파일을 읽기 전용으로 확인했다.
- C:/Users/USER/Downloads/주광 발주(2026년38차) - 발주내역_주광.xlsx
- C:/Users/USER/Downloads/주광_발주내역_2026_42_43_44.xlsx

38차 원본은 15개 시트이며 오래된 차수·복사 시트가 함께 있다. `주광 카장수알 38차`의 C2는 선출고(목요일), D2는 발주수량, E2는 부산윌슨, G2는 22일 화요일 출고예정, Z2/AA2는 사용요일이다. 장미 구역 D29/E29는 동일 발주를 박스/단으로 표현하므로 합산해서는 안 된다.

42·43·44차 파일은 웹 발주내역 출력 구조다. `주광 발주내역`의 G4=일요일6, H4=윌슨일요일1, I4=일요일합계7, J4=42-1합계7이다. 실제 일요일은7이며 G+H+I=14 또는 J까지 더하는 방식은 중복이다. 이는 당시 저장 원본과의 동일성을 증명한 것이 아니라 발견한 파일의 실제 셀 조사다.

이 파일의 44차 범위 AQ4:BI199에는 0이 아닌 숫자가 없다. 44차 주문/요일분배의 수량 원본으로 사용할 수 없다. 빈칸은 미입력이며 취소 또는0으로 해석하지 않는다.

운영 재조회: 533/2026/44-01 활성 주문48행, 출고상세0행 유지. 최근30일 /api/orders SUCCESS 중 custKey533을 JSON으로 확인한 로그4건은41-01 sales-paste이며 요일필드가 없다. 이 조회만으로 다른 메뉴의 모든 업로드 부재를 단정하지 않는다. 일반 import-parse 코드는 분석 후 임시 원본을 unlink하며 영구 보관 경로가 없다. 주광 전용 서버 템플릿은 별도다.

### 구현 시 처리 기준
- 기존 주문이 있으면 품목별 수량과 단위를 보존하고, 요일별 계획과의 차이만 표시한다. 요일 적용을 주문 최종본 전체교체 API에 재전송하지 않는다.
- 출고 미분배 품목은 원본 수량이 확인된 날짜만 신규분배한다. 날짜합이 주문총량과 다르면 잔량/선출고/윌슨 포함 여부를 먼저 확인하며 임의로 주문총량에 맞춰 배분하지 않는다.
- 이미 같은 날짜·품목·수량이 저장돼 있으면 추가0건. 다른 수량이면 전후 비교로 충돌을 보여주고 단순가산하지 않는다.
- 확정 출고·기출고는 자동 변경하지 않는다. 선출고를 다시 신규분배하지 않는다. 사용일은 출고일이 아니다.
- 총량과 환산열은 검산에만 사용한다. 일요일합계가 있으면 일반일요일+윌슨과 일치하는지 확인하고 한 번만 반영한다.
- 연도·세부차수·품목·실제날짜와 원본 sheet/cell을 기록하고 한 트랜잭션·중복방지·동시수정 검증을 적용한다.

현재 범위는 사용자 후속 요청에 따른 조사·처리방안 확인이다. 운영 원장 수정과 기능 배포는 하지 않았다. 38/42차 파일은 구조 검증에 활용 가능하지만 44차 실제 일별 수량은 아직 확인되지 않았다.

## 구현 및 검증 갱신
- `/orders/weekday-upload` 별도 주문보존 진입점. 원본 시트·품종 명시, 기존 활성 주문에 연결한 양수 날짜만 신규 분배. 기존 동일 분배는 no-op, 다른 분배·확정 헤더·주문초과·동시변경은 중단. 빈칸/0은 취소가 아님.
- 서명 원본/계획은 사용자·단계·20분 유효기간에 묶임. 동일 operationId 재시도 중복 방지, 트랜잭션 내 주문 지문 재검증. 자동확정/농장/재고조정 없음.
- 일반 출고분배 업로드도 시트와 품종을 명시하여 숨김/타 시트 키맵 및 선택 외 품목을 제외. 선택한 품종 안의 기존 전체교체 계약은 유지.
- 실제 파일 재분석: 38-01 카네이션9/장미2/수국6행, 42-01 카네이션13/장미12/수국12/알스트로7행, 모두 경고0. 44-01 네 품종 모두0행이므로 운영 보정/재업로드하지 않음. 반복 제목·공백 합계·기타 구역 승계 방지 회귀 추가.
- 격리 실제 MSSQL: 신규 날짜5+15, 주문25 보존, 전년도99 보존, 동일 요청 및 재분석 no-op, 충돌/동시변경 차단, 두 번째 날짜 INSERT 강제실패 전체롤백 통과. 원장/농장/재고/견적 지문 동일.
- 배포 및 실브라우저 최종 확인 진행 중. EXE GUI 직접 조작은 미검증.
