# 입고 소급 정정 요청 → 영업지원 매칭 → 최종 반영 설계

상태: 사용자 업무 기준을 반영한 후속 설계. 기존 PR1454의 즉시 교체 기능과 구분한다. 이 문서 작성으로 새 승인 기능이 배포된 것은 아니다. 기준 소스 origin/master 2f191418, 2026-11-04 실제 EXE CLI와 운영 SELECT 대조. 운영 수정 0.

## 사용자 결정

1. 수입부가 농장·품목·수량 수정안을 요청한다. 요청만으로 입고·분배·재고를 바꾸지 않는다.
2. 영업지원이 해당 업체별 분배를 매칭·감소·추가하고 최종 확정할 때 반영한다.
3. 품목 A→B이고 수량이 같으면 기존 분배를 B로 옮기는 매칭을 허용한다.
4. 분배수량을 줄이고 끝낼 수 있다. 감소분을 다른 품목에 반드시 더하도록 강제하지 않는다. 다른 품목 추가는 독립적으로 선택한다.
5. 분배가 바뀌면 해당 견적·매출도 검토한 결과로 함께 정정한다. 분배만 바꾸고 견적·매출을 방치하는 정책은 채택하지 않는다.
6. 같은 품목·수량을 유지하는 농장 정정은 수량 재분배 사유가 아니다. 연결 확인 후 농장 정정만 확정하며, 총량·재고·견적·매출금액과 기존 확정 상태를 보존한다.

## 실제 구조와 범위

- 실제 dnSpy `FormShipmentDistribution.btnSave_Click`은 업체별 `ShipmentDetail.OutQuantity` 및 환산수량·판매단가·공급가·VAT를 저장한다. `dtFarm` 변경은 별도의 `ClassShipmentFarm.Insert` 경로다. 날짜별 수량/금액은 `ShipmentDate`에 저장한다.
- `ShipmentFarm`은 `FarmKey + ShipmentQuantity + SdetailKey`를 갖는다. 운영 스키마에서 `WarehouseKey/WdetailKey`가 이 테이블에 없는 것을 확인했다. 기존 입고 한 건이 어느 분배행을 만들었는지 자동으로 단정할 수 없다.
- 운영 SELECT: 2026년 41/42/43/44차 상세1558/1412/1445/1351행, 상세확정1558/1412/1445/1350행. 같은 범위 `ShipmentFarm` 연결행0. 현재 표본은 업체·품목 총량 분배이며 농장별 배정이 선행조건이 아니다. 2025 동일 차수도 별도 조회하여 연도 분리 확인. 이 숫자는 조회시점 표본이며 앞으로 모든 원장에 농장배정이 없다는 보장은 아니다.
- 견적은 일반 양수 출고의 경우 `ViewShipment + ViewOrder + ShipmentDate + PeriodDay` 조회로 만들어진다. 모든 견적 행이 독립 `Estimate` 행인 것으로 가정하면 안 된다. 별도 차감/추가 `Estimate`는 물리적 연결과 사용자 선택을 검증한 경우에만 대상으로 삼는다.
- `ShipmentDetail.Amount/Vat`와 날짜별 합계가 매출·견적에 각각 쓰인다. 분배 수량만 업데이트해서 자동으로 모든 금액이 맞아질 것으로 가정하지 않는다. 기존 `amountVatFromCostEst`, `alignShipmentDetailMoneyToDatesMany`, native 단위/반올림 정책을 재사용한다.

## 요청 종류 판정

| 종류 | 판정 | 영업지원 작업 | ERP 반영 |
|---|---|---|---|
| 농장 정보 정정 | ProdKey별 수량·환산·단가·금액 동일, 농장만 변경 | 이전/신규 농장 및 연결 확인, 수량 매칭 생략 | 입고 농장 및 명시적 연결 정보만 정정. 분배·재고·금액·확정 보존 |
| 품목 정정 | ProdKey 변경, 수량 유지 또는 변경 | 원분배의 유지/이동/감소와 대상품목 선택 | 승인된 분배 및 입고, 관련 날짜·견적·매출·재고 함께 반영 |
| 수량 정정 | 동일 ProdKey의 입고수량 변경 | 업체/출고일별 최종 분배수량 검토, 감소만으로 종료 허용 | 승인된 입고·출고 차액 및 후속 재고, 수량에 따른 금액 함께 반영 |
| 원가/단가 동시 변경 | 수량이 같아도 매입/운임/판매단가 등 경제적 값 변경 | 금액 영향을 별도 표시하여 명시 검토 | 농장만 정정 경로로 처리하지 않음 |

농장 문자열만 바뀌었다는 이유로 원가·판매금액을 자동 재산정하지 않는다. 이미 연결된 문서의 공급자 정체성이나 원가 근거가 실질적으로 달라지는 경우는 일반 농장 정보 정정과 구분한다. 원가 연결이 존재한다는 이유만으로 무조건 차단하는 기존 정책을 그대로 복제하지 않는다.

## 화면과 상태

수입부 입고관리: 기존 원장 선택 → 수정 요청 → 농장 또는 수정 파일/사유 입력 → 변경 전후 확인 → 영업지원 요청.

영업지원 요청함: 요청자/연도·차수/입고번호/요청종류/변경 요약 → 요청 상세 → 분배 매칭(필요한 경우) → 견적·매출·재고 영향 확인 → 최종 확정. 반려·요청 취소도 감사 이력에 남긴다.

상태: 초안 → 검토 대기 → 검토 중 → 적용 완료. 별도 상태는 반려/취소. 확정 버튼이 눌렸다는 이유로 먼저 적용 완료로 표시하지 않는다. 트랜잭션 커밋과 사후 검산에 성공한 경우에만 완료한다. 처리 오류나 원장 변경은 검토 상태를 유지하고 다시 검토한다.

검토 대기/임시저장은 웹 요청 데이터만 저장한다. 다른 사용자의 정상 ERP 작업을 장시간 잠그지 않는다. 최종 확정 순간에 원장 버전·물리적 키·수량·금액·확정 상태를 다시 대조한다. 요청 후 원장이 변했다면 기존 승인을 재사용하지 않는다.

## 영업지원 매칭 표

물리적 `SdetailKey/SdateKey`, 연도·세부차수, 업체, 출고일, 기존 품목/단위/수량/단가/금액, 처리방식, 대상품목, 최종 수량/단가/금액, 증감과 사유를 표시한다. 단위가 다른 품목끼리는 숫자만 같은 것을 동일 물량으로 취급하지 않는다.

- 유지: 선택 원분배를 보존.
- 이동: 선택 수량을 원품목에서 빼고 대상품목에 더함. 동일 업체/출고일을 기본 제안하고 변경은 명시 선택.
- 감소: 선택 분배수량을 줄임. 대상품목은 불필요하며 0도 허용.
- 추가: 대상품목 분배 증가 또는 신규 배정. 원품목 감소와 강제 연결하지 않음.

예: 기존 A100을 B100으로 정정, 업체별 A60/A40이라면 B60/B40 제안 후 영업지원이 확인. 기존 A100을 A80으로 정정하면서 분배 A60/A30을 A50/A30으로 줄이고 종료 가능. 감소10을 다른 품목에 자동 추가하지 않음.

총량 검증은 단순히 `입고 변화량 = 분배 변화량`을 강제하지 않는다. 품목·차수별 기초재고+입고−실제 분배/출고의 결과를 확인한다. 일부는 재고로 남을 수 있다. 감소분과 다른 품목 증가분을 한 숫자로 상계해 부족을 숨기지 않는다.

농장 배정 기록이 있는 행은 별도 연결 조정 대상이다. 동일 농장·품목의 모든 과거 `ShipmentFarm`을 통째로 새 농장으로 바꾸지 않는다. 입고 단위 계보가 없으므로 영업지원이 명시한 행/수량만 연결 정정한다.

## 최종 확정 원자 작업과 보존

| 동작 | 웹 요청/감사 | 입고 | 업체 분배/출고일 | 주문 | 재고 | 견적·매출/손익 |

| 요청/임시 매칭 | 저장 | 읽기 | 읽기 | 읽기 | 읽기 | 영향 미리보기 |
| 농장만 정정 확정 | 전후/확정자 기록 | 농장 정정 | 총량·날짜 보존, 선택한 농장 연결만 검토 | 보존 | 보존 | 금액 보존, 연결정보 검증 |

native V2 재고 게이트와 원장 잠금 → 미리보기 기준 재검증 → 입고+승인 분배+날짜별 수량/단가/금액 → 기존·신규 품목 재고와 이후 snapshot 재계산 → 실제 견적 조인/매출/손익 검산 → 감사·완료 커밋 순서로 설계한다. 독립 HTTP API 여러 개를 차례로 호출해 부분 커밋하는 방식은 금지한다.

41차 수정 시 42~44차 재고가 영향 범위이고 더 뒤/다음 연도 snapshot이 있으면 거기까지 검산한다. 이후 분배행은 자동 재작성하지 않고 영업지원이 명시한 행만 변경한다. 44차까지만 검사하고 이후 재고를 무시하지 않는다. 확정 여부 자체로 일괄 거부하거나 모든 차수 확정을 해제하지 않는다.

부족 재고는 품목·차수·부족량을 표시하고, 숨겨진 보정으로 통과시키지 않는다. 기존 사용자 규칙의 부족분 재고조정을 선택하는 경우에도 별도의 명시 확인과 같은 트랜잭션이 필요하다.

기존 확정 상태는 영향을 받는 행의 계약에 따라 보존한다. 신규 대상품목에 고객 주문이 없으면 EXE 견적 INNER JOIN에서 빠질 수 있으므로 양수 실제 주문/대체품 연결의 정책을 확정해야 한다. 0수량 가짜 주문은 금지하며, 사용자 요청의 품목 정정과 고객 원주문 정정을 동일한 동작으로 단정하지 않는다.

이미 외부 발송된 견적 파일이나 외부 회계 전표를 웹 원장 정정만으로 자동 소급 변경했다고 표시하지 않는다. 재발행 필요 여부는 영향 목록에 표시하고, 외부 전송/이카운트 쓰기는 이 기능에 포함하지 않는다.

## 구현 전 확정·검증할 기술 항목

- 권한: 수입부 요청/취소, 영업지원 최종 확정, 대표 권한 포함 여부는 기존 권한 helper와 맞춘다. 요청자의 클라이언트 역할값을 신뢰하지 않는다.
- 저장: 요청 본문/리비전/매칭/감사/operation UUID를 트랜잭션으로 저장할 웹 전용 원장 계약. 기존 감사 테이블을 업무 원장처럼 임의 재사용하지 않는다. 새 schema가 필요하면 실행 가능한 제안 SQL만 작성하고 프로젝트의 SSMS 절차를 따른다.
- 신규 품목 분배의 주문 연결, 기존 차감 Estimate 처리, 원가·확정 손익의 재산정과 버전 관리, 정확한 scope/잠금/readback을 구현 전에 확정한다. 아직 이 새 writer가 검증됐다는 주장은 하지 않는다.
- 양성 fixture: 농장만 변경(금액/수량/재고 불변), A→B 같은 단위, 서로 다른 단위, 감소만, 감소+다른 품목 증가, 추가만, 0으로 감소, 다중 업체/출고일, 이미 존재하는 대상품목 합치기, 기존 농장배정 없음/있음, 후속연도 snapshot.
- 반례 fixture: 오래된 요청/다른 연도 동일 차수/중복 확정/권한 위조/부족수량/원가 불일치/농장 연결 모호/계산·감사 실패. 모든 실패는 부분 변경0.
- 완료 기준: 새 기능 계약 JSON·실제 MSSQL 통합·EXE 견적 노출·매출 일치·필수 ERP/빌드·PR CI·배포·실브라우저 모두 통과. 현재 문서는 이 완료 상태를 뜻하지 않는다.
