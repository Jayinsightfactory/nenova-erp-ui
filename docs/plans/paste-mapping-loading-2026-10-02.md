# 붙여넣기 매칭 저장·조회 부하 보완

## 범위와 기준
- 매칭현황: 품목/거래처 별칭을 기존 웹 매칭 API로 추가한다. 빈 별칭/대상 없음은 차단한다. 저장 성공 응답과 재조회 후 완료 표시, 실패는 화면에 남긴다.
- 품목 선택/검증된 등록 완료: 서버 응답 성공 전 로컬 캐시를 저장 완료로 취급하지 않는다. 전체 일괄 경로의 누락된 학습을 추가한다. 실패 재시도는 매칭 API만 호출하며 ERP 등록을 다시 실행하지 않는다.
- 같은 정규화 별칭이 서로 다른 품목으로 쓰이면 일괄 학습을 보류한다. 수량·단위·차수는 매칭 저장 대상이 아니다.
- 현황 창 변경 후 부모 캐시는 서버 전체 맵으로 교체해 삭제/변경이 반영되게 한다.
- '분석 결과 열기'는 '등록분배하기'로 표시한다. 클릭은 검토 화면을 열 뿐 즉시 원장을 쓰지 않는다.
- 자동 사전분석 및 디스크 영구 분석 보존은 유지한다. 원문 조회/이력/상태 자동 주기를 완화하고 수동/작업 직후 새로고침은 유지한다. 숨김/오프라인/중복 진행 중 배경 조회는 억제한다. 작업권 heartbeat 및 쓰기 직전 검증은 유지한다.

## 근거
- 실제 dnSpy CLI FormOrderAdd를 2026-10-02 재실행. GetDataProduct는 Product.ProdKey→OrderMasterKey, btnSave_Click은 별도 원장 저장. 별칭은 웹 전용이며 EXE 품명/키를 수정하지 않는다.
- 운영 SELECT: ProdKey447 Moon Light/박스. 39-02 ViewOrder 2025=6/2026=24, ViewShipment 2025=4/2026=24; 활성 품목3284. 표본 조회69ms로 전체 서버 장애라고 단정할 근거는 아님.
- 현 learnItemMapping은 POST 응답을 검사하지 않고 로컬 먼저 저장하며 catch를 무시. 전체 일괄은 학습 호출 없음. 현황은 편집·삭제만 존재.
- feed5초, 상태 API3개15초, 전체 이력15초, 분석 후 업체별 상태8초(중복 방지 없음) 경로 확인. 실제 운영 CPU/SQL wait 병목의 비율은 미계측.
