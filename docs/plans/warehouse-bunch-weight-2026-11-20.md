# 47-01 입고 단 수량과 중량 합계

2026-11-20 설치 Nenova.exe의 ExcelLoadingPackingList.MakeTempTable은 I열을 BunchQuantity로 읽고, InsertMaster에서 uspCreateWarehouse와 주차 재고계산을 호출한다. 운영 usp_CreateWarehouse 정의의 출고·견적 단 분기는 모두 입력 BunchQuantity를 사용한다.

- 원본의 명시 행 단 수량을 보존한다. 원본의 단당 송이 또는 박스당 단 값이 명시됐을 때만 정수로 산출하고 값이 충돌하면 보류한다. 기존 상품 마스터로 결측 단을 대체하지 않는다.
- EC/US 직접 입고와 기존 Excel 입고에서 단 출고 또는 견적 상품에 양수 실물 수량이 있으면 누락·0·인쇄 포장값 충돌을 막는다. 기존 저장 경계를 동일 정책으로 통과해야 한다.
- 새 미리보기는 조회만 한다. 최종 Excel 저장은 트랜잭션에서 품목 일치와 단위를 재확인한다. 상품 합계에서는 중량 전용 품목 3100/3101 및 동일 원장의 구조가 확인된 예전 중복 중량 행만 뺀다. 일반 품목은 이름에 중량 문구가 있어도 포함한다.
- 운영 읽기 확인에서 8169는 원시 46,037과 상품 42,500송이, 7480은 원시 46,664와 상품 43,750송이·70박스·0단이었다. 8188은 7,600송이·2박스, 8189는 11,250송이·1박스 유지. 2025 동일 세부차수·같은 송장번호는 0건.
- 2026/47-01 대상 네 품목 주문 27행·출고 21행·확정 출고 0·견적 0. 기존 입고 수량과 직접 주문/출고/견적/손익 원장을 수정하지 않는다. 승인된 신규 저장의 기존 주차 재고 재계산만 실행한다.
- Nivalia 1654, Mystic 327496, Hood 201693의 실제 단 원본은 미확인이다. 현재 마스터 산술은 보정 근거가 아니다.

신규 입고 양수 단 실패 대조는 동일 정책에서 명시 단 통과, 누락/0/인쇄 충돌 차단, 박스 출고·단 견적을 확인한다.

운영 스키마의 WarehouseKey는 IDENTITY 또는 DEFAULT가 없다. 신규 Excel 웹 저장에서 기존 usp_GetNextKey와 재고 게이트 V2를 재사용한다. 새 관리 번호·원장·StockHistory·재고 계산과 읽기 확인은 하나의 트랜잭션이다. 같은 연도·세부차수·농장·인보이스의 활성 중복만 차단한다.

47-01 대상 출고 상세에 연결된 ShipmentDate 19, ShipmentFarm 0, Amount/Vat/isFix 존재 18, 해당 주차 WebProfitReport 확정 0. 소급 보정은 자료 범위와 후속 영향을 재검증해야 한다.

실제 SP는 새 WarehouseKey를 인자로 받지 않고 공용 TempWarehouseDetail 전체를 읽는다. 운영 4행은 작업 중인지 확인할 수 없으므로 재사용하거나 제거하지 않는다. Excel 신규 경로는 기존 직접 인보이스와 같은 scoped 상세, StockHistory/품목 재고차액, V2 게이트/재고계산 도우미를 재사용한다. 공용 준비 테이블 접근이 없다.

루프백 127.0.0.1:14339의 임시 고유 SQL DB에서 실제 Excel API 핸들러의 명시 40단→2박스·40단·400송이·출고2·견적40·금액100을 검증했다. 독립 실행한 캡처 전산 SP 결과와 일치하고, 누락 차단, 조회 미리보기, 동일 키 중복 차단, 2025 동차수, 기존 staging, StockHistory 수량차액을 확인했다. 기존 직접 인보이스 전체 SQL 회귀의 동시성, 재고 실패 롤백, 응답 유실 처리도 통과했다.

격리 SQL 최종 재실행에서 ViewWarehouse 읽기값과 상세 수치가 같았다. 주문/출고 원장과 준비 테이블 전체 스냅샷도 저장 전후 일치했다. 수입 회귀 279건 통과, 조건부 6건 건너뜀. 입고 엑셀 및 ERP 쓰기 범위·235개 계약·dnSpy 검사 통과.
