# 카톡 요청·변경 이력 밀집 확인 화면

## 사용자 결정 (2026-09-11)

카톡 내용과 대응 작업이 한눈에 연결되는 것이 우선이다. 기본 열은 카톡 변경 요청,
대응 작업, 매칭 상태다. 상세 수량·잔량·원문·감사 내역은 필요할 때만 펼친다.
1920×1080 CSS pixel / 100%에서 먼저 검증하며 작은 화면에서도 조작을 보존한다.

## 표시 계약

- 최신순 변경 요청이 기본이다. 매칭된 요청도 같은 목록에서 확인한다.
- 명확한 순수 잔량 목록은 잔량 안내 탭, 분류 불명은 분류 확인 탭에 건수와 함께 보존한다.
- 취소 뒤 재고로 잡으라는 혼합 메시지는 변경 요청이다. 원문은 삭제하지 않는다.
- 한 카톡 원문은 한 묶음이다. 여러 요청 중 일부만 근거가 맞으면 일부 매칭으로 표시한다.
- 자동 매칭은 정확한 sourceIdentity와 requestId에 대응하는 분배 변화 근거에 한한다.
  주문 이력이나 현재 재고, 사용자의 수동 표시만으로 자동 매칭을 주장하지 않는다.
- 근거가 없는 상태는 미확인이다. 미처리라고 단정하거나 기존 ERP 작업을 막지 않는다.
- 직접 처리함/미처리/내 표시 취소는 기존 별도 수동 원장 기능이며 자동 배지와 분리한다.
- 일상 안내는 접고 실제 조회/저장 실패는 보이게 한다. 기존 15초 제한 조회,
  늦은 응답 격리, 선택·입력 초안 보존, 연도·세부차수 범위를 유지한다.

## 부작용 표

| 동작 | Order/Shipment/Estimate/Stock | 카톡 원문 | 수동 표시 원장 |
|---|---|---|---|
| 조회·분류·탭·펼치기 | 보존 | 보존 | 읽기만 |
| 선택 원문을 입력으로 | 보존, 자동 분석·등록 없음 | 보존 | 보존 |
| 직접 처리함 표시·취소 | 보존 | 보존 | 기존 UUID/CAS 경로만 |

SQL, EXE 저장 방식, 기존 분석·추가·취소·확정 API는 변경하지 않는다.

## 완료 검사

분류·부분 매칭·중복 식별값 회귀, 기존 ERP 계약, manifest, 쓰기 보호, 빌드,
1920×1080 브라우저 밀도·잘림·상태·실패 보존 검사 후 운영 읽기 전용 확인.
운영 원장을 테스트 목적으로 추가/취소하지 않는다.
