# Codex 하위 작업 모델·권한 운영 규칙

## 목적

설계 품질은 유지하면서 사용량을 줄이고, 하위 작업이 권한 승인 대기 때문에 멈추지 않도록 한다. 이 문서는 `docs/NENOVA_CONTROL_TOWER.md`의 세션 운영 규칙을 보완한다.

## 기본 원칙

1. 메인 작업은 컨트롤 타워이자 유일한 통합 책임자다.
2. 고성능 모델은 설계, ERP 부작용 판단, 보안 경계, 최종 통합 검토에 집중한다.
3. 범위가 확정된 구현, 검색, 테스트, 문서 정리는 더 경제적인 모델에 배정한다.
4. 하위 작업에는 필요한 파일, 근거, 의존성, 허용 범위와 완료 기준을 시작 전에 모두 제공한다.
5. 하위 작업은 승인 요청을 생성하지 않는다. 승인이나 추가 권한이 필요한 동작을 발견하면 실행하지 않고 메인 작업에 반환한다.
6. 외부 쓰기와 운영 원장 쓰기는 하위 작업에서 수행하지 않는다.

## 모델 배정표

| 단계 | 기본 모델 | 추론 강도 | 담당 범위 |
|---|---|---|---|
| 설계·PRD·계약 | `gpt-5.6-sol` | `xhigh` | 요구사항 분해, 데이터 계약, side-effect matrix, dnSpy/DB 근거 해석, 수용 기준 |
| 최고위험 설계 | `gpt-5.6-sol` | `max` | ERP 쓰기 구조, 마이그레이션, 인증·권한·테넌트 경계처럼 잘못되면 데이터 손실 또는 유출이 가능한 경우만 |
| 범위가 확정된 구현 | `gpt-5.6-terra` | `medium` 또는 `high` | 설계서와 계약에 따른 코드 작성, 독립 모듈 구현, 회귀 테스트 추가 |
| 기계적 작업 | `gpt-5.6-luna` | `medium` | 파일 검색, fixture 작성, 문서 정리, 화면 여백 조정, 테스트 실행, 로그 요약 |
| 최종 통합 검토 | `gpt-5.6-sol` | `high` 또는 `xhigh` | 구현-계약 일치, 교차연도·ERP 부작용·보안·회귀 위험 최종 판정 |

- 고성능 모델은 동일 내용을 반복 구현하거나 장시간 테스트를 돌리는 데 사용하지 않는다.
- 단순 작업이 예상보다 복잡해지면 작업자가 임의로 범위를 넓히지 않고 `NEEDS_REDESIGN`으로 메인에 반환한다.
- 지정 모델을 사용할 수 없는 환경에서는 같은 등급의 사용 가능한 모델로 대체하되, 모델명과 대체 이유를 작업 보고서에 기록한다.

## 권한 등급과 실행 위치

| 등급 | 작업 예시 | 실행 위치 | 하위 작업 처리 |
|---|---|---|---|
| `P0_LOCAL` | 저장소 읽기, 허용 파일 수정, 로컬 테스트·빌드 | 하위 작업 | 승인 없이 실행 |
| `P1_EXTERNAL_READ` | GitHub 상태 조회, 운영 웹 읽기, DB SELECT, dnSpy 증거 수집 | 메인 작업 사전 준비 또는 전용 읽기 검증 작업 | 시작 전에 연결·인증·자료를 준비한 경우만 실행 |
| `P2_EXTERNAL_WRITE` | 브랜치 전송, 변경사항 검토 요청 생성, 병합, 배포 | 메인 작업 | 하위 작업 금지 |
| `P3_SENSITIVE_WRITE` | 운영 DB INSERT/UPDATE/DELETE, 데이터 보정, 비밀값·권한 변경, 파일 삭제 | 메인 작업 | 사용자 명시 승인 직후에만 실행 |

권한을 “전체 승인”했다는 이유만으로 `P2`·`P3`를 하위 작업에 넘기지 않는다. 메인 작업이 대상과 범위를 확인한 뒤 직접 수행해야 한다. 아직 구체화되지 않은 미래 동작은 미리 포괄 승인할 수 없으므로, 하위 작업이 추측해서 실행하지 않는다.

## 하위 작업 시작 전 메인 사전 준비

메인 작업은 하위 작업을 만들기 전에 다음을 끝낸다.

- 최신 기준 코드와 독립 작업공간 준비
- 필요한 입력 파일을 작업공간 안의 승인된 경로로 복사 또는 연결
- 패키지 의존성과 로컬 실행 환경 확인
- 필요한 로그인·저장소·읽기 전용 연결 상태 확인
- 민감정보 원문을 제외한 dnSpy/DB/운영 웹 증거 묶음 제공
- 수정 가능한 파일과 금지 파일 확정
- DB 읽기·쓰기 테이블과 사용자 동작별 부작용 표 제공
- 모델, 추론 강도, 사용량 상한 역할 지정
- 완료 기준과 필수 테스트 지정

이 준비가 끝나지 않으면 하위 작업을 시작하지 않는다.

## 하위 작업 승인 요청 금지 계약

하위 작업은 다음 형식으로 시작한다.

~~~text
[승인 정책] APPROVAL_FREE_CHILD
[모델 역할] ARCHITECT | IMPLEMENTER | MECHANICAL | REVIEWER
[허용 권한] P0_LOCAL (명시적으로 준비된 P1_EXTERNAL_READ만 예외)
[금지] 승인창 생성, 운영 DB 쓰기, push/병합/배포, secret 조회, 다른 작업공간 접근
[권한 부족 시] 작업을 멈추지 말고 가능한 로컬 작업을 완료한 후 NEEDS_MAIN_PREFLIGHT 항목만 보고
~~~

예상하지 못한 권한이 필요하면 승인 요청을 띄우지 않고 아래 구조로 반환한다.

~~~text
NEEDS_MAIN_PREFLIGHT
- 필요한 동작:
- 필요한 이유:
- 대상 시스템/파일/테이블:
- 읽기 또는 쓰기:
- 안전한 대안:
- 완료된 로컬 작업:
~~~

메인 작업은 이 요청을 검토해 필요한 작업만 직접 수행하고, 결과를 민감정보 없이 하위 작업에 다시 제공한다.

## 기본 작업 흐름

1. 메인: 사용자 요청과 기존 미완료 작업을 정리한다.
2. 설계 작업: `gpt-5.6-sol/xhigh`가 PRD, 계약, 위험표, 수용 기준을 만든다.
3. 메인: 설계를 검토하고 권한·입력·작업공간을 사전 준비한다.
4. 구현 작업: `gpt-5.6-terra`가 서로 겹치지 않는 파일 범위에서 구현한다.
5. 기계 작업: `gpt-5.6-luna`가 fixture, 문서, 테스트 실행과 결과 정리를 담당한다.
6. 메인: 변경을 한곳에 모으고 충돌을 해결한다.
7. 최종 검토: `gpt-5.6-sol/high~xhigh`가 계약·ERP·교차연도·보안 회귀를 판정한다.
8. 메인: 필요한 외부 쓰기와 운영 반영을 수행하고 실제 결과를 확인한다.

## 병렬 실행 규칙

- 동시에 실행하는 하위 작업은 기본 2~4개로 제한한다.
- 같은 파일, 같은 쓰기 API, 같은 DB 테이블의 변경은 병렬화하지 않는다.
- 설계가 끝나기 전에 구현 작업을 시작하지 않는다.
- 각 작업에는 한 명의 수정 책임자만 둔다.
- 통합·병합·배포 책임자는 항상 메인 작업 하나뿐이다.
- 하위 작업의 완료 답변은 메인 작업에 자동 보고하고, 메인은 사용자에게 한글 업무명으로 통합 보고한다.

## 작업 보고서 필수 항목

- 사용 모델과 모델 역할
- 추론 강도
- 권한 등급
- 메인 사전 준비 완료 여부
- 변경 파일과 변경 금지 파일
- 실행한 테스트와 실패 원인
- 확인한 실제 데이터와 확인하지 못한 실제 데이터
- `NEEDS_MAIN_PREFLIGHT` 또는 `NEEDS_REDESIGN` 여부
- 다음 하위 작업에 전달할 입력

## 적용 범위

이 규칙은 Codex 하위 작업, 별도 Codex 작업, Claude CLI 병렬 작업에 공통 적용한다. 다만 각 도구의 권한 체계는 별도이므로 “메인에서 승인했다”는 문구만으로 다른 작업의 권한이 기술적으로 상속된다고 가정하지 않는다. 승인 없는 실행이 필요하면 메인 권한을 상속하는 하위 에이전트를 우선 사용하고, 독립 작업에는 `P0_LOCAL` 범위와 사전 준비된 자료만 배정한다.
